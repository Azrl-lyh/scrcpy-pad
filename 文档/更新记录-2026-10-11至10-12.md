## 2. 逐个问题的实现要点

### 2.1 #1 悬浮窗层级
- 旧实现只在勾选时调用 `with_always_on_top()`，取消勾选后**没人把层级降回去**，于是继续保持置顶。
- 现在每帧按当前勾选值显式设置 `AlwaysOnTop | Normal`，勾掉即掉出置顶。

### 2.2 #2 组合键 `leftshift+左键` 不触发（根因已定，暂不改）
- 根因：输入层在**组合键判定窗口完成之前**就用 `system_key_member` 把该键当"系统键"处理了；而当前「三角洲」方案把 `recoil.trigger_key` 绑成了 `272`（`BTN_LEFT`，压枪触发键），于是**任何含左键的组合键都永远等不到闭合**。
- 用户 2026-10-11 明确选择：**暂不修改**（"2. 不同意。暂时不修改。"）。界面上只加了一行提示说明这个坑。

### 2.3 #3 水平补偿并入档位表
- 原状：垂直补偿按档位（`strengths`）多套，但水平补偿（幅度/周期/波形）是**全局一份**。
- 现状：`Recoil` 新增三个**按档并行**的向量 `gear_horizontal_px` / `gear_horizontal_period_ms` / `gear_horizontal_wave`（全部 `#[serde(default)]`），切档时垂直与水平**一起切**，各档可分别设置。
- 老配置迁移：加载时若 per-gear 为空，就把老的全局值**复制到每一档**（手感逐档不变）；有一条单测锁死这个迁移不变量。面板上原来那块独立的「水平补偿」已删除。
- 档位增删/重排共七条并行向量保持同步（`sync_gears` / `add_gear` / `remove_gear` / `move_gear`）。

### 2.4 #4 未绑定的系统键走原生转发
- 现在"未绑定"= 直接把原生事件转发给 scrcpy，不再被我们的映射吞掉；同时鼠标侧也做了区分：**未绑定的鼠标键/滚轮放行给 scrcpy，鼠标位移仍然被我们吞**（`mouse_shield_swallows` / `mouse_button_bits`），避免两套输入打架。
- 另外增加了**鼠标按键真实状态探针**（`RAW_BTN_DOWN` 位图 + `raw_button_oracle`）：我们"以为抬起了"但物理上仍按着的键，不会被合成释放。

### 2.5 #5 轨迹（trace）默认落盘
- 三个优先级：`--trace <路径>` > `SCRCPY_PAD_TRACE` > **默认**（配置目录 `trace-<时间戳>.jsonl`）。默认开启后，用户双击启动也能拿到轨迹。
- 关键修复：以前 `BufWriter` 放在一个**永不析构**的 `OnceLock` 里 → 文件一直是空的；现在**逐行 flush**。
- 容量：同目录只保留最近 3 个 `trace-<数字>.jsonl`，启动时自动删最旧的。
- 记录内容：`in`（捕获到的输入，含位移/按键）、`out`（**确实要写进 socket 的**指令，落在写线程里 ⇒ 这是"我们到底发了什么"的唯一真相）、`st`（Raw Input 状态机）、`aim`（瞄准/门控/锚点/落指/其它触点/总映射）。

### 2.6 单实例守卫 + "零残留"
- Windows 用命名互斥体 `Local\scrcpy-pad-single-instance-v1`；已有实例时**不再静默起第二个**，写日志并以退出码 `2` 结束。
- 所有退出路径（正常关闭 / `--selftest` / `--mask-selftest` / 风格重启循环 / 出错）统一走 `fn finish()`：flush 轨迹 → 恢复系统状态 → 关闭控制通道 → 退出。
- 单测用**测试专属锁名**，避免"我在跑测试"被误报成"程序还开着"。

## 4. 第 6 条（手碰手机 → FPS 锁死）的取证与修复

### 4.1 现场证据（用户真机，2026-10-12 03:35:52–03:38:51）

轨迹文件：`配置目录/trace-1791747352.jsonl`（2.4 MB）；诊断日志：同目录 `diagnostics.log`。

- **锁死那 4 秒我们一直在发**：`out` 记录显示持续下发合法坐标（屏幕空间 2772×1280 内）的 `MOVE` 与"重叠换手"`DOWN/UP`，例如 `t=101791 DOWN pid=3000 (1386,537)` / `t=101791 UP pid=3001 (1586,699)`。`out` 记录落在**写线程**里（即命令真的进了 socket），而诊断日志这段时间**零 WARN / 零 ERROR**。
- **重叠换手解不开**：整段锁死期间共 13 次重叠换手（新指先按下、旧指后抬起，指针数**从不归零**），设备端始终不理会。
- **全抬才能解开**：用户实测 F8（关映射 → 抬起全部触点）、F9（退出/重进 FPS → 先 `aim_lift`）、以及新做的「唤醒视角」键（只抬指）——**几乎一按就夺回控制**；`强制重连`（重启通道，也会清空本地触点状态）同样有效。三种手段唯一的共同动作是：**把我们按着的那根瞄准指抬起来（零触点）**。
- **不是链路问题**：通道存活自检、`/proc/net/unix`、设备端 `ps` 在正常态与锁死态表现一致；本程序退出时 `adb forward` 也被清干净（无残留）。

### 4.2 设备侧新发现（小米/Redmi + MIUI）

- `dumpsys input` 里除了 AOSP 的内容，还有 MIUI 的注入相关开关：
  `mInjectEventStatus`、`mIsFilterInterceptMode(=1)`、`mSynergyMode`、`mOnewayMode(=1)`、`mPadMode`、`mCtsMode`、`mNeedSyncMotion`…
  ⇒ 设备端**存在一层我们看不见的"注入过滤/拦截"开关**。
- `dumpsys input` 同时给出 InputDispatcher 的真实触点账本：`TouchStates: <no displays touched>`（空闲态），有触点时的形态待真机采样。
- 真机触摸屏 = `/dev/input/event5`（`focaltech_ts`，含 `ABS_MT_POSITION_X/Y` + `ABS_MT_TRACKING_ID`），**shell 用户可只读流式读取**（实测 `getevent -lt /dev/input/event5` 可跑，无权限错误）⇒ "手在摸手机"这个触发条件**我们看得见**。

### 4.3 结论与修复方向

综合起来最自洽的机制是：**物理手指在屏上的那段时间，我们这条注入流被设备/MIUI/游戏侧不再受理（或部分丢弃）**，导致设备端手势状态与我们的本地记账**错位**；错位之后**重叠换手也无法自愈**（指针数不归零 = 旧手势不结束），只有**全抬（零触点）再重建**才行。

因此修复分两层，**都不改变正常滑动时的手感**（正常滑动仍然是"新手按下 → 旧手抬起"的重叠换手，这是用户明确要求的语义）：

1. **取证层（默认开，纯只读）**：每 ~1s 读一次设备端账本（MIUI 开关 + `TouchStates` 原文 + 触点数），**变化时**写 INFO；同时只读监听"手摸手机"并记录边沿。⇒ 下次卡死时，诊断日志里就有设备端的真相，不用再猜。
2. **自愈层（新开关「卡死自愈」，默认开）**：满足任一条件即**自动抬指重建**（= 自动做一次「唤醒视角」，下一次位移自动重落指）：
   - **手离开手机**（物理触摸的 Up 边沿，即用户报的那个触发动作刚刚结束）；
   - **账本与本地对不上**（账本触点数 0 而我们本地认为瞄准指按着；或账本触点比本地多 = 我们发出去的 UP 没到设备端）。
   限流 300ms，宏步进/绑定捕获/取点期间不自愈；自愈次数与最近原因显示在悬浮状态行。

### 4.4 本轮落地的实现（已过三道门）

自愈**默认开启**（FPS 面板 `[卡死自愈（推荐）]`；老配置里没有这一项也读成开），只在下列任一时刻动作：

- **手离开手机**：只读监听触摸屏 `getevent`，物理手指抬起（Up 边沿）⇒ 立刻请求一次自愈；
- **设备端账本与本地对不上**：每秒只读一次 `dumpsys input`，若「账本触点数 = 0 而本地认为瞄准指还按着」或「账本触点比本地多（我们发出去的抬起没到设备端）」⇒ 立刻自愈。

"自愈" = 自动做一次 `aim_lift`（与「唤醒视角」键**同一个动作**）：只抬起那根瞄准指，**不关映射、不退出 FPS、不改门控/挂起/配置**，下一次鼠标位移自动重落指。

**防误触发的护栏**（每一条都有单测钉着）：

| 护栏 | 作用 |
|---|---|
| 账本必须"曾经看见过我们的注入"（新鲜账本读到 ≥1 且当时手机没被手摸）才可信 | 避免把"这台设备本来就不把注入触点显示在账本里"误判成故障 |
| 「账本 0 而本地按着」要**连续两份**采样都成立 | 避开"鼠标刚按下、设备端还没见到这根指"的窗口 |
| 手机被手摸期间，账本触点偏多**不算**故障 | 物理手指本来就会出现在账本里 |
| 两次自愈间隔 ≥ 300ms | 不会连续抬指 |
| 宏录制/步进、绑定捕获、截图取点期间不自愈 | 那些操作里用户正在界面上动手 |
| 账本读失败 = **未知**（不是 0） | adb 抖一下不会骗出一次凭空重建 |

- 悬浮状态行新增：`手机=摸/离`、`账单=N`（读不到显示 `?`）、`自愈=N(最近原因)`。
- 诊断日志里账本**只在变化时**记一条，内容含 MIUI 注入开关原文与 `TouchStates` 原文 —— 下次卡死时，设备端的证词就在日志里。

> 两个自救热键（唤醒视角 / 强制重连）**保留**，作为自愈没生效时的兜底；默认仍然不绑。

### 9.2 根因已定位并修复（2026-10-12 06:0x–07:0x）

**根因一句话**：`getevent` 在**只给一个设备路径**时输出**不带设备名前缀**，而解析器硬性依赖那个前缀 ⇒ **每一行都被丢弃** ⇒ "手离开手机"这条自愈触发在真机上**一条边沿都收不到**；另一条触发（设备账本）在本机**天生不可能成立**（见下）。两条触发全死 ⇒ 自愈永远不动作，这就是"依旧不行"。

**证据链（可复现）**

1. 两条流同时挂、同一次触摸对比（用户点屏）：
   - 带路径（App 就是这么跑的）：`[ 1024366.965761] EV_ABS       ABS_MT_TRACKING_ID   000434d7` ← **无** `/dev/input/event5:` 前缀
   - 不带路径（我上一轮"验证成功"用的形态）：`[ 1021725.473347] /dev/input/event5: EV_ABS       ABS_MT_TRACKING_ID   00043415` ← 有前缀
   - 解析器第一句是 `line.find("/dev/input/")`，找不到就把**整行（含 `[时间戳]`）**当事件体 → 第一个 token 是 `[` → 每行判为"不是我们要的事件"。
2. 设备端进程实证：`ps -A -o PID,PPID,ARGS` 显示 App 的子进程 `getevent -lt /dev/input/event5` **活着**、节点正确（全机只有 `event5 focaltech_ts` 声明 `ABS_MT_TRACKING_ID`，`pick_touch_screen` 也确实选中它）。
3. 用户点屏在**设备账本**里留下铁证：`设备端输入账本: … raw=Some(1) cooked=Some(1)`（`Last Raw Touch` 只反映物理触摸屏），而 App 一条边沿都没记 ⇒ 数据到了管道，是解析把它们全丢了。
4. **第二条触发天生不通**：用户按住左键让瞄准指落下时（06:02:14）账本仍是
   `触点账单=0 | TouchStates: <no displays touched>` ⇒ 本机 `TouchStates` **不统计注入触点**
   ⇒ `trusted`（`ledger_reflects_injection`）永不置位 ⇒ `ZeroWhileDown` 恒假、`n > local` 也恒假
   ⇒ **账本对账这条路在本机不可能触发**（它的价值只剩取证）。

**已修（3 处）**

| 修 | 内容 |
|---|---|
| **根因** | `parse_getevent_touch_line`：先剥 `/dev/input/...:` 前缀（若有），**再剥 `[时间戳]`** —— 单设备/多设备两种形态都认；老 getevent（无 `-l`、十六进制码）两种形态也都认。新增回归测试 `parses_single_device_output_without_prefix`（用真机原文） |
| **残留** | 每次通道重连都会 drop 一次触摸监听 Receiver，而线程正卡在管道读上、要等**下一次有人摸手机**才退出 ⇒ 设备端叠出多个残留 `getevent`（真机实测 3 个）。现在整进程只保留一个监听（重连只作废"手在不在手机上"的状态），并在 `finish()` 里 `adb::stop_physical_touch_watches()` 显式收掉子进程（Windows 不随父进程杀子进程）—— 用户明确要求零残留 |
