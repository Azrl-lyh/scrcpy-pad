## 2. 任务 2 · FPS 视角跳变 / 上下临界点修复（核心）

### 2.1 根因（两个独立缺陷叠加）

**缺陷 A —— 跳变（重复计入）**
旧路径：`aim_flush` 先把累计偏移整段注入，随后 `aim_recenter_with_carry` 又注入
`|O| − 阈值` 一次。设备实际收到的是 `2·O − th`，于是"推一点、画面转头两倍"，
表现为"跳变"。

**缺陷 B —— 上下临界点（触点被推出屏幕）**
"无边界"分支的注入**从不做屏幕夹取**。拖动量一旦超过"锚点到屏幕边缘"的余量，
触点就跑到屏幕外，被 Android 端直接丢弃 —— 表现为"推到某个点突然不动了"。
竖屏/横屏下"上下余量"通常远小于默认阈值 400，所以上下方向先撞上临界点。

### 2.2 方案：**单轴跑步机（per-axis treadmill）**

代码位置：`src/engine.rs`

| 符号 | 位置 | 作用 |
|------|------|------|
| `AIM_TREADMILL_MAX_HOPS` | engine.rs:1621 | 单次 flush 最多抬指/重按的跳数上限（32），防病态输入卡死 |
| `fn aim_band_limits` | engine.rs:1633 | 算出锚点在屏幕内每侧可用的**活动带**：`min(回转半径, 锚点到该侧边缘的距离)`，且 ≥0、再做一次屏幕夹取 |
| `fn plan_aim_treadmill` | engine.rs:1657 | 把待注入偏移 `(ox,oy)` 切成若干**每一段都落在活动带内**的段；返回 `(段列表, 残余偏移)`。残余偏移也夹回带内，保证 `st.ox/oy` 永不出带 |
| `fn aim_flush_unbounded` | engine.rs:1693 | 逐段下发；段与段之间**无缝抬指 → 重新按回锚点**；全程触点不离开屏幕 |
| 字段 `AimState::dead_paid` | engine.rs:1183 | "无边界模式下本轮拖动是否已扣过死区" |

要点：

- **精确总量**：所有段落之和 = 待注入偏移（在跳数上限内精确相等，见测试），
  即"手指推了多远、画面就转多少"，不再有 A 的重复计入。
- **无缝换手**：只在**段与段之间**抬指重按，且立刻按回锚点，服务端看到的是连续拖动；
  死区只在一轮拖动的**开始**扣一次（`dead_paid`），换手不重复扣 —— 物理上是同一根手指。
- **封顶行为**：极病态输入（超过 32 跳）时截断，但**每一段仍在带内**，触点始终不外溢。
- **`aim_flush` 的早退门槛**（engine.rs:1796）：
  `let after_dead = !aim.boundary && st.dead_paid; if !after_dead && mag <= dead { return; }`
  —— 已经换过手之后，残余偏移再小也不能被死区判定吞掉，否则换手后的小步推进会"卡住"。
- **W1-1 不回归**：`last_motion` 必须写**事件的捕获时刻** `at`（由 `aim_flush` 统一写），
  本轮删掉了 `aim_flush_unbounded` 尾巴上那句 `st.last_motion = Some(Instant::now())`
  —— 它会用"引擎处理时刻"覆盖"捕获时刻"，把 W1-1 修好的时延误差又引回来。

删除项：`aim_recenter_with_carry`（缺陷 A 的第二段注入）整体删除，替换为上面的跑步机。
`aim_lift` / `aim_release_local` / `aim_recenter` 三处都新增 `st.dead_paid = false;`（新一轮拖动重新扣死区）。

`clamp_to_screen` 的注释同步更正（engine.rs:5360 附近）：开放世界**故意**允许触点出屏，
FPS 无边界**不允许**（由 `aim_band_limits` 保证）。

### 5.2 终点解析（`src/engine.rs`）

```rust
type ActiveDir = (u64, f32, Option<(f32, f32)>);   // (pid, 角度, 手动终点)

fn wheel_dir_offset(m, cx, cy, angle_deg, manual, push) -> (f64, f64)
// Some(manual) → m.point(manual) − (cx,cy)；允许在基准圆外、也允许在圆内
// None         → (cos·push, sin·push)  ← 旧行为，一字未改

fn wheel_combo_offset(m, cx, cy, active, push) -> Option<(f64, f64)>
// 0 个方向 → None（收手）
// 1 个方向 → 它自己的落点（≈0 也算 None）
// ≥2 个方向 → 取前两个方向落点的**中点**，再把**距离规整到基准圆**（|push|）
```

**双键语义为何"取中点后规整到基准圆"**：用户原话是"最终响应目标 = 两键方向的**中点
（位于基准圆上）**"。若取字面中点，0°+90° 的合成距离只有 `0.707·push`，
**双键反而比单键推得更浅**，与"轮盘"手感矛盾；规整到基准圆后方向取两键之间的方位、
距离仍是"影响范围"定义的那一个 —— 这正是把影响范围当**基准**用的含义。
**此口径写在代码注释里，若用户本意是字面中点，改一处 `k` 即可。**
（测试中已断言：合成后模长 == push；某键有手改点时中点方向被明显拉偏。）

`fn wheel_part_offset(w, m, part: MacroWheelPart)`（engine.rs:5352）：
`Up/Down/Left/Right` → 固定角度、`manual: None`；`Custom(i)` → `dirs.get(i)?.angle_deg`
+ `directions[i].manual` —— **宏里的轮盘步骤与手按键走同一套落点规则**。
