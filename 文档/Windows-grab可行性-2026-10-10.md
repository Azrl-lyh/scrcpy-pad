## 1 grab 是什么、这个程序为什么需要它

Linux 侧 `capture.rs` 的 `grab` 走 `EVIOCGRAB` —— **独占打开** `/dev/input/event*`。一旦抓取：

- 该设备的原始按键**不再进入系统输入栈**，别的程序（包括游戏、桌面环境）一个事件也收不到；
- 松开（ungrab）时设备立刻回到系统。

程序需要它，是为了解决三件具体的事：

| # | 需求 | 触发场景 |
| --- | --- | --- |
| G1 | **被映射的键不该同时被电脑上的其它程序收到** | 把 W/A/S/D 映射成手机上的移动键，同时不希望电脑上的游戏/聊天窗也收到 W |
| G2 | **FPS 瞄准时鼠标不该满屏幕乱跑、撞到屏幕边就丢位移** | 甩枪时鼠标顶到屏幕边缘，位移被系统钳制 |
| G3 | **FPS 瞄准时鼠标不该被别的程序读走** | 焦点在别的窗口时仍能连续转向 |

Linux 一条 `EVIOCGRAB` 全包了。Windows 没有对应物，于是本程序用**三套机制凑**出了近似效果。

## 2 现状：Windows 侧已经在做什么

| 机制 | 实现位置 | 覆盖的需求 | 缺口 |
| --- | --- | --- | --- |
| **低级键盘/鼠标钩子**（`WH_KEYBOARD_LL` / `WH_MOUSE_LL`） | `capture.rs:2585` 起、`keyboard_proc` / `mouse_proc` | 输入**捕获**（读事件） | 钩子默认只是"旁听"，不回 1 就是转发 |
| **候选键吞掉**（swallow 掩码） | `capture.rs:95` `swallow_bit`、`capture.rs:669` `swallow` | G1 的**一部分** | **只有 8 个候选键**：Esc、F11、鼠标右/中/侧键×2、滚轮上/下。**字母数字键不吞** —— 这是**故意**的（README §1.6：映射开着也要能打字） |
| **Raw Input**（`RegisterRawInputDevices` + `RIDEV_INPUTSINK`） | `capture.rs:2534` | G2/G3 的**位移来源**：相对位移直接来自设备，不再依赖光标位置 | 只解决"我读到位移"，不解决"别人也读到" |
| **光标回中 + 回声识别** | `capture.rs:3237` 起、`capture.rs:3631` 起 | G2 的**规避**：让光标不断回到屏幕中部，别顶到边 | 快速甩动时回中跟不上；多显示器/缩放下有边界情况（代码里已有专门处理） |
| **透明系统光标**（`SetSystemCursor`） | `capture.rs:2029` | 观感：鼠标"消失"（焦点在 scrcpy 窗口也消失） | 只是**看不见**，不代表**冻结** |

**所以现状是**：输入**读**得干净（Raw Input），**看得见/看不见**控制得干净（透明光标），**物理位置**靠回中规避，**泄漏给别的程序**只在 8 个候选键上被堵住。而这最后一项在 Windows 侧已被明确标注为"只 Linux 可用"，并在界面上做成一行说明（`app.rs:10449-10450`）。

## 3 Windows 上"真正的 grab"有哪些路线

下面按"独占程度"从低到高排列。**关键分界线在 §3.6**：前五条都是用户态，都拦不住一件事。

### 3.1 路线 A：维持现状（钩子 + 吞键 + 回中 + 透明光标）

- **成本**：0（已实现）。
- **独占程度**：仅 8 个候选键的 legacy 消息被吞。
- **结论**：这是**基线**。

### 3.2 路线 B：`RIDEV_NOLEGACY` / `RIDEV_CAPTUREMOUSE`（Raw Input 的"不走 legacy"模式）

注册 Raw Input 设备时加 `RIDEV_NOLEGACY`，系统**不再为这些设备生成 legacy 消息**（`WM_KEYDOWN`/`WM_MOUSEMOVE`/`WM_LBUTTONDOWN`…），只把 `WM_INPUT` 发给注册窗口。效果上非常接近 grab：**别的程序收不到 legacy 键盘鼠标消息**。

- **前提**：注册窗口必须在**前台**（前台窗口一失去焦点，该标志即失效）—— 对"scrcpy 窗口在全屏打游戏"这个典型场景是满足的，对"切出去看攻略"就不满足了。
- **成本**：低。本程序**已经在用 Raw Input 通道**（`RIDEV_INPUTSINK`），加一个标志、并处理"前台/后台切换时重注册"的时机即可。约 **1~2 人日**。
- **风险**：`RIDEV_NOLEGACY` 会影响**整个系统**对这批设备的 legacy 消息生成（不只本程序），如果程序崩溃没来得及 `RIDEV_REMOVE`，用户会短暂地"键盘鼠标失灵"——必须做**进程退出/异常兜底**。另外它也会挡掉自己窗口的 legacy 消息，所以要保证所有输入路径都已走 `WM_INPUT`（程序现在是 **混合**：键盘走钩子、鼠标位移走 Raw Input，切换时要一并理清）。
- **独占程度**：**高**（前台时），但**不拦 Raw Input**（见 §3.6）。

### 3.3 路线 C：`ClipCursor` 真正钉住光标

`mouse_grab` 期间把光标裁剪到目标点周围的 1×1 矩形（或一个小矩形），**光标物理上就动不了**，不再需要"回中 + 回声识别"那套补丁；位移完全来自 Raw Input（本程序已经是这么读的）。

- **成本**：低。约 **0.5~1 人日**：进入/退出 `mouse_grab` 时 `ClipCursor`，并在窗口前台变化时重新施加（`ClipCursor` 会被焦点切换清掉）。
- **前提/风险**：① 目标程序自己也调 `ClipCursor` 时会互相覆盖（后调的赢）；② 全屏独占的 D3D 程序可能忽略；③ 多点几下的 `SetCursorPos` 仍会被裁剪矩形钳制，行为与现在不同 —— 要连同"回中"逻辑一起简化（这反而是**减代码**）。
- **注意**：`ClipCursor` **不**阻止其它程序读取光标位置，也不阻止它们收到鼠标消息 —— 它只保证"指针不会跑到别的地方去"。
- **独占程度**：中（解决 G2，不解决 G1/G3）。

### 3.4 路线 D：`ShowCursor` / 透明光标（已实现）

只影响观感。**与 grab 无关**，列在这里只是提醒不要把"看不见鼠标"当成"抓住了鼠标"。

### 3.5 路线 E：`BlockInput`

一次屏蔽**全部**键盘鼠标输入（包括对本程序自己的）。缺点：

- 无法"只拦被映射的键"，属于用核弹打蚊子；
- `Ctrl+Alt+Del` **永远拦不住**（设计如此），`BlockInput` 也有完整性级别与前台进程相关的前提，不满足时直接失败；
- 程序一旦崩溃没解除，用户会**完全失去输入**，只能等 `BlockInput` 超时或重启。

**结论：不采用。**

### 3.6 原理性边界：用户态拦不住别的进程的 Raw Input

这是上面所有用户态路线的共同天花板，必须写清楚：

> **低级钩子（`WH_KEYBOARD_LL`/`WH_MOUSE_LL`）能吞掉 legacy 消息，但不能阻止另一个进程通过 Raw Input（`WM_INPUT`）拿到同一批输入。**

Raw Input 是按"注册了该设备的窗口"投递的，钩子链的结果不影响它（这是社区的长期实践共识，Windows 从未提供用户态的"独占"原语）。后果：

- 用 Raw Input / DirectInput 读输入的程序（大量 PC 游戏、绝大多数"专业"输入软件）**照样能收到**我们想独占的键与鼠标位移；
- 反过来，**别的程序也拦不住我们**（本程序读 Raw Input 正是因此才在 FPS 场景下可靠）—— 这是同一枚硬币的两面。

**所以"真正的 grab"只有内核态一条路（§3.7）。**

### 3.7 路线 F：内核过滤驱动（唯一真正的 grab）

做法：写一个**上层过滤驱动**（KMDF filter）挂在 `kbdclass` / `mouclass` 上，或使用现成的开源驱动（Interception 一类），对指定设备设"全部过滤"，然后由用户态独占接收。

| 项 | 评估 |
| --- | --- |
| 独占程度 | **等价于 EVIOCGRAB**（整个设备只在你的用户态程序里可见） |
| 研发成本 | 自研 KMDF 过滤驱动：**20~40 人日**起（含 IOCTL 协议、用户态客户端、安装器、卸载清理、蓝屏排查） |
| 用现成驱动 | 省掉研发，但引入**第三方驱动的许可**（Interception 一类是 **GPL 系**，与本仓库 MIT **不兼容**，**需逐字核实**其许可证字样）与**分发**问题 |
| 签名 | Windows 10/11 x64 要求内核驱动被签名：**EV 代码签名证书**（约每年数百美元）+ 微软硬件开发者中心**证明签名/WHQL**流程；证书自 2021 起要求硬件令牌或云 HSM |
| 兼容性 | 每个 Windows 大版本、每次"内核驱动签名策略"变化都要复测；安全启动、HVCI（内存完整性）开启时对未签名/未 WHQL 驱动的拦截更严 |
| 反作弊 | 装过滤驱动的程序在**游戏侧**极易被判定为外挂工具（本程序的定位是"给手机做映射"，但 PC 上装驱动这一动作本身就会引起误判） |
| 维护 | 装/卸驱动要提权；卸载不干净会**永久影响用户输入** —— 这是最严重的一类故障 |
| 结论 | **不建议**。除非将来出现"必须在 PC 上开着别的程序、且必须让它一个键都收不到"的刚性需求，否则性价比极低。 |

### 3.8 其它被否掉的路线（列出以省去重复调研）

| 路线 | 否掉的原因 |
| --- | --- |
| `WinUSB` / `CreateFile` 直开 HID 设备（`\\?\hid#...`） | 只能**下发** feature report，**拿不到独占读**；输入路径仍对所有程序开放。❌ |
| `RIDEV_CAPTUREMOUSE` 单独用 | 只是"鼠标消息捕获"的一种表达，等同 B 的一部分，不拦键盘。 |
| `RegisterHotKey` 抢键 | 只能抢**组合**键，且抢了之后其它程序收不到、本程序也拿不到"哪个键被映射"的完整信息，与逐键映射的模型不匹配。❌ |
| 注入 DLL 挂钩目标进程的 `GetRawInputData` | 需要注入每个目标进程、极易崩溃、且**行为等同于外挂**。绝对不采用。❌ |
| Windows 游戏输入 API（`Windows.Gaming.Input` / GameInput） | 没有"独占/独占设备"语义。❌ |
| 会话隔离 / 沙箱 / 另开会话跑目标程序 | 影响面过大，不是"grab 实现"。❌ |

## 4 一条被忽略的便宜路线：把"吞键"从 8 个键扩到"全部已绑定的键"

现状的 `swallow` 是一个 **16 位掩码**，只覆盖 8 个候选键（`capture.rs:95` `swallow_bit`）。这是为了让钩子回调里"查一次位表 + 读一次原子"就完事，**零锁零遍历**。

而这件事的真正需求（G1）是"**凡是被我映射掉的键，就别再给别的程序**"。要满足它，只需把掩码换成一张按虚拟键码索引的 **256 位小位图（4×u64 原子数组）**，界面线程每帧把"当前配置里被绑定的物理键"置位；钩子回调只做 `bits[vk >> 6] >> (vk & 63) & 1`。成本 **1~2 人日**，性能与现在同量级（多两次内存读）。

**但要注意它和现有设计意图冲突**：现在的 README §1.6 明确写了"刻意不拦 Space/Tab/Enter/字母数字（映射开着也要能打字聊天框）"。所以这条**不能**直接改默认行为，应该做成一个可选开关：

> **[独占模式（吞掉所有已绑定的按键）]** —— 开启后，只要某个键当前被映射，映射期间它就不再传给电脑上的其它程序；未绑定的键照常。默认关闭（保持"映射开着也能打字"）。

这条路线买到的，正是 grab 在**用户态能买到的那部分**（G1 的 95%），且**零驱动、零签名、零提权**。它拦不住的仍然是 §3.6 的 Raw Input。

| **合计** | | **4.5** | | | |

### 6.2 不推荐（内核驱动，约 20~40 人日 + 持续成本）

若将来真的要做，前置条件必须全部满足（缺一条就不该做）：

1. 有**明确的用户需求**："PC 上并行的程序必须一个键都收不到"（而不是"偶尔泄漏很烦"）；
2. 驱动许可证已逐字核实、与本仓库 MIT 兼容，或自研；
3. 已准备好 **EV 证书 + 微软证明签名**的年度成本与流程；
4. 已规划**卸载清理**与**故障恢复**（驱动残留会让用户彻底失去输入）；
5. 已接受在 PC 游戏侧被误判为外挂工具的后果。

## 7 结论

1. **"Windows 下 grab"在用户态没有真正的等价物** —— 这不是本程序实现不力，而是 Windows 从未提供该原语；且低级钩子与 Raw Input 是两条平行通道（§3.6）。
2. **但"够用的那部分"很便宜**：§6.1 的四项 4~5 人日就能把 G1/G2 补齐到用户态的上限，且不引入任何签名、提权、驱动风险。
3. **内核驱动是唯一的真 grab，但不建议做**：成本比整个鸿蒙移植的控制链路还高，风险面（崩溃失输入、卸载残留、反作弊误判）却落在用户身上。
4. **文档要诚实**：无论做到哪一档，都必须写明"拦不住别的进程的 Raw Input"，避免用户产生"我已经完全独占"的错误预期。

> 与仓库既有决策的关系：`文档/全面审计与提升方案-2026-10-05.md` 的 V1-2③ 决定"Windows 隐藏 grab 复选框"——那是因为**当时**唯一的 grab 语义就是 `EVIOCGRAB`。本文提出的 §4/§6.1 是**另一个东西**（吞键范围可配 + `ClipCursor`），所以不是推翻那个决定，而是在 Windows 上给出一个**属于 Windows 自己的**选项。实施前需要用户拍板是否要这个选项。
