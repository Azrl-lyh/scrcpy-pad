## 1. Linux 能做得比 Windows 更好的

### 1. EVIOCGRAB 是内核级设备独占，Windows 的「准 grab」只能是近亲替代
- **能拿到什么**：整把设备独占，一条不落。开启映射后，同一把键盘/鼠标的按键在系统里**任何**前台程序都收不到，不需要按「已绑定键」白名单逐个过滤，也不存在「注册窗失焦就失效」的窗口。这是可行性级收益，不是百分比级。
- **Linux 的机制**：`ioctl(fd, EVIOCGRAB, 1)` / `EVIOCGRAB, 0`（evdev 设备节点的内核级 grab），配合 open(/dev/input/eventN) 后的 `read()` 事件流；独占期间内核对其它读者返回 -EAGAIN，输入不再走其它进程的 evdev 读路径。
- **现状**：src/capture.rs:2700 `let r = if want { device.grab() } else { device.ungrab() };`，上下文注释在 :2698-2710，成功/失败各落一条 diag_info「已独占/已放开」。开机与热插拔在 scan 里按设备类型选 flag（:2578-2582，键盘跟 grab、鼠标跟 mouse_grab）。evdev 侧实现是 `sys::eviocgrab(fd, 1)`（evdev-0.13.2 raw_stream.rs:645）。对照 Windows：只有「吞已绑定键」（capture.rs:434 `keyboard_swallows` + :447 `bound_key_words` 位图），且 :463-465 那条 `#[cfg(all(not(windows), not(test)))]` 分支恒返回 `[0;4]`，注释写明「那边的独占走 EVIOCGRAB 整把抓取」。
- **判定**：纯方案候选。（Windows 侧「做不到系统级独占」这一半是**已实测**：协议 B21/P1，`文档/DSH工作纪律-证据优先工程协议.md:1249-1257` —— NOLEGACY|INPUTSINK 注册 ret=1，注册方自收 WM_INPUT×6，另一进程前台窗仍收 6/6 legacy。Linux 侧从未真机跑过。）
- **代价**：代码 0 行（已实现）。权限需要读 /dev/input/event* 的 ACL（input 组）或 sudo；不需要 CAP_SYS_ADMIN。**不影响 Windows 侧一致性**：grab 是设备级还是进程级本来就分叉，配置字段 `grab_enabled` 两平台共用，语义靠 UI 文案解释。

### 2. Linux 没有 LowLevelHooksTimeout 那条 300ms 静默摘钩的死线
- **能拿到什么**：不存在「回调超时 → 系统静默摘钩 → 整套键鼠突然失灵且无日志」这一类故障模式。Windows 上钩子回调一旦超过 LowLevelHooksTimeout（默认 300ms）系统就不再调你，并且**不报错**；Linux 的 evdev 读循环卡住只会自己漏事件，不会波及全系统键鼠。
- **Linux 的机制**：没有用户态钩子这一层。事件由内核 input 子系统投递到 evdev 的环形缓冲，应用 `read()` 取，卡住只影响自己；EVIOCGRAB 期间若进程被 SIGKILL，内核在 fd 关闭时自动释放 grab，无残留独占。
- **现状**：src/capture.rs:13-16 模块头原文记录了 300ms 与「静默丢事件并摘钩」。Linux 侧对应实现是 :2675-2833 的 device_loop：硬错误累计到 20 次才注销槽位（:2798-2828），第一次与第二十次各记一条日志（:2800），退出前 :2831-2833 保证 `if grabbed { device.ungrab() }`。
- **判定**：纯方案候选。（300ms 那条本身是 Windows 侧的既有记录；Linux 侧「不会发生」要真机才能确证。）
- **代价**：0 行代码。无额外权限。不破坏一致性——反而减少一处分叉带来的用户困惑。

### 3. evdev 的 input_event.time 是内核设备时间戳真值，可以做真正的事件时刻
- **能拿到什么**：事件时刻不再受「用户态被调度走多久」影响。Windows 侧只能用钩子回调进场的 `Instant::now()`（capture.rs:43-54 注释：钩子结构体自带的 time 是 GetTickCount 系，1ms 分辨率、依赖 timeBeginPeriod、挂起恢复跳变、49.7 天回绕）。Linux 上事件在设备驱动里就打上时间戳，用户态晚读 3ms 也不会把事件时刻算晚 3ms。
- **Linux 的机制**：`struct input_event.time`（内核在事件入队时取 ktime），默认时钟 CLOCK_REALTIME，可用 `ioctl(fd, EVIOCSCLOCKID, &CLOCK_MONOTONIC)` 切成单调时钟免受 NTP 微调影响。
- **现状**：src/capture.rs:2666-2671 `fn event_time(ev, sys_anchor, inst_anchor)`：`let behind = sys_anchor.duration_since(ev.timestamp()).unwrap_or_default(); inst_anchor.checked_sub(behind).unwrap_or(inst_anchor)`。注释 :2659-2665 说明默认 CLOCK_REALTIME、每批重锚、不跨批累积漂移、时间戳落未来则夹到锚点。调用点 :2717-2721（每批取一次 SystemTime::now + Instant::now）、:2723。**没有** EVIOCSCLOCKID 调用——该 ioctl 在 evdev crate 里只存在于私有 `sys.rs:76`（`ioctl_write_int!(eviocsclockid, b E, 0xa0)`），未导出为公开 API。
- **判定**：需实测才能定。（机制成立，但「换单调时钟后延迟数字改善多少」必须真机对比；且当前每批重锚已吃掉主要漂移。）
- **代价**：代码约 10 行（一次 `libc::ioctl(fd, 0x400445a0, &CLOCK_MONOTONIC)`，注意 `_IOW(E, 0xa0, int)` 的编码），需要拿到 RawFd。无额外权限。不破坏 Windows 一致性（Windows 侧本来就不用结构体 time）。

### 4. EVIOCGKEY 问的是内核按键真值，Windows 的 GetAsyncKeyState 会「失明」
- **能拿到什么**：掉 release 时能拿到**确定**的真值而不是猜。Windows 侧 :5315-5335 的注释自己承认：前台是别的进程时 GetAsyncKeyState 对鼠标键会谎报 0，返回 0 同时表示「确实没按下」和「这次调用失败」，API 上无法区分，因此只能靠宽限期 + 下一个真事件兜底。Linux 的 EVIOCGKEY 返回一张位图，没有这种含混态。
- **Linux 的机制**：`ioctl(fd, EVIOCGKEY(len), buf)` 读内核维护的当前按键位图（按 KEY_* 码索引），另有 EVIOCGLED / EVIOCGSW 分别读 LED 与开关状态。
- **现状**：src/capture.rs:2886-2959 `fn reconcile_keys`：:2887-2897 取快照（paths / delivered / missed_seen），:2914-2959 **持着 st 锁**做全部 ioctl，:2922 惰性 open 真值句柄存进 `s.truth_devs`，:2938 `dev.get_key_state()`，失败就丢句柄。:2964-2976 lost 集合（delivered 有、内核没有）→ `release_all` 补发抬起；:2980-2994 missed 集合只报告、只在变化时报一次。节拍 RECONCILE_TICKS=4（:2383，≈400ms）。
- **判定**：纯方案候选。（代码路径完整但从未真机执行；Windows 侧「失明」是代码与注释事实，非协议登记项。）
- **代价**：0 行（已实现）。改进项见第 21、25 条（锁粒度）。无额外权限。不破坏一致性——Windows 侧对应机制是 GetAsyncKeyState + 宽限期，本来就各走各的。

### 5. epoll 单线程 multiplex 多设备，替代「每设备一条线程」
- **能拿到什么**：设备从 2 个涨到 5 个（键盘 + 鼠标 + 手柄 + 第二个键盘 + 触摸板）时，线程数与每秒唤醒次数不跟着涨。当前每设备一条线程、空转期 2ms 一轮（capture.rs:2796），单设备 500 次/秒唤醒，5 设备就是 2500 次/秒；epoll 一阻塞就只在真有事件时醒。
- **Linux 的机制**：`epoll_create1` / `epoll_ctl` / `epoll_wait`，设备 fd 设 O_NONBLOCK 后注册 EPOLLIN；或更简单的 `poll(2)` 单线程多 fd。热插拔配合 `inotify_add_watch(/dev/input, IN_CREATE|IN_ATTRIB)` 取代 2s 轮询。
- **现状**：src/capture.rs:2586-2599 每台设备 `std::thread::spawn` 一条线程，进 :2588 `priority::boost(Class::Highest)` 后跑 `device_loop`；:2795-2797 读不到就 `WouldBlock` → `std::thread::sleep(Duration::from_millis(2))`。全仓 `grep -rn epoll|inotify|eventfd src/ Cargo.toml` 零命中（仅两处误命中注释词：capture.rs:562、:2243）。热插拔靠 supervisor 每 RESCAN_TICKS=20 个心跳（:2378，≈2s）重扫一次。
- **判定**：纯方案候选。
- **代价**：代码约 300–400 行（device_loop 改状态机 + 每 fd 读缓冲 + 令牌校验外移），是本文改动量最大的一条。无额外权限。**会让 Windows 侧结构分叉**：Windows 侧必须「每设备一线程 + 消息泵」（RAWINPUT 的注册窗必须在有消息泵的线程上），只能各走各的，两平台共享的只有 CaptureEvent 出口。

### 6. SCHED_FIFO / sched_setscheduler 替代 setpriority 的「尽力而为」
- **能拿到什么**：满载时不再被 CFS 排到几十毫秒之后。当前 Linux 分支调 `setpriority(PRIO_PROCESS, 0, -5)`，普通用户没有 CAP_SYS_NICE 时内核直接 EPERM，代码用 `let _ =` 静默吞掉（priority.rs:41-52 注释自认）——**很可能现在 Linux 上的优先级提升完全无效**，而 Windows 侧 SetThreadPriority 是有效的。这是「Linux 现在反而更差」的一处。
- **Linux 的机制**：`pthread_setschedparam(pthread_self(), SCHED_FIFO, &{sched_priority: 1..99})` 或 `sched_setscheduler(0, SCHED_FIFO, ...)`，需要 CAP_SYS_NICE（或 RLIMIT_RTPRIO > 0，由 systemd 的 LimitRTPRIO= 给出）。次优解是 SCHED_RR 或 cgroup v2 的 cpu.weight。
- **现状**：src/priority.rs:41-52 全文即 Linux 分支，`libc::setpriority(libc::PRIO_PROCESS, 0, nice)`（:50），Highest=-5 / AboveNormal=-2。全仓 `grep -rn sched_|SCHED_ src/` 仅命中 priority.rs:43/:45/:50 三处，无 sched_setscheduler / SCHED_FIFO。调用点：capture.rs:2588（每设备读线程）、control.rs:283（注入写线程）、app.rs:3069（引擎 AboveNormal）。
- **判定**：需实测才能定。（先要真机确认 setpriority 现在到底成没成——diag 没记返回值，得加一行日志或 `ps -o ni` 看；成了才谈 SCHED_FIFO 的增量。）
- **代价**：代码 20 行（换调用 + 失败落日志）。权限二选一：`sudo setcap cap_sys_nice+ep ./scrcpy-pad`（单文件授权，重编译后失效）或 systemd user unit 里 `LimitRTPRIO=10`（见第 17 条）。**不建议两平台同形**：Windows 没有等价的 FIFO 概念；但**必须**把失败可见化，否则用户以为提了优先级。

### 7. /proc 与 /etc/os-release 让诊断直接说人话
- **能拿到什么**：用户报「不工作」时，日志里已经有发行版 + 内核版本 + 会话类型（Wayland/X11）+ 用户是否在 input 组 + 全部输入设备清单与判定结论，省掉一轮「你什么系统」。
- **Linux 的机制**：/etc/os-release 的 PRETTY_NAME、/proc/sys/kernel/osrelease、/proc/self/status 的 Uid:/Groups:、/etc/group 反查组名、环境变量 XDG_SESSION_TYPE / WAYLAND_DISPLAY / DISPLAY / DESKTOP_SESSION。
- **现状**：src/diag.rs:571-592 `os_description`（拼「发行版 · 内核 x.y」）、:604-623 `session_description`（:602-603 注释：Wayland 与 X11 对 evdev 抓取、光标隐藏的行为并不一致）、:627-658 `user_and_groups`（读 /proc/self/status 的 Uid/Groups，再用 /etc/group 反查，直接输出「含 input 组? 是/否」并提示 `sudo usermod -aG input`）。Windows 分支 :595-600 只有 OS / PROCESSOR_ARCHITECTURE。
- **判定**：纯方案候选。（代码已写但从未在 Linux 上执行过，输出格式没人见过。）
- **代价**：0 行（已实现）。无权限。不破坏一致性：Windows 走自己分支，但**输出行格式必须保持一致**（同一组 # 头 + 同样字段顺序），否则「导出诊断报告」的解读口径会分叉。

### 8. inotify 热插拔替代 2s 轮询
- **能拿到什么**：插上键盘到可用的最坏等待从约 2s 降到毫秒级。现在 RESCAN_TICKS=20 × HEARTBEAT_MS=100 ⇒ 最长 2 秒空窗（capture.rs:2376-2378），期间按键完全没人接。
- **Linux 的机制**：`inotify_init1(IN_NONBLOCK)` + `inotify_add_watch(/dev/input, IN_CREATE|IN_DELETE|IN_ATTRIB)`，inotify fd 本身可注册进同一 epoll 循环。
- **现状**：src/capture.rs:2458 起 supervisor 线程 → :2847 `sleep(HEARTBEAT_MS)` → :2855 `tick % RESCAN_TICKS == 0` 时 `scan`。:2605-2617 `event_paths()` 就是 `read_dir(/dev/input)` 过滤 event 前缀。inotify 全仓零命中（见第 5 条的 grep）。
- **判定**：纯方案候选。
- **代价**：代码 60–80 行（若与第 5 条合并做，增量更小）。无额外权限。Windows 侧对应机制是 WM_DEVICECHANGE 广播——语义类似，但**不要**为了同形而把 Linux 的 2s 轮询留成常态（只留作 inotify 失败时的兜底）。

## 2. Linux 独有、Windows 根本没有的能力

### 9. /dev/uinput 反向注入：本机造一个虚拟键鼠，绕过 adb
- **能拿到什么**：可以做「不接设备也能自检」——把已知事件序列注入虚拟设备，让整条捕获→引擎→注入链路在无 Android 设备时跑通（现在 Linux 侧零测试覆盖，就因为没设备就一条事件都没有）。也是实现「映射回本机」类功能的唯一途径。
- **Linux 的机制**：`/dev/uinput`（或 /dev/input/uinput），`ioctl(UI_SET_EVBIT / UI_SET_KEYBIT / UI_SET_RELBIT)` 声明能力 → `UI_DEV_CREATE` → `write(struct input_event)` 注入 → `UI_DEV_DESTROY`。evdev crate 自带 `pub mod uinput`（evdev-0.13.2 lib.rs:180），不需要新依赖。
- **现状**：**宿主侧零实现**。`grep -rn "uinput|uhid" src/ Cargo.toml` 的命中全是另一回事：src/control.rs:435 `pub fn uhid_create` / :452 `uhid_input` / :456 `uhid_destroy`，那是**通过 adb 发给设备端 scrcpy-server 的 UHID 指令**（让手机认一个虚拟 HID），与宿主 /dev/uinput 无关；其余命中是 `--mouse=uhid` 之类的参数文案（src/app.rs:401/:408/:415）。
- **判定**：纯方案候选。
- **代价**：代码 150–250 行（建设备 + 事件写 + 生命周期 + 测试夹具）。权限：/dev/uinput 通常 0660 root:input，需要 udev 规则（见第 16 条）或 sudo。**不破坏一致性**：纯测试/自检设施，不进生产路径；Windows 侧对应物是 SendInput，可以做对等实现但不必须。

### 10. EVIOCGABS 读数位板/触摸板的绝对坐标
- **能拿到什么**：数位板笔的绝对位置 + 压感（ABS_X / ABS_Y / ABS_PRESSURE），可以直接映射成游戏里的绝对瞄准或滑动，不需要从相对位移积分（现在鼠标路径只有 REL_X/REL_Y）。触摸板同理（ABS_MT_POSITION_X/Y）。
- **Linux 的机制**：`ioctl(fd, EVIOCGABS(axis), &input_absinfo)` 拿 min/max/fuzz/flat/resolution，或 `EVIOCGABSn` 一次读全部；多点用 ABS_MT_SLOT / ABS_MT_TRACKING_ID + ABS_MT_POSITION_X/Y（协议 B）。
- **现状**：**零实现**。`grep -rn "EVIOCGABS|get_abs_state|get_absinfo|AbsoluteAxis" src/` 零命中。capture.rs:2747-2783 只处理 RelativeAxis；:2649-2657 `is_mouse` 的判据是「supported_relative_axes 含 REL_X 且 REL_Y」，注释 :2644-2648 明写触摸板走 ABS 多点、没有相对轴，**因此根本不被认作鼠标**（被当成「不像键鼠」丢进 ignored，:2532-2541）。
- **判定**：纯方案候选。
- **代价**：代码 200+ 行（新事件类型 + 能力查询 + 归一化到屏幕坐标 + 引擎侧新输入源）。无额外权限（读已有 fd）。**会让配置分叉**：需要新配置字段（如 `tablet_mode`），Windows 侧 WinTab / WM_POINTER 是另一套，字段可共用但取值语义必须写清楚。

### 11. libinput 手势事件（三指/四指滑动、捏合）
- **能拿到什么**：手势可以直接当宏触发器，不需要「按住某键 + 鼠标划」这种笨办法。
- **Linux 的机制**：`libinput`（libinput_device_* / LIBINPUT_EVENT_GESTURE_SWIPE_BEGIN），或 Wayland 侧的 `zwp_pointer_gestures_v1`。注意 libinput 通常**自己开设备**，与 EVIOCGRAB 直读 evdev 是互斥的两条路线。

- **代价**：代码 300+ 行 + 一个新 C 依赖（libinput 无纯 Rust 等价物）+ 需要 input 组。**强烈不建议**：它会把「独占」这条命根子换掉，且与 Windows 侧完全无法对齐。这是本文最该砍的一条。

### 12. Wayland 的 zwp_relative_pointer_v1：天然无边界，不需要回中
- **能拿到什么**：Wayland 会话下鼠标可以无限移动而不撞屏幕边——不需要「移过头就 SetCursorPos 回中」。Windows 侧必须靠 16ms 节流的回中（capture.rs:3091 `RAW_RECENTER_INTERVAL = Duration::from_millis(16)`；回中判定与调用在 :5258-5265），每次回中是一次 SetCursorPos（`fn move_cursor` 在 :4778，SetCursorPos 在 :4780），既是同步阻塞 Win32 调用（:3208 注释原文「那些都是会阻塞的 Win32 调用」），又会在 :5236-5245 产生需要识别的「回声」（`motion.echo` 比对后丢弃，:5240/:5245 两处清空）。用相对指针后这段结构性开销和回声逻辑一起消失。

### 13. zwp_pointer_constraints_v1 是 ClipCursor 的正确对应物

### 15. /dev/input/by-id 给稳定设备身份

### 16. udev 规则 / input 组：把「必须 sudo」变成一次性安装

## 3. 性能优化点（按链路逐段拆）

> 链路：evdev → 每设备线程与 mpsc → 引擎 recv_timeout → 引擎判定 → control 队列 → TCP → adb → 设备端。下面每条都标「具体哪一处代码 + 换个做法能省多少」，并诚实说明那个省法是否只在 Linux 可行。

### 19. device_loop 的 WouldBlock → sleep(2ms)：链路里最大的一段可消除延迟
- **能拿到什么**：每批事件最多 +2ms、平均 +1ms 的额外延迟直接归零。参照系：引擎快档 IDLE_FAST_MS=4（src/engine.rs:167），Windows 上实测被抬到 10.2ms（timer.rs:3-10）；这一段 2ms 是纯用户态引入的、Linux 独有的浪费。顺带消掉每设备 500 次/秒的空转唤醒。
- **Linux 的机制**：`poll(2)` / `epoll_wait(2)` 阻塞等 EPOLLIN，或用 evdev 的阻塞模式（去掉 :2543 的 set_nonblocking(true)）直接阻塞 read；超时用 `ppoll` 一次给「最近一个 scheduled 动作到期时间」，并用 eventfd 做 stop 唤醒。
- **现状**：src/capture.rs:2543 `device.set_nonblocking(true)`；:2795-2797 `Err(e) if e.kind() == WouldBlock => { std::thread::sleep(Duration::from_millis(2)); }`（:2796）。对比 Windows 侧阻塞在消息泵（GetMessage）上，**没有**这个轮询。
- **判定**：需实测才能定。（2ms 是代码里写死的常量，属于读码事实；但「它对端到端延迟的实际贡献」要用 trace 时间戳量。）
- **代价**：代码 80–150 行（改成 poll/epoll + 保留 stop 标志的唤醒手段）。无 sudo。**这条不为 Linux 独有**：Windows 侧同问题用 WaitForMultipleObjects 也能解，但 Windows 侧等待已由消息泵驱动、问题不存在——所以实际只在 Linux 侧改写，不算分叉。

### 20. 每圈一次的令牌校验加锁（capture.rs:2695）
- **能拿到什么**：每圈省一次 Mutex lock/unlock + 一次 HashMap 查找，约 100–200ns。空转期每秒 500 次 × 设备数，满载时每批都要付。数字小，但它是**纯开销**，且这段代码在最高优先级线程上。
- **Linux 的机制**：不需要 Linux 特有机制，用 `AtomicU64` 存每设备的当前令牌即可。
- **现状**：src/capture.rs:2695 `if token != lock(&st).alive.get(&path).map(|s| s.token).unwrap_or(0) { break; }` —— 每圈一次全局锁。对照 :2417 `type Shared = Arc<Mutex<State>>`、:2420 `fn lock`（中毒恢复）。
- **判定**：纯方案候选。
- **代价**：代码 10–20 行（槽位里加 `Arc<AtomicU64>`，线程持有克隆）。无权限。**两平台同形**（Windows 侧也能受益），不产生分叉。

### 21. 每个按键事件一次加锁（capture.rs:2734-2739）
- **能拿到什么**：一批最多 32 条事件（evdev EVENT_BATCH_SIZE=32，evdev-0.13.2 lib.rs:220，一次 read 最多 32 条）最多省 32 次加锁-解锁，按 50–100ns/次算约 1.6–3.2µs/批。键盘连按时可观。
- **Linux 的机制**：无特殊机制，把整批的 delivered 变更攒成局部集合、批末一次加锁合并。
- **现状**：src/capture.rs:2734-2739 每个 Key 事件一个 `{ let mut s = lock(&st); if pressed { s.delivered.insert(key.0); } else { s.delivered.remove(&key.0); } }`；:2998-3008 `release_all` 同样是**每条**一次 `lock(st).delivered.remove(&code)`。
- **判定**：纯方案候选。
- **代价**：代码 30–50 行。无权限。两平台同形（Windows 侧同结构），不分叉。

### 22. 每批两次时钟系统调用（capture.rs:2717-2719）
- **能拿到什么**：空批（WouldBlock 之后紧接着的下一轮）也照样取 `SystemTime::now()` + `Instant::now()`，vDSO 路径约 20–25ns/次，合计 40–50ns/批，空转 500 次/秒就是 20–25µs/秒。**收益极小**，列出来是为了说明「为什么不做」。
- **Linux 的机制**：真要省的话，用第 3 条的 EVIOCSCLOCKID 把设备时钟切到 CLOCK_MONOTONIC，就**完全不需要 SystemTime 锚点**，只剩一次 Instant::now()。
- **现状**：src/capture.rs:2717-2721：`let sys_anchor = SystemTime::now(); let inst_anchor = Instant::now();` 在 `match device.fetch_events()` 的 Ok 分支里，**不管 events 是否为空**都取；:2723 `event_time(&ev, sys_anchor, inst_anchor)`。
- **判定**：需实测才能定。（机制清楚，但收益在纳秒级，需要确认是否值得为它引入 unsafe ioctl。）
- **代价**：代码 5 行（events 为空提前 continue）或 10 行（切时钟）。无权限。两平台无关。

### 23. 无界 mpsc 通道 + 引擎 recv_timeout 的结构性延迟
- **能拿到什么**：满载时不再让捕获线程无限往前排。`std::sync::mpsc::channel()` 是无界的，引擎被调度走 20ms，捕获线程就往队列里塞 20ms 的事件；醒来后一次性处理一批历史事件，注入的是「过去」的输入。改成有界通道 + 丢弃策略可以把这段延迟封顶。
- **Linux 的机制**：不依赖 Linux 特有机制；`std::sync::mpsc::sync_channel(n)` 即可。真正的 Linux 侧差异是**突发形态**：evdev 一次 read 最多 32 条、且设备被独占后事件不再分给别处，突发更集中。
- **现状**：src/app.rs:2898 `let (cap_tx, cap_rx) = channel::<CaptureEvent>();`（无界）；:3004 `Capture::start(cap_tx)`；:3070 `engine::run(shared, cap_rx, ...)`；src/engine.rs:3580 `rx: Receiver<CaptureEvent>`；:4366 `match rx.recv_timeout(wait)`。全仓无 `sync_channel`（grep 零命中）。对照 src/control.rs:66 已有 `MOVE_BACKLOG_LIMIT=256` 的「丢旧保新」策略——**捕获侧没有对应物**。
- **判定**：纯方案候选。
- **代价**：代码 50–80 行（含丢弃计数与诊断日志）。无权限。**两平台同形**（这条不是 Linux 独有，Windows 侧一样受益）；若只改 Linux 就会真的造成行为分叉。

### 24. control.rs 已在攒批，BufWriter 是负收益（反例条目）
- **能拿到什么**：0。列出来是为了把「看起来能优化」的地方钉住，避免下一轮有人再提。
- **Linux 的机制**：—（这里是可移植的 TCP 路径，与 Linux 无关）
- **现状**：src/control.rs:279-332 写线程：:283 提最高优先级，:284 `while let Some(cmd) = queue.pop()`，:300-315 一次唤醒把队列里已排好的命令攒到 `WRITE_BATCH_LIMIT=64`（:71），:316 `stream.write_all(&buf)` 一次写出。注释 :286-296 解释：Nagle 已关（:247 `set_nodelay(true)`），一条一写 = 一个 TCP 报文 + 一次系统调用，还要和视频流挤 adbd 转发。`BufWriter` 在这里只是多一次内存拷贝、并多一次 flush 时机决策。
- **判定**：纯方案候选。（「负收益」是结构推断，不必实测就能否掉。）
- **代价**：0（不做）。

### 25. reconcile 持锁做全部 ioctl（capture.rs:2914-2959）
- **能拿到什么**：400ms 一次的对账现在**持着全局 State 锁**对每台设备做 EVIOCGKEY；这期间所有设备线程的 :2695 / :2734 都阻塞。键盘多（3–4 把）时一次对账可能占锁几十微秒，最坏挤压一整个事件批。改成先无锁读全部真值、再加锁比对，可把锁持有时间压到 O(事件数)。
- **Linux 的机制**：无特殊机制；顺序调整即可。EVIOCGKEY 是纯读 ioctl，无副作用，本来就不需要锁保护。
- **现状**：src/capture.rs:2914-2959，进锁区间后 :2922 惰性 open 真值句柄（可能触发 open 系统调用！）、:2938 `dev.get_key_state()`；:2960 起才做 lost/missed 分流。注释没解释为何必须持锁。
- **判定**：纯方案候选。
- **代价**：代码 40–60 行。无权限。两平台同形（Windows 侧 reconcile 用 GetAsyncKeyState，锁结构类似）。

## 4. 平台一致性代价

### 26. grab 语义与文案已经在分叉，且必须继续分叉
- **能拿到什么**：把「哪些必须同形、哪些必须分叉」写成明文，避免下一次改动把 Linux 的 EVIOCGRAB 塞进 Windows 的「吞键」框架里。
- **Linux 的机制**：EVIOCGRAB 是设备级（对整个系统生效）vs Windows 的 WH_*_LL 是进程级（只对注册进程生效，且 P1 实测另一进程前台窗照样收 6/6 legacy）。语义层级不同，不是实现差距。

- **判定**：已实测（协议 B21/P1，`文档/DSH工作纪律-证据优先工程协议.md:1249-1257`：NOLEGACY|INPUTSINK 对其它进程无效；P1b 前台变体零收益 ⇒ 砍掉 G-d）。
- **代价**：0 行代码。**必须同形**：settings.json 的键名与布尔语义；**必须分叉**：UI 文案与「独占」的承诺口径——Windows 上不能承诺「别的程序收不到」。

### 27. swallow_bound_keys 在 Linux 上是一张恒空的位图
- **能拿到什么**：明确这是「Windows 专用字段在 Linux 上无效果」，不是 bug。

### 28. clip_cursor_in_aim 在 Linux 上是死字段

### 29. MouseCaptureMode::Mask 在 Linux 上静默回落隔膜

### 30. 光标消隐：接口在，Linux 实现是空壳
- **能拿到什么**：Linux 上「映射时隐藏光标」现在完全没做——接口函数是空的，调用点照常调，用户看不到任何效果。这是功能缺口，不是优化。

### 31. 设备身份的三种表达：路径 / VID-PID / 稳定 id
- **能拿到什么**：把「哪把键盘」这件事在三处表达统一，否则第 15 条落地时会出现「配置里记的是 eventN、日志里记的是设备名、UI 里记的是序号」的三口径。
