# 录入场景与取消语义 UX 方案（2026-10-10）

> 本文回答用户 2026-10-10 大改动第 1 条的附带要求：
> "同时思考其他类似录入场景并给出 UX 优化方案，单独输出为一份 md 文件。"
>
> 触发问题是"捕获中点击 [取消按键捕获]，这一次点击被录成了触发键"。该问题本身本轮已修（见 `文档/本轮改动记录-2026-10-10-134000.md` §1）。
> 本文不再复述那处修复，而是把它抽象成一条规则，逐个检查程序里**其余同类"录入中"场景**是否也合格，并给出改进方案。**本文只给方案，尚未实施。**

---

## 0 问题的抽象

程序的交互里有一大类状态叫 **"正在录入"**：

> 用户按了某个 [开始/设置/取点/捕获/修改…] 按钮后，程序进入一个**等待用户输入**的状态，
> 用户接下来的**按键**或**鼠标点击**不再按正常语义使用，而是被"记账"成了配置数据。

处于这个状态时，"我想取消"这个动作**本身也是一次输入**。于是有三重危险：

1. **取消动作被记账**：点 [取消] 的那一下鼠标/键盘事件落进录入缓冲，变成一条脏数据（本次的根因）。
2. **取消入口太远**：入口在别处（顶栏、另一个页签），用户要先找再移过去，路上还会产生更多被记账的输入。
3. **取消了但没清干净**：退出录入态后，半途产生的草稿/占用/缓存留在配置或界面里（"举着等按键"、黄色圆圈还在、"已取点"计数没归零）。

三者都会让用户产生同一个感受：**"这个东西不受我控制。"**

## 1 本次已落地的规则（作为后续标尺）

| 规则 | 实现 |
| --- | --- |
| **原地取消** | 取消/停止控件就摆在录入控件**自己那一行**，不在顶栏、不跨页签。 |
| **按下即生效** | 取消按钮按**下**就退，不等抬起（抬起可能落在别的控件上）。 |
| **取消区吞输入** | 每帧登记"就地取消/停止控件"的矩形（`app.rs:2910` `note_cancel_zone`），录入路径（`app.rs:2929` `swallow_cancel_click`）遇到落在这些矩形里的**按下**直接丢掉。 |
| **未落定不入账** | 录入只有走到"落定"那一步才写配置；取消一律是"丢弃缓冲"，不是"写入后再撤销"。 |
| **零残留** | 取消后清空录入缓冲（`app.rs:2435` `cancel_key_capture`）与界面态（黄色圈、草稿、提示行）。 |

## 2 判定标尺（六条）

拿这六条量每一个录入场景：

1. **有没有"取消"？**（有开始就必须有取消 —— 用户原话："有始必有终"。）
2. **取消入口是否就在录入现场？**（同页、同一行、同一弹窗内。）
3. **取消动作本身会不会被记账？**
4. **取消是否零残留？**（配置、界面、占用、日志请求都回到进入前。）
5. **取消是否可逆可预期？**（用户能否预知"我将会丢掉什么"。）
6. **有没有"不选择"的选项？**（用户原话："既然给了选择，就要给'不选择'的选择" —— 例如"不设置按键""不取点"必须是一个能走通的状态，而不是被迫随便点一下。）

## 4 逐项方案

### 4.1 修改响应范围：补一个 [取消修改]（优先级：高）

**现状**：`resizing` 期间在截图上拖或在数值框上滚，半径**实时**写进实时配置；退出只有 [完成]（`app.rs:9164-9178` 轮盘、`app.rs:12822` 键位）。用户想"我刚才改错了、退回去"只能按 Ctrl+Z —— 而撤销是按"整个操作"记的，拖了三次再撤销会退回到**进入之前**，如果他只想退一步就做不到。这违反"取消必须可逆、可预期"。

**方案**：

1. 进入 `resizing` 时记一份 `resize_entry: Option<f32>`（进入那一刻的半径；轮盘的半径与系数都记）。
2. [完成] 右边并列一个 **[取消修改]**（danger 色），点了把值写回 `resize_entry` 并退出，**不**入撤销栈（等于"从没发生过"，而不是"改了一次又改回来"）。
3. 该按钮登记进取消区（`note_cancel_zone`）—— 因为 FPS 瞄准开着时，点它的那一下可能被"按住才瞄准"之类的键吞掉/记账。
4. 提示行改成两段式：`修改响应范围中 —— 拖动/滚轮调整，[完成] 保存，[取消修改] 还原为进入前的 35.2px。`

**为什么不是"直接复用 Ctrl+Z"**：撤销栈是**全局**的，用户撤销一次会连带退掉上一次的其它操作；"取消本次修改"必须是**局部**的，两者语义不同。

### 4.2 滑动曲线编辑：把实时写回改成"确认制"（优先级：中）

**现状**：`ui_easing_editor`（`app.rs:9845`）在 `changed` 的每一帧就把参数写回实时配置，只在拖动开始记一个撤销点。关窗（X）**不是取消** —— 值早写进去了。

**方案**（两选一，建议 A）：

- **A（确认制，推荐）**：弹窗改成先改**副本**，底部放 `[应用] [取消] [恢复默认]`；[应用] 才写回并记一个撤销点，[取消]/X 关窗丢弃副本。曲线预览照样实时跟着副本画，所以"边调边看"的手感一点不丢。**收益**：关窗的语义变得可预期（"我关了就是没改"），也让"恢复默认"成为一个自然的第三个选项。
- **B（最小改动）**：保留实时写回，但把 X 换成显式的 `[完成] [撤销本次修改]`，并在弹窗标题旁标一块"实时生效"提示。**代价**：用户仍可能关了窗以为没改。

### 4.3 宏录制：加 [放弃本次录制]（优先级：中高）

**现状**：`macro_recording` 只有 [停止录制]（`app.rs:6417`，已进取消区），停止即把录到的步骤写进宏草稿。录错一次（比如中间乱按了几下）想重来，只能停止后再手动清空或 [取消编辑]。

**方案**：

1. [停止录制] 右侧并列 **[放弃录制]**（danger），点击清空 `macro_recording` 并保留**开始录制之前**的编辑区内容（进入录制时记一份 `macro_recording_entry: Vec<MacroInstruction>` 快照）。
2. 录制中的提示行补一句：`录制中 —— 操作虚拟键盘或键盘录入步骤；[停止录制] 保留结果，[放弃录制] 丢弃本次。`
3. 录制中 [载入草稿]/[另存草稿] 现已被拒绝（`app.rs:6850`、`app.rs:6899`），保持；但拒绝提示里应指路"先停止或放弃录制"。

### 4.4 扩展宏弹窗/取点类的"关窗即丢失"要给出预警（优先级：低）

这些场景已经是"关窗 = 全还原"（正确的取消语义），但用户**看不出来**关窗等于放弃。方案：

- 弹窗抬头加一行常驻小字：`关闭即放弃本次修改`。
- 若弹窗里有**已改动内容**（与打开时快照不同），标题栏图标变实心/加一个 `•` 记号，并在关窗时给一次**一次性**气泡提示（不做二次确认弹窗 —— 那是"用打扰换安全"，与用户要求的"取消要顺畅"相冲）。

### 4.5 后台任务的顶栏取消：位置是对的，补"取消后不掉状态"（优先级：低）

连接/截图/坐标刷新/音频唤醒/日志收集这五类**不该**用"就地取消"：它们没有就地控件，而且动不动就要打断用户正在看的界面。顶栏 + 固定槽宽（`app.rs:2092` `cancel_button_slot_width`）是恰当的。

要补的是**取消的**语义：取消后必须回到"从未点过"的状态（用同一个"未连接/未截图"的空态渲染），而不是停在一个半成品上。**建议逐个自查并加一条断言**：取消后相关界面态字段必须是初始值（截图取消 → 不显示旧图；连接取消 → 按钮回到 [连接]、自检回到未知）。

### 4.6 统一的"取消手势"（优先级：中，跨场景收益最大）

现在每个场景的取消载体都不同（按钮 / 关窗 / 点空白）。建议统一三件事：

1. **Esc = 取消当前录入**（优先级最高的一处通用键）。注意本程序**允许把 Esc 绑成键位**（`capture.rs` 的吞键表里 Esc 是候选之一），所以规则要写成：**录入态下 Esc 优先当取消**，因为录入态本来就在吞键盘；退出录入后再归还给用户绑定。这样不会与"Esc 被绑成返回键"打架。
2. **右键 = 取消当前录入**（取点场景尤其自然：右键在图上就是"我不要这个点"）。同样要检查右键是否已被绑定（`swallow_bit` 表里有右键），规则同上：录入态优先。
3. **双击空白 = 取消取点**（次级，可选）：取点的画布上双击空白处，等于 [取消取点]。

统一之后，用户的肌肉记忆是"**录错了就按 Esc / 右键**"，不用每次找按钮。**取消按钮仍然全部保留**（可发现性），Esc/右键只是快捷方式。

### 4.7 取点的辅助：十字线与吸附（优先级：低，纯增益）

取点时画一条贯穿画布的十字准线，鼠标附近显示**像素坐标**（已有）；再把草稿圈**吸附**到附近已有键位的圆心/边缘（按住 Alt 关闭吸附），可以显著减少"手抖差 3 像素"这类返工 —— 返工越少，"想取消"的次数就越少，这是从源头减少取消需求。

### 4.8 "有始必有终"的成对性检查表（快速自查用）

每加一个新入口时对一遍：

| 入口 | 必须存在的出口 |
| --- | --- |
| 开始录制 | 停止录制 **+ 放弃录制** |
| 开始取点 | 取消取点（原位）**+** 图上点一下 |
| 开始取键/捕获 | 取消设置（原位，按下即生效） |
| 开始改范围/半径 | 完成 **+ 取消修改** |
| 打开编辑器弹窗 | 保存/应用 **+** 关窗（= 放弃） |
| 新增草稿（还没落定） | 取消新增（丢草稿，不留占位） |
| 新建配置/新建宏/新增轮盘 | 删除（且删除后下标失效要有提示） |

## 5 建议的实施顺序

| 顺序 | 项 | 工作量 | 理由 |
| --- | --- | --- | --- |
| 1 | §4.1 修改响应范围 [取消修改] | 小（两个调用点 + 一个 `f32` 字段 + 一行按钮） | 唯一**真缺取消**的地方，且符合用户已明确的"有始必有终"。 |
| 2 | §4.6 Esc/右键 取消 | 中（需处理与绑定的优先级） | 一次改动惠及全部场景，是"取消"这件事的通用出口。 |
| 3 | §4.3 宏录制 [放弃录制] | 小 | 录制是最容易录错的场景，返工成本最高。 |
| 4 | §4.2 曲线编辑确认制 | 中 | 语义正确性提升，但使用频率低于上面三项。 |
| 5 | §4.4 / §4.5 / §4.7 | 小~中 | 观感与防呆，随版本捎带。 |

## 6 与已有承诺的一致性

- 用户风味要求 **"有始必有终"** → §4.1 / §4.3 是补终；§4.8 是把这条固化成自查表。
- 用户风味要求 **"用户有最大选择权：既然给了选择，就要给'不选择'的选择；取消必须无残留、可逆、可预期"** → §4.1 的 [取消修改]、§4.2 的确认制、§4.6 的 Esc/右键，都是把"不选择"变成一个**明确、便宜、随时可用**的动作。
- 本文全部为**方案**，未改任何代码；实施时应逐项单独提交说明，并各配一条单测（取消后配置与界面态等于进入前，是可以用纯函数断言的）。
