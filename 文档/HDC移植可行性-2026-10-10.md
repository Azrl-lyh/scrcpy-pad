## 0 结论速览

| 维度 | 结论 |
| --- | --- |
| **可行性** | **控制方向完全可行**（输入注入、截图取点、键位/轮盘/宏/FPS 的算法层一行不用改）；**实时画面（投屏）是最大风险点**，HDC 现有工具只给"一张一张的 PNG"，没有等价于 scrcpy 的 H.264 流；要恢复实时画面，**必须在手机上装一个自己的伴生应用**，等于重写 scrcpy-server 的视频那一半。 |

| **工作量（不含实时画面）** | **约 3~5 周**（1 名熟悉本仓库的开发者），得到"能玩、但快速连点/甩枪会比现在钝"的版本。 |
| **工作量（含实时画面）** | **约 2~3 个月**，其中一半时间花在手机端伴生应用的签名、投屏权限与延迟调优上。 |

## 1 现状：本程序到底依赖 ADB 与 scrcpy 的哪些东西

`scrcpy` 在本程序里其实干**两件事**，必须分开看：

| 角色 | 由谁提供 | 本程序怎么用 |
| --- | --- | --- |
| **画面显示** | scrcpy 主程序（独立窗口，独立进程） | `adb::launch_scrcpy`（`adb.rs:741`）把它拉起来，之后**完全不管它**，只管往参数里加东西 |
| **输入注入通道** | scrcpy-server 的 **control socket** | 本程序自己实现协议客户端 `src/control.rs`（INJECT_KEYCODE / INJECT_TOUCH / UHID_*） |

而 ADB 本身被用作"**投递器**"：

| 功能 | 源码位置 | 实际命令 |
| --- | --- | --- |
| 列设备 | `adb.rs:46` `list_devices` | `adb devices` |
| 屏幕尺寸（自然方向） | `adb.rs:74` `screen_size` | `adb shell wm size` |
| 屏幕尺寸（含旋转） | `adb.rs:97` `display_size` | `adb shell dumpsys window displays` |
| 刷新率 | `adb.rs:114` `display_refresh_rate` | `adb shell dumpsys SurfaceFlinger --latency` / `dumpsys display` |
| 截图（取点用） | `adb.rs:206` `screencap_png` | `adb exec-out screencap -p` |
| 设备信息（型号/系统/版本） | `adb.rs:546` `device_info` | `adb shell getprop ro.product.brand` 等 |
| 推送并启动控制端 | `adb.rs:573` `start_control_server` | `adb push scrcpy-server` → `adb forward tcp:PORT localabstract:scrcpy…` → `adb shell CLASSPATH=… app_process … scrcpy-server … control=true video=false` |
| 启动 scrcpy（画面） | `adb.rs:741` `launch_scrcpy` | 拉起 `scrcpy.exe` |
| 音频唤醒 | `adb.rs:824` `nudge_audio` | `adb shell input keyevent <code>` |

**注意最后一个细节**：本程序启动 scrcpy-server 时是 `video=false control=true` —— **视频根本不走 control 通道**。也就是说，本程序与 scrcpy 的耦合面，其实比"看起来"小得多：它只用了 **scrcpy-server 的输入注入半边** + **scrcpy 主程序的显示半边**。这直接决定了移植的难度分布。

## 2 HDC 侧的对应能力

HDC（HarmonyOS Device Connector）提供：`hdc list targets`、`hdc shell`、`hdc file send/recv`、`hdc fport/rport`（TCP 与 local socket 转发）、`hdc install`（装 HAP）。

设备侧（OpenHarmony 自带的 shell 工具）：

| 能力 | 工具 | 用法 |
| --- | --- | --- |
| 触摸 | `uinput -T` | `-d x y`（按下）、`-m x1 y1 x2 y2 [keep_ms] [smooth_ms]`（移动，**最多三条并行轨迹**）、`-u x y`（抬起）、`-c`（点按）、`-g`（拖拽） |
| 键盘 | `uinput -K` | `-d/-u/-l（长按）/-r（重复）/-t（文本）` |
| 鼠标 | `uinput -M` | 移动/按下/抬起/单击/双击/拖拽/滚轮，含左右中侧键 |
| 截图 | `uitest screenCap -p <path>` | 抓一张 PNG，再 `hdc file recv` 拉到电脑 |
| 截图（备选） | `snapshot_display` | 需在真机上确认输出行为 |
| 系统信息 | `hdc shell param get …` / `hidumper` | 取型号、系统版本、屏幕参数 |

## 3 逐项对照与差距

### 3.1 对照表

| 现状（ADB/scrcpy） | HDC 替代 | 判定 |
| --- | --- | --- |
| `adb devices` | `hdc list targets` | ✅ **已实现**（`harmonyos-pc/src/hdc.rs:31`，含单元测试） |
| `wm size` | `hdc shell hidumper` / `param get` / 或直接读截图像素尺寸 | ⚠️ **需实机确认**；最省事的做法是用截图的 PNG 尺寸反推（`harmonyos-pc/src/capture.rs` 已经在做等效的事） |
| `dumpsys window displays`（含旋转的坐标空间） | 无直接等价 | ⚠️ **需自研**：靠 `hidumper` 输出解析 + 跟随截图方向推断，逻辑与现在 `screen_mismatch` 那套（`app.rs`）类似但取数来源要换 |
| 刷新率 | `hidumper -s RenderService` 可能给出 | ⚠️ **可选功能**，取不到就退回"未知"（程序本来就把刷新率当参考值） |
| `screencap -p` | `uitest screenCap -p` + `hdc file recv` | ✅ **已实现**（`harmonyos-pc/src/capture.rs`，且有 2026-09-29 真机抓图）。**代价**：这是"抓一张、传一个文件"，比 `screencap` 慢 |
| **实时视频** | **无现成替代** | ❌ **最大缺口**，见 §3.2 |
| 控制通道（`INJECT_TOUCH`/`INJECT_KEYCODE`） | `hdc shell uinput -T/-K` | ✅ 功能等价，**性能不等价**，见 §3.3 |
| `UHID_CREATE/INPUT/DESTROY`（虚拟手柄右摇杆） | 无 | ❌ **不可用**（详见 §3.4） |
| 指针消隐 / 鼠标捕获 | **与手机无关**，是 Windows 侧的事（`capture.rs` 的 `cursor_hide`/`mouse_grab`） | ✅ **零改动** |

### 3.2 缺口一：实时画面（决定项目形态的那一个）

scrcpy 之所以能投屏，是因为它把 `scrcpy-server.jar` 推到手机上、用 `app_process` 跑起来，让 Android 的 `MediaCodec` + `SurfaceControl` 直接编码屏幕，H.264 数据经 socket 回传，电脑端解码显示。

HarmonyOS 上**没有**等价的"免安装"路径：

- `uitest screenCap` 是**截图**，一次一张 PNG（1~2 FPS 量级，`harmonyos-pc/README.md` 实测的自动抓取约 **2 FPS**）。拿来取点足够，拿来打游戏完全不够。
- 真正的实时投屏要用 HarmonyOS 的屏幕捕获能力（`AVScreenCapture` / 系统截屏服务），而这些能力**要求应用被签名并持有相应权限**，还通常要在设置里取得用户授权。也就是说：**必须有一个装在手机上的伴生应用**（HAP）。

本仓库里已经有这个伴生应用的雏形：`harmonyos/`（ArkTS）。它现在只做蓝牙键盘直连，但如果要移植实时画面，**它就是正确的落点** —— 把它扩成"捕获屏幕 → 编码 → 经 fport 回传"，就等于自实现 scrcpy-server 的视频半边。

**这意味着**：所谓"去掉 scrcpy，找替代或自实现类似功能"，在**画面**这一项上没有"找替代"这个选项，只有"自实现"，而且自实现的那一半比控制那一半重得多。

### 3.3 缺口二：多触点与注入延迟

**（a）多触点数量**：本程序的引擎按"设备端同时最多 **10** 个触点"设计（README 与 `app.rs` 的"引擎自检"都写了这个数字，触点池满了会拒绝按下并记账）。而 `uinput -T -m` **最多支持三条并行轨迹**。这不是"改个常数"的事：它会影响引擎的触点分配策略（哪些触点该共享、满了优先丢谁）与界面提示。**这是"算法逻辑不变"这句话唯一的例外。**

**（b）延迟**：这是最现实的问题。现在的链路是"**一个常驻 TCP socket，发 20 来个字节**"；HDC 链路是"**发一条命令 → 手机上起一个 `uinput` 进程 → 执行 → 返回**"。`harmonyos-pc` 现在就是每次注入都 `Command::new(hdc)…`（`hdc.rs:94` `run` → `backend.rs:44` `send`），一次输入 = 一次进程创建 + 一次 HDC 往返。

本来有个显而易见的优化——**开一个常驻的 `hdc shell` 交互会话，把命令写进它的 stdin**。但 `harmonyos-pc/README.md` 记录了实测结论：

> the tested HDC 3.2 build reports `Not support stdio TTY mode`, so redirecting an interactive shell's stdin cannot execute `uinput` commands reliably.

即**这条优化在当前 HDC 版本上走不通**。剩下的办法只有一条：**在手机上驻留一个自己的进程**（伴生 HAP 或推送一个 native 小程序，用 `hdc fport` 转发一个 socket），让它持有 `uinput`/`inputEventClient`，由电脑端持续喂命令。这又回到"要装东西"的结论。

**影响面**：
- **点按/长按/系统键/宏回放**：延迟变差但**可用**（人对 20~50ms 的单击不敏感）。
- **快速连点、划动、FPS 甩枪/跟枪、轮盘推拉**：**明显可感**。本程序上一轮刚刚为"输入延迟"做过专项排查（`文档/输入延迟排查报告-2026-10-05.md`），把计划动作的抖动从 11.5ms 收敛到 1.05ms——移植会把这部分工作**整体作废**。
- 这条必须在动手前想清楚：**移植后，"手感"会退回哪怕不是 0.1.x 也至少是"移植前 + 一个 HDC 往返"的水平。**

### 3.4 缺口三：虚拟手柄（UHID）与其它 scrcpy 特性

- **虚拟手柄右摇杆**（`UHID_CREATE/INPUT/DESTROY`，`control.rs:18`）：HarmonyOS 无对应接口。好消息是这一项在**本程序里已被标记废弃、不再维护**（README 与 `help.md` 都写了），移植时可以直接砍掉，界面保留选项或直接移除。**代价：0。**
- **系统键注入**：现在走 `INJECT_KEYCODE`（Android keycode）。HDC 侧要换成 `uinput -K <key>`，**键值表需要重新映射**（Android keycode ≠ HarmonyOS keycode）。这是一张**纯体力活的映射表**，工作量小但必须逐键真机核对。
- **剪贴板/音频等**：本程序没用到，不用管。

### 3.5 缺口四：分发与合规

- `hdc.exe` 随 **DevEco Studio** 分发。**能不能随本程序一起打包分发，需要确认许可条款**（现有 `harmonyos-pc` 的做法是要求用户自己装 DevEco 并通过环境变量或默认路径定位，这是稳妥的）。
- `uitest` / `uinput` 在**零售华为固件上可能不开放**（`harmonyos-pc/docs/architecture.md` 已明确提示，并提供 `doctor` 子命令去真机探测）。**这意味着移植版的可用性可能取决于机型和固件**——这是产品级风险，不是技术风险。

## 5 建议的做法：把"移植"降级成"加一个实现"

"整体移植"最贵的不是写代码，是**把已经调好的算法与界面重来一遍**（`harmonyos-pc` 的 `keymap.rs` 就是这重写的产物，1462 行 vs 主程序 2655 行——它不是主程序那份）。更划算的做法是**在传输层切一刀**：

```
现在：  app.rs / engine.rs ─────────► adb.rs + control.rs ──► scrcpy-server
                                                          └─► scrcpy.exe（画面）

改造：  app.rs / engine.rs ─────────► trait Transport
                                        ├── impl ScrcpyTransport（现状，零行为变化）
                                        └── impl HdcTransport（新增）
```

要抽出来的接口很小（对照 `control.rs` 的全部公开方法）：

```rust
trait Transport {
    fn touch_down(&self, id: u64, x: i32, y: i32);
    fn touch_move(&self, id: u64, x: i32, y: i32);
    fn touch_up(&self, id: u64, x: i32, y: i32);
    fn key(&self, down: bool, code: u32);
    fn list_devices(&self) -> Vec<String>;
    fn screen_size(&self) -> Result<(u32, u32)>;
    fn refresh_rate(&self) -> Option<f32>;
    fn screenshot_png(&self) -> Result<Vec<u8>>;
    fn device_info(&self) -> DeviceInfo;
    // 画面：由 Transport 之外的 DisplayBackend 负责（现在 = scrcpy.exe，将来 = 伴生 HAP 流）
}
```

**收益**：
- 抽的时候 scrcpy 一侧**行为完全不变**，可被现有 229 项测试与 `ci/clippy_diff.py` 守住；
- 抽完之后，"支持鸿蒙"变成**加一个实现**，而且可以**按能力逐块替换**（先只换截图，再只换注入），永远保持程序可用；
- 主程序的 `engine.rs` / `keymap.rs` / `app.rs` 一行不用重写 —— 这才真正兑现了"UI 与算法逻辑不变"。

## 8 建议

1. **先做 R1 的机型考察**（半天）。`uitest`/`uinput` 不开放，一切免谈。
2. **再做 P0 的传输层抽象**（4 人日）。它风险最低、收益最确定，且**无论最终是否移植都不会白做** —— 它让"支持第二个平台"从此变成"加一个实现"，而不是"重写一遍"。
3. **画面单独决策**。§3.2 已经说明画面没有"找替代"这条路。建议：**控制链路先上，画面用 `uitest screenCap` 顶着**（程序本来就只需要截图来做取点与浮层，对局画面可以仍由 scrcpy 或其它投屏工具提供）—— 这样能拿到一个**两周内可用**的鸿蒙版本，把"实时画面"的问题推后到有明确需求时再投入 P2。
4. **不要**用 `harmonyos-pc/src/keymap.rs` 那份重写版覆盖主程序 —— 主程序那份是这几轮打磨的结果（宏、按后延迟、组合键、轮盘抢占…）。两线共用同一份算法代码是唯一可持续的做法。

> 附：本文与 `harmonyos-pc/docs/architecture.md` 的关系 —— 那份文档描述的是**已经动手的独立产品线**；本文回答的是**"能不能把主程序整体搬过去"**。两份结论并不冲突：都指向"控制链路可行、画面是硬骨头、先抽象传输层"。
