# Windows / Linux 手感一致性 —— 讨论稿（2026-10-19）

> **性质：讨论稿，不是计划。** 这里只做两件事：把「手感」拆成能被讨论的东西，以及说清哪些差异是宿命、哪些是欠账、哪些对齐反而错。不谈排期、不谈人日、不谈先后顺序。

---

## 1. 「手感」到底由什么决定：拆成五段可测量的东西

「手感」是个笼统词，笼统就没法讨论一致性。把它拆成五段，每段都有可观测的量：

| 段 | 用户感知到的 | 可测量的量 | 谁的代码决定 |
|---|---|---|---|
| ① 捕获时延 | 按下到「程序知道」 | 事件从设备到引擎队列的毫秒数 | 平台捕获层（`src/capture.rs`） |
| ② 判定时延 | 「程序知道」到「决定做什么」 | 引擎轮询节拍 + 组合窗判定 | `src/engine.rs`（跨平台同一份） |
| ③ 执行时延 | 「决定」到「手机动」 | adb 注入队列的排队与发送 | `src/control.rs`（跨平台同一份） |
| ④ 光标行为 | 甩枪时准星跟不跟手、会不会跑出屏幕 | 光标位移与真实位移的一致度 | 平台独占层 + 回中逻辑 |
| ⑤ 状态可见性 | 用户知不知道「现在是什么状态」 | 状态行/日志在一眼之内可读 | 界面层 |

**关键观察：②③ 本来就是同一份代码。** 所以「平台手感差异」在结构上只可能来自 ①④⑤ 三段。讨论一致性时如果去动 ②③，等于人为制造差异——这是第一条要守的边界。

---

## 2. 逐段对照：三种性质完全不同的差异

### 2.1 ① 捕获时延：Windows 有个「10.2ms 网格」，Linux 没有（但也没量过）

- **Windows 的事实（已实测）**：不调 `timeBeginPeriod` 时，`recv_timeout(4ms)` 实测 **10.245ms**、`16ms` 实测 **20.479ms**（约 10.2ms 网格）；调了之后 4.253ms / 16.457ms（±0.25ms）。仓库用 `timer::raise()` 把这条抹平了（`src/timer.rs:18-37`、`src/main.rs:25` / `:132`）。
- **Linux 的事实**：`src/timer.rs:39-43` 是空实现，注释说「单调时钟 + futex 超时本身足够精确」。**但仓库里没有任何一次 Linux 侧的计时实测**。
- **性质判定**：这是**可对齐但未验证**。同一份 `recv_timeout` 写法在两边的实际回程差多少，现在无人知道。**在量出来之前，任何「Linux 更跟手」或「两边一样」的说法都是猜的。**
- **讨论点**：这条差异一旦量出来，可能发现 Windows 侧 `raise()` 是必要的（已知），而 Linux 侧还有进一步提升空间（把 `epoll_wait` 的 timeout 用上而不是 sleep）——但那属于性能域，不是一致性域。**一致性只要求「目标值一样」（4ms/16ms），不要求「实现路径一样」。**

### 2.2 ④ 光标行为：这是最大的、也是最不该被抹平的差异

两边的机制完全不在一个层面：

| | Windows | Linux |
|---|---|---|
| 机制 | 钳制（`ClipCursor` 1px 竖条）+ 每 **16ms** 把光标 `SetCursorPos` 拽回中心 + 过滤自己制造的回声（`src/capture.rs:259` / `:3091` / `:5239`） | `EVIOCGRAB` 后**合成器收不到指针事件**，光标就停在那儿不动（`src/capture.rs:2700`） |
| 本质 | **追**：先把光标关起来，再从被钳制的位移反推真实位移，还要防自己造的假事件 | **停**：设备事件改投给本进程，光标物理上不再被移动 |
| 真实位移的保真度 | 受 16ms 采样量化 + 回声过滤影响 | 理论上 1:1（内核直给） |
| 屏幕边界 | 会自动撞边（所以才要钳） | 不存在「边界」这个概念 |

**性质判定**：这是**结构性差异，不可对齐**。原因写在 B21 方案文档里：Windows 没有 `EVIOCGRAB` 的等价物，且用户态拦不住别的进程读 Raw Input（P1/P1b 已实测）。所以：

- 想让 Windows 像 Linux 一样「停」，唯一路径是内核驱动（已明确不做：20–40 人日 + EV 证书 + 反作弊风险）。
- 想让 Linux 像 Windows 一样「追」，是**主动降级**——把一份纯内核级的干净实现改成一堆事后补救，没有理由。

**讨论点**：既然不可对齐，一致性该落在哪？落在**「用户不必知道差别」**：两边都做到「瞄准时准星只跟手、不跑出屏幕、不会点到别的窗口」。Linux 天然满足，Windows 靠三层补丁满足。**验收口径必须是结果，不是机制。** 这一条已经体现在文案分层上（`WIN_GRAB_MODES_NOTE`，`src/app.rs:185`）——但那份文案是写给 Windows 用户看的，Linux 用户看到的应该是「本平台为设备级独占」，而不是同一段话删掉几句。

### 2.3 ④-补 光标**可见性**：这是 Linux 侧一个还没补的真实缺口

`src/capture.rs:1827` / `:1839` 两个函数（`set_cursor_visible_from_ui` / `hide_cursor_shape_from_ui`）在**非 Windows 上是空函数**。也就是说：**Linux 上进 FPS 模式，系统光标不会被隐藏。**

- Windows 侧做得很彻底：透明系统光标（`SetCursor(NULL)`）+ 每次重绘后重设，跨窗口全局生效。
- Linux 侧是**零实现**——不是「故意不一致」，是**欠账**。
- 用户感知：Windows 上瞄准时看不到箭头，Linux 上箭头一直在屏幕中间晃。**这是两边手感差里最刺眼的一条**，而且和「独占」没关系，纯粹是没写。
- **性质判定**：**可对齐**（语义上两边都该隐藏）。但实现路径不同：X11 用 `XFixesSetCursorByName("none")`，Wayland 得靠 `zwp_locked_pointer_v1.set_cursor_position_hint` 或合成器行为（未实测）。所以**语义先对齐，实现各写**。

### 2.4 ⑤ 状态可见性：Windows 有两个 Linux 没有的开关，Linux 有两个 Windows 没有的开关

| 开关 | Windows | Linux | 性质 |
|---|---|---|---|
| 「映射时屏蔽原键(grab)」 | 无（做不到） | 有（`src/app.rs:13554`） | 结构性 |
| 「已绑定键不再传给其它程序(独占模式)」 | 有，默认关（`:13561`） | 无（不需要） | 结构性 |
| 「钉住光标(避免甩枪撞边)」 | 有，默认开（`:16668`） | 无（不需要，已停） | 结构性 |
| 「鼠标独占」三档 + 遮板/隔膜二选 | 有（`src/theme.rs:406-416`） | 无（`src/mask/other.rs:1-12` `available()` 恒 false） | 结构性 |
| FPS 状态行（`clip_status_line`） | 有（`:16605`） | 无 | 结构性 |

**这里藏着一个真实风险**：这些开关都**存在 `settings.json` 里**，而配置文件是跨平台共用的。用户把 Windows 的 `settings.json` 拷到 Linux（或反过来），那些不适用的字段会**静默失效**——不会报错，但也不会起作用。如果界面上那个复选框也被 `cfg` 隐藏了，用户就永远看不到「你设的这个东西在这台机器上不存在」。

**讨论点**：一致性在这里的正确形态不是「把开关都做出来」，而是「**让不可用的东西可被看见**」。三种做法各有取舍：
- 隐藏（现状）：界面干净，但跨平台拷贝配置时沉默。
- 显示但置灰 + 一行说明（推荐讨论）：多一行字，换「不沉默」。
- 显示且可点、点了写日志（不推荐）：制造「我设了」的错觉。

顺带一条：`文档/善后计划-2026-10-18.md` 的 B-1（组合键不进吞键位图）**只在 Windows 有意义**，Linux 上根本不存在「漏吞」这回事。这类「按平台裁掉的任务」如果不在任务表里标明平台，下个会话会当成两平台共同的债去还。

### 2.5 ①-补 热插拔：两边**一样烂**，这不叫分叉，叫共同债

Linux 靠 `RESCAN_TICKS = 20 × HEARTBEAT_MS = 100` ⇒ 约 2 秒（`src/capture.rs:2376-2378`）；Windows 侧仓库里 `RegisterDeviceNotification` **零命中**，也是轮询。

**讨论点**：两边都是「插上键盘到能用最多等 2 秒」。这种差异不需要「一致性」这个概念——它需要的是一次共同修复。把它误判成「平台分叉」会导致在错误的地方做对齐（比如为了「跟 Windows 一样」而**故意**让 Linux 保持 2 秒）。

## 3. 三类差异的判决表

| 差异 | 例子 | 该不该对齐 | 对齐的方式 |
|---|---|---|---|
| **结构性**（OS 原语有无） | 独占机制、光标停/追、遮板有无 | **不对齐机制，只对齐结果** | 用「用户能感知到的结果」做验收；文案分别讲清折扣 |
| **实现缺口**（一边没写） | Linux 光标消隐、Linux 无计时实测 | **必须对齐** | 语义先定，实现各写；补实测数字 |
| **共同债**（两边都差） | 热插拔 2 秒、日志截断重写 | 不是一致性问题 | 别混进一致性议题 |
| **伪差异**（同一份代码） | 判定节拍、组合窗、宏步进、注入队列 | **禁止为它做任何平台分支** | 出现平台分支就是缺陷 |

**这张表最重要的一行是最后一行。** 项目里 `② 判定` 与 `③ 执行` 是同一份代码，`CHORD_FAST_MS = 45` / `CHORD_SLOW_MS = 120` / `IDLE_FAST_MS = 4` / `IDLE_SLOW_MS = 16` 这些数字都是两平台共用的。任何「Windows 上调 50ms、Linux 上调 40ms」的想法都是在**主动制造**用户换平台时的体感突变。

## 4. 一致性的四条原则（讨论用，不是条款）

**原则一：分层的边界就是一致性的边界。** 项目已经有一个好结构：`src/capture.rs` 把**决策**放在模块顶层的纯函数（`should_clip` / `clip_step` / `keyboard_swallows` / `rotate_target`），平台实现只负责**执行**（`ClipCursor` / `EVIOCGRAB` / 钩子）。=> 一致性的天然单位是「决策」，不是「实现」。凡是两边都该有同一套判断的，判断写进跨平台纯函数；只有这样它才**可被同一组单测锁住**。这条已经在 B21-3 上验证过有效。

**原则二：不一致必须「有话说」，不能「静默」。** 现在三种静默都存在：配置字段静默失效、`available()` 恒 false 导致入口消失、日志级别 `warn` 压掉验收日志（B21-C 那次的教训）。一致性不是「两边长得一样」，而是「在任何一边，用户都能知道这台机器上什么是真的」。

**原则三：验收口径必须选跨平台可测的量。** 「准星跟手」不可测；「FPS 模式 30 秒内光标位移净偏移 < N px」可测。「按键不抖」不可测；「连按 100 次，注入时间戳的 P99 延迟 < X ms」可测。**一致性不是把两边的机制改成一样，而是让两边的同一个数字落在同一个区间里。** 现在的问题是：Windows 侧的这些数字有一部分（10.2ms 网格、回中 16ms、45ms 组合窗），Linux 侧**一个都没有**。没有数字就没法谈一致性——只能说「看起来差不多」。

**原则四：不要把「跟 Windows 一致」当目标，要把「跟用户的预期一致」当目标。** Linux 用户对「独占」的预期来自 Linux 生态（evdev grab 是常规做法），Windows 用户对「独占」的预期来自……没有先例（Windows 从来给不了）。所以同一句「独占」在两平台**本来就该有不同的折扣说明**，而不是硬掰成一句话。反过来，`help.md` / README 里的「平台差异」如果写成「Linux 较弱/Windows 较弱」，那是错的——B21 之前的文案就犯过这个错（旧文写「仅 Linux 可用…Windows 无需该项」，G-a 才改掉）。正确写法是**讲机制，不讲优劣**。

## 5. 反过来：哪些「不一致」其实是 Linux 的正当优势

讨论一致性时容易滑向「两边一样才叫好」。但有四条差异是**应当保留**的，抹平它们等于故意降低 Linux 侧质量：

1. **独占是真的**：Windows 的「独占模式」只在 legacy 消息层生效，拦不住读 Raw Input 的程序（P1/P3 实测）。Linux 是内核级。→ **文案必须让 Windows 用户知道这一点**，而不是让 Linux 也跟着写得含糊。
2. **没有 300ms 钩子时限**：Windows 低级钩子有 `LowLevelHooksTimeout`（默认 300ms），超时事件静默丢弃、反复超时静默摘钩。Linux 读 fd，不存在这类故障。→ 不需要「对齐」一个不该存在的故障模式。
3. **没有「前台窗口」判定**：`foreground_pid()` 在 Linux 恒 `None`。这不是缺功能——`src/adb.rs:129` 自己点出过「游戏在前台但焦点被弹窗抢走」会让前台判据误判。Linux 侧根本不做这个判定，也就没有这个误判。
4. **时间戳是设备真值**：`input_event.time` 是内核设备时间戳，Windows 低级钩子只有 `GetTickCount` 级。这影响宏录制与组合窗的精度上限——**是上限差异，不是实现差异**。

## 6. 现在**回答不了**的问题（诚实清单）

下面这些问题本轮没有答案，而且不是「想得不深」，是**缺一次真机执行**：

| 问题 | 为什么现在答不了 |
|---|---|
| Linux 侧实际捕获时延是多少？比 Windows 快还是慢？ | 仓库零实测；`/dev/input` 在本机与 WSL 都不存在 |
| Linux 侧 4ms 节拍真的能跑到 4ms 吗？ | 同上；`timer.rs` 非 Windows 是空实现，从未量过 |
| Wayland 下 `EVIOCGRAB` 与合成器会不会互相干扰？ | 需要真实 GNOME/KDE/wlroots 会话 |
| Linux 侧光标隐藏该走哪条路（X11 `XFixes` / Wayland locked pointer）？ | 需要先确认会话类型与合成器实现 |
| 「钉住光标」这类 Windows 补丁在 Linux 上是不是根本不需要？ | 逻辑上是（grab 后光标不动），但**没有一次真机确认** |
| 用户从 Windows 换到 Linux 时，第一眼会撞上几处断裂？ | 至少三处已知：配置目录首次不存在（已修）、中文字体可能缺（已有兜底）、input 组权限（未测） |

**这六条是「一致性」讨论的地基。** 在地基没有之前，能做的只有两件事：把结构性差异讲清（原则二），把伪差异守住（原则一、四）。**其余等一次真机。**

---

## 7. 一句话收束

> **一致性不是「两边一样」，而是「同一个用户预期，在两台机器上都不落空」。** 机制层面 Windows 与 Linux 永远不一样（一个追、一个停），但用户层面的三个预期是共同的：瞄准时准星只跟手、按键不会被别的程序截走、状态随时看得见。对齐这三条，其余差异该讲清就讲清、该保留就保留。
