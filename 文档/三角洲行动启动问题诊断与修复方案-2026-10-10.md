## 2 与安卓模拟器的技术差（网页版对话结论的落地判断）

网页版那条回答的技术骨架是对的，但**每一项能不能落到本程序上，取决于我们站在链路的哪一层**。

| 模拟器手段 | 本程序能否等价 | 依据 / 原因 |
| --- | --- | --- |
| **引擎级适配**（改 UE 输入模块、缓存事件窗口，光标移出窗口仍响应） | ❌ **做不到** | 我们是 scrcpy-server 的 **control socket 注入 MotionEvent**（`control.rs:2` `TYPE_INJECT_TOUCH`、`:492-509`），碰不到游戏引擎。这是**原理性边界**，不是实现不力 |
| **相对位移 + 灵敏度系数** | ✅ **已有** | `sensitivity_x/y`（`keymap.rs:1559-1560`，默认 2.0）+ `move_speed`（`:1562-1563`，默认 1.0）；Raw Input 直接取设备相对位移（`capture.rs` W1-2） |
| **光标回中 / 隐藏光标** | ✅ **已有，且做得比模拟器细** | Raw Input 路径每 **16ms** 检查并在越界时回中（`capture.rs:2058 RAW_RECENTER_INTERVAL`、`:3498-3509`）；钩子路径用**坐标匹配的"预期回声"**识别自己造成的回中（`capture.rs:3350-3359`、`:3649-3658`），不是旧的 `skip_next` 布尔；透明系统光标 `SetSystemCursor`（`:3327`） |
| **平滑延迟 / 坐标插值**（把一次位移拆成多个 ACTION_MOVE） | ⚠ **部分缺失** | 我们有**空间上的拆分**（无边界跑步机换手，`engine.rs:1937-1962`），缺**时间上的拆分**；而且消息数受队列预算约束（`control.rs:66` 上限 256，超了反而丢） → DF-6 |
| **PointerId 正确管理** | ✅ **比模拟器更稳** | 固定号段、不动态分配：普通绑定 `<2000`、轮盘 `2000+j`（`engine.rs:74`）、瞄准 `3000`（`:76`）、宏 `7000+`（`:86`）、滚轮缩放 `40000/40001`（`:89-90`）。**真正的风险不是串号，是池满(10)与同号高频 UP/DOWN** |
| **回中"延迟 + 渐进"** | ⚠ **有延迟、无渐进** | 静止 `recenter_idle_ms`（默认 120ms，`keymap.rs:1724`）后才归中 —— 延迟这一半已经对了；但归中是**同帧 UP+DOWN**（`engine.rs:1883-1891`），不渐进 → DF-3 |
| **高帧率 / Vulkan 渲染优化** | ❌ **不适用** | 画面由 scrcpy 出。投屏帧率问题已于 `§4.10@1077` 三实验闭环定案为**游戏侧节拍**（三角洲 120 档实测 ≈119fps），不是本程序的问题 |

**结论**：模拟器的"丝滑"来自**引擎侧 + 驱动侧**；我们只有**注入侧**。所以能做的只有四件事：**坐标正确、触点拿得到、位移不在时间上被压扁、归中不制造假手势**。本方案全部围绕这四件事。

## 3 现状取证：本程序到底怎么把鼠标变成"转视角"

### 3.1 两条注入路径（互斥，取决于 `aim.boundary` 与 `aim.open_world`）

```
鼠标位移 (CaptureEvent::Motion, capture.rs 1ms 合并窗口)
   └─ engine.rs:3417 → :3441 aim_on_motion(reserved = 轮盘 + 普通绑定 + fps + 组合 + 宏)
        ├─ aim.open_world == true  →  open_world_on_motion   engine.rs:2118-2191   ← 老路径
        └─ aim.open_world == false
             └─ aim_flush  engine.rs:2071-2111
                  ├─ aim.boundary == true  →  aim_target 钳到屏幕内   :1791-1809   ← 默认
                  └─ aim.boundary == false →  aim_flush_unbounded 跑步机 :1973-2020
```

- **默认组合 = `open_world=false` + `boundary=true`**（`keymap.rs:145-147` `default_boundary() -> true`；`:1582-1583` `open_world` 默认 false）→ 走 `aim_target` 的**钳屏**分支，**没有换手机制**。
- `§4.14 任务2` 的跑步机只覆盖 **`open_world=false` 且 `boundary=false`** 这一格；另两格（默认格 + 开放世界格）**都没吃到那个修复**。

### 3.2 归中（三选一，不是叠加）

| 模式 | 触发 | 实现 |

### 4.4 重点展开：跑步机"零可用方向"空转（T3，新发现）

`aim_band_limits`（`engine.rs:1913-1923`）= **每方向取 min(回转半径, 锚点到该边的距离)**，并且 `.max(0.0)`：

```rust
band.min(axf).max(0.0)                          // 向左
band.min((m.w - 1.0 - axf).max(0.0))            // 向右
band.min(ayf).max(0.0)                          // 向上
band.min((m.h - 1.0 - ayf).max(0.0))            // 向下
```

锚点贴在（或被钳到）某条边上时，**该方向可用量 = 0**。此时 `plan_aim_treadmill`（`:1937-1962`）：

```rust
loop {
    let sx = rest_x.clamp(-left, right);   // left=right=0 → sx 恒为 0
    let sy = rest_y.clamp(-up, down);
    segs.push((sx, sy));
    rest_x -= sx;                          // 减 0,rest 永不减少
    rest_y -= sy;
    if (rest_x.abs() < 0.5 && rest_y.abs() < 0.5) || segs.len() >= max_hops.max(1) { break; }
}                                          // → 一路跑到 32 段
```

产出 **32 个完全相同的段**，而 `aim_flush_unbounded`（`:1997-2013`）在**每两个相邻段之间**发 `touch_up` + `touch_down`：

> **单次鼠标位移事件 → 最多 31 对 UP/DOWN**（62 条命令），而且**没有任何实际推进**。

三重后果：

1. **转不动**：该方向可用量为 0，物理上就是推不动（这一点文档认为"设计如此"）；
2. **污染队列**：每次鼠标事件 62 条命令，1kHz 鼠标 = 每秒 6 万条 → 立刻冲爆 `MOVE_BACKLOG_LIMIT=256` → **其它子系统（移动轮盘/宏）的 MOVE 被丢旧保新** → 症状 ③；
3. **余量被静默吞掉**：`:1959-1961` 把 `next` 再钳回可用矩形，零可用方向上等于把累计偏移归零 —— 注释（`:1958`）承认"32 段兜底截断时余量可能很大"，但处理方式是**丢掉**。

> ⚠ **这条与 §0.1 第 2 条建议直接相关**：我们建议 FPS 取消「限制在屏幕边界内」，就必然进入这条路径。**DF-1 与 DF-2 必须一起做**，否则换完参数会踩到新坑。

### 4.5 为什么"启动三角洲行动"这个时刻特别容易触发

把三条时间线叠起来：

```
T0  程序 adb 启动游戏
T1  手机转横屏 / 换分辨率 / 换刷新率        ← 坐标空间此刻起是"旧"的
T2  你用鼠标点游戏内 UI（登录、设置、开始）  ← 只有鼠标，没有按键 → 不触发空间重查
T3  进对局，你以为一切就绪
T4  第一次按 W（移动）                      ← 这一下仍用旧空间注入
T5  引擎发现"空闲≥3s 后第一个按键" → 异步重查空间（几十~几百毫秒）
T6  空间更新为 WxH，日志出现"触摸坐标空间已更新"
```

**T4 那一下就是"有时推不动/转不动"，T5→T6 之间的坐标切换就是"有时候跳一下"。** 而且它天然是**间歇性**的：只有"长时间没按键之后再按键"才会发生，正好对应你说的"有些时候"。

| W3 | **探针自愈一旦 `GiveUp` 就永久失效**。连续探针无回音 → 重装一次 → 仍无回音则 `probe_off = true`（`:2792`），此后 `:2802` 永不再发探针、不再因探针重装；残余的 `stall_hit` 只看"消息泵是否卡住 ≥3s"（`:444-446`），而**系统静默摘钩不会让消息泵卡住** → 键盘与鼠标钩子全部失灵直到重启（**同时**解释 ② 和 ③） | `capture.rs:2768, 2792, 2802, 2737-2805, 444-446` | 中 |

| W5 | 开镜/门控键的 DOWN 丢失 → `gate_down` 整个按键周期为假（`engine.rs:3508-3512` 每次从 `held` 整体重算）→ "按住右键却转不动" | `engine.rs:3508-3512, 1499-1504` | 低-中 |
| **W6** | **【现场证据】对账在 700ms 后"合成"KeyRelease，把长时间按住的鼠标键判成丢了抬起**。`last_seen` 只在按键事件时写、抬起清零，**不会自动重复刷新**，所以"鼠标键/Shift/Ctrl/Alt 按住 >700ms 且 `GetAsyncKeyState` 报未按下"就会向引擎补发一次**假抬起**。**本机日志：25 条全部是 `BTN_RIGHT`（18:23–18:41）** —— 说明这条路径在真实对局里**每按一次右键都可能触发**。你目前右键没绑任何键（`hold_key` 为空），所以对视角无直接影响；但**任何绑在鼠标键上的 Hold / 系统键 / 门控键都会被中途松掉** —— 若将来把开镜键设成 `hold_key`，就是"按住右键 0.7 秒后视角停转" | `capture.rs:2059-2073`、`:3004-3008`（`mark`）、`:3732-3784`；`diagnostics.log` 实测 25 条 `BTN_RIGHT` | **高（现场证据）** |

**观察手段的缺口**：`raw_state`、`WM_INPUT` 计数**都没有暴露到界面或日志**，只有两条跃迁日志（"已启用"／"退回光标差路径"）。所以 W1/W2 目前**无法靠现有诊断定位**，必须临时加计数或 trace —— 这正是 DF-9 的前半。

**与「Windows grab」文档的关系**：我已核对，`capture.rs` **全文件没有 `ClipCursor`、也没有 `RIDEV_NOLEGACY`**（grep 命中 **0**）。也就是说 `src/help.md:114` 写的"在 FPS 模式内隐藏并**锁定**光标"里，**"锁定"这一半并未实现** —— 现在只是"隐藏 + 漂出短边 1/4（≥96px）才拉回中心"。这与 `文档/Windows-grab可行性-2026-10-10.md` §6.1 的 G-2（用 `ClipCursor` 真正钉住光标）是同一件事，可作为独立小项排期。

## 5 修复方案

> 纪律：每条都按"现象 / 位置 / 改法 / 验收 / 风险"写全；落地时每项单独出一条单测，并走既有的四道门（`cargo fmt --check`、`cargo test --bin scrcpy-pad`、`python ci/clippy_diff.py`、WSL `cargo check --all-targets`）。
>
> 编号说明：**DF-1 ~ DF-7 是瞄准/引擎侧**；**DF-12 / DF-13 是本次现场证据新增的两条**（键位冲突、轮盘落指确认）；**DF-9 ~ DF-11 是 Windows 采集层**（见 §4.6，独立发现）；**DF-8 是验证工作、不是代码**，因此排在最后。

### DF-1　有边界路径"触边即换手"（治 ② 的主刀）

- **现象**：默认勾选「限制在屏幕边界内」时，触点推到屏幕边就停转，要等阈值累积或停手 120ms 才恢复。
- **位置**：`engine.rs:2071-2111`（`aim_flush`），`hit_edge` 已在 `:2093` 拿到、却在 `:2109` 被 `let _ =` 丢弃。
- **改法**：把 `hit_edge` 用起来 —— 落点被钳制（即触点已贴边）时**立即走一次换手**：`touch_up` 在边缘点 → 把"超出钳制范围的余量"作为新一段拖动从锚点继续（与无边界跑步机同一思想，但**边界是屏幕而非活动带**）。余量必须携带，否则会转向不足。
- **验收**：单测：锚点靠右、持续右推 → 注入序列为"move 到右边缘 → up → down 锚点 → move 余量"，且**所有段之和 == 期望偏移**；锚点贴边（可用余量 0）时也能持续转，不再有"停转窗口"。
- **风险**：中。换手瞬间对游戏是"抬指+重按"，与 DF-3 相关，建议同批落地。
- **说明**：**这不是重复提案 `§4.14` 的跑步机** —— 跑步机只覆盖 `boundary=false`，本项覆盖默认的 `boundary=true`。

### DF-2　跑步机零可用方向不再空转（治 T3 与 ③ 的连带污染）

- **位置**：`engine.rs:1937-1962`（`plan_aim_treadmill`）、`:1973-2020`（`aim_flush_unbounded`）。
- **改法**：
  1. `plan_aim_treadmill`：某次钳制**完全没有进展**（`sx`、`sy` 与上一次相同且 `rest` 未减少）时**立即 break**，段数 = 1；
  2. `aim_flush_unbounded`：单次调用**最多换手一次**；零进展时**不发 UP/DOWN**（只保留余量）；
  3. 零可用方向下**不要静默丢弃余量**：保留在 `st.ox/oy`（并加一个 `st.band_blocked` 标志供界面提示"该方向锚点贴边，无法继续转"），而不是钳回 0。
- **验收**：单测：`lim=(0,0,0,0)`、`push=(100,-50)` → 段数 == 1、UP/DOWN 对数 == 0；`lim=(0,400,400,400)`、`push=(100,0)` → 同上；连续调用 100 次不产生任何 UP/DOWN。
- **风险**：低（纯函数 + 已有两条回归测试在位，`engine.rs:7226` / `:7318`，可作基线）。

### DF-3　归中分帧：UP 与 DOWN 不同帧（治 ① 的 J1）

- **位置**：`engine.rs:1875-1894`（`aim_recenter`）、调用点 `:2103-2107` 与 `:2194-2210`。
- **改法**：`aim_recenter` 拆两步 —— 第 1 帧只 `touch_up` 并置 `st.recenter_pending = Some(now)`、`st.down = false`；第 ≥1 个引擎迭代后再 `touch_down` 锚点。中间期间 `aim_flush` 不发任何 move。用常量控制间隔帧数（0 = 现行为，便于回退）。
- **验收**：单测：调用一次 recenter → 只产生 UP；再调一次 flush → 产生 DOWN，位置 == 锚点；无边界路径行为不变。
- **风险**：中（归中会慢一帧；若游戏对"抬手"敏感，反而更干净）。

### DF-4　锚点最小活动带 + 界面显示四方向可用带（治 T3/T4 的诱因）

- **位置**：`engine.rs:1767-1773`（`aim_anchor`）；界面 `app.rs:11280-11318`。
- **改法**：`aim_anchor` 除钳进屏幕外，再保留一个最小活动带 `AIM_ANCHOR_MARGIN`（建议 `max(64, 回转半径/4)`，且不超过短边的 45%）；界面同时显示"锚点实际落点"与四个方向的可用带宽（px），贴边时红字提示。
- **验收**：单测：锚点 `(0,0)` / `(w-1,h-1)` 归一后四方向可用带 ≥ margin；界面自检出现四个数字。
- **风险**：中（会改变你显式设定的锚点）→ **必须把修正后的实锚点显示出来**，让用户看得见。

### DF-5　坐标空间：鼠标路径也参与重查 + 变更即收手（治 §4.5 的 T4/T6）

- **位置**：`engine.rs:3746-3758`（空闲判定只认按键）、`app.rs:10217-10233`（`sync_display_space`）。
- **改法**：
  1. 把"空闲计时"改为**任何输入**（鼠标位移也算），或在 FPS 模式下对鼠标位移也做一次 3 秒空闲重查；
  2. `sync_display_space` 检测到尺寸**变化**时，主动抬起全部触点（复用 `release_all` 那一套）并把 `AimState::anchor_used` 置为失效，避免"新空间 + 旧触点/旧锚点"混用；
  3. 进入 FPS 模式（`mode_active` 由 false → true）时**立即**重查一次空间。
- **验收**：真机/手工：竖屏开 FPS → 进游戏转横屏 → 第一次注入即为新空间；日志顺序为"触摸坐标空间已更新为 WxH"**先于**任何注入；不再出现"第一次 WASD 不生效"。
- **风险**：低。

### DF-6　单帧位移上限（可选，默认关；网页版"平滑"建议的注入侧替代物）

- **位置**：`engine.rs:2071-2111`（`aim_flush`）。
- **改法**：给 `aim_flush` 增加"单次最多推进 `max_step_px`（建议 = 回转半径 或 短边 15%）"，超出部分留在 `st.ox/oy`，由 `aim_tick` 在后续迭代继续推进。效果 = 把一次巨大的鼠标位移**摊到若干帧**，观感连续而不是一帧跳到底。
- **验收**：单测：注入 `(3000,0)`、`max_step=400` → 第一帧只发 400，余量保留，后续帧继续，**总量守恒**。
- **风险**：中（引入"最大转速"，快速甩枪可能变慢）→ 默认关闭或给足够大的默认值；**不要**照搬网页版的"50~120ms 平滑延迟"，那会明显增加跟手延迟。

### DF-7　FPS 一键预设 + 自检增强

- **位置**：`app.rs:11042` 起（鼠标瞄准页）。
- **改法**：新增「FPS 推荐参数」按钮：取消勾选「限制在屏幕边界内」、回转半径 200、拖动死区 0、归中 = 静止 + 60ms、锚点居中偏上（如 `(0.5, 0.42)`）、`hold_key` 清空；写 undo + 日志。自检区补"当前触点数 X/10"与"锚点四方向可用带"。
- **验收**：一键套用后长距离左右甩枪不再停住；keymap 层单测验证字段值。
- **风险**：低。（**前置依赖 DF-1/DF-2**，否则取消勾选会踩到空转。）

### DF-12　硬编码 `Ctrl+Alt` 与用户可绑定系统键的冲突（治 C1，**现场证据最高**）

- **现象**：玩着突然"视角不动了"，按键/开火正常，**必须再按一次才恢复**。
- **位置**：`engine.rs:3738-3744`（硬编码 `Ctrl(29)+Alt(56)` → 翻转 `aim.released`）、`:3532-3544`（`toggle_key` 上升沿翻转）、`:3571-3577`（`suspend_key` 按住挂起）。
- **改法**：
  1. **冲突校验**：保存配置/界面渲染时，若 `toggle_key` 或 `suspend_key` 含 `Ctrl` 或 `Alt`，给出**红字冲突提示**，并列出冲突对象（硬编码 `Ctrl+Alt`、以及任何以它们为前缀的组合键，如你的 `Ctrl+Z`）；
  2. **优先级明确**：冲突时**让用户显式绑定的键生效**，硬编码手势让位（或反过来，但必须写清楚并提示）；
  3. 更彻底：把"交还鼠标"也做成可配置项（默认仍是 `Ctrl+Alt`，保持向后兼容）。
- **验收**：单测：`toggle_key = Ctrl` 时 `ctrl_alt_chord` 不再翻转 `released`；界面出现冲突告警。老配置（未改绑）行为一字不变。
- **风险**：低。
- **备注**：**这一条不需要改代码也能自救** —— 把 toggle/suspend 改成 `F9`/`F10` 即可（见 §0.1 第 0 条）。

### DF-13　轮盘落指确认 + keepalive 补 DOWN（治 M5）

- **现象**："推了没反应，换个方向又好了。"（手指停在圆心）
- **位置**：`engine.rs:6492-6505`（`touch_down` 后乐观置 `down=true`）、`:6534-6574`（keepalive 只在 `down==false` 时重试）。
- **改法**：keepalive 在 `down == true` 但**从未观察到该落点生效**的情形下，也周期性补发一次 DOWN（幂等 + 限流）；或对"落指后 N ms 内没有后续有效 MOVE"重新走 `update_wheel` 的完整落指路径。
- **验收**：单测：`down=true` 但落指 DOWN 被拒 → keepalive 会重试 DOWN。
- **风险**：中（**重复 DOWN 确实可能搅乱 server 的指针池** —— `engine.rs:505-507` 的注释已经警告过，所以必须幂等且限流，不能无脑重发）。

### DF-9　Raw 通道看门狗 + `raw_state` 可见化（治 W1 / W2）

- **现象**："视角突然完全不动、按键与开火正常"，或"先卡 700ms、再猛跳一下"。
- **位置**：`capture.rs:2370-2372`（`raw_takes_motion`）、`:3796-3800`（兜底只认 `RAW_PENDING`）、`:3524-3531`（回退）、`:2438/2936`（另两处状态写入）。
- **改法**：
  1. **加看门狗**：进入 `RAW_RELATIVE` 后，若连续 ≥ `RAW_STALL_TIMEOUT_MS`（建议 500ms）收不到任何 `WM_INPUT`，把状态退回 `RAW_PENDING`，让钩子路径重新接管位移，并写一条 warn 日志；
  2. **回退时同步 `motion.last`**：任何"位移来源从 Raw 切回钩子"的路径，都必须先把 `motion.last` 设为当前光标位置并清 `echo`，避免 W2 的整段跳变；
  3. **可见化**：把 `raw_state` 与 `WM_INPUT` 计数暴露到"调试信息"或瞄准自检里（一行即可）。
- **验收**：单测：`RAW_RELATIVE` + 超时无事件 → 看门狗退回；回退函数断言 `motion.last == 当前光标`。手工：让 Raw 静默中断后，视角应在 0.5s 内自愈而不是永久死亡。
- **风险**：中（阈值太小会在低回报率设备上误退回 → 用 500ms 且只在"完全无 WM_INPUT"时触发）。

### DF-10　探针 `GiveUp` 后的降级与告警（治 W3）

- **位置**：`capture.rs:2768`、`:2792`、`:2802`；界面 `app.rs:10544-10583`。
- **改法**：`GiveUp` 时**不要静默**：① 上屏明确告警（"输入捕获自愈已被停用：本进程内不再自动重装钩子，若出现按键/视角失灵请重启程序"）；② 增加一条**不依赖探针回音**的兜底 —— 键盘/鼠标钩子长时间（如 5s）零事件、但 `GetAsyncKeyState` 显示有键按下时，允许再重装一次。
- **验收**：模拟摘钩（`SCRCPY_PAD_UNHOOK_AFTER_MS`）→ 连续两轮失败后界面出现告警；随后按键仍能被兜底救回。
- **风险**：低。

### DF-11　捕获层补"丢失的按下"（治 W4 / W5）

- **位置**：`capture.rs:3777-3784`（只补 UP）、`:3704-3773`（`reconcile`）；`engine.rs:6557-6561`（保活判据）。
- **改法**：
  1. 对账时**两个方向都补**：`GetAsyncKeyState` 显示**按下**而我们没有按下记录、且该键在最近 `DOWN_GRACE_MS`（如 200ms）内无事件 → **补一次 DOWN**（与"补 UP"对称；同样只在"我们对该键有过状态记录"的前提下做，避免误判）；
  2. `wheel_keepalive` 的重试判据从 `wheels[j].pressed` 改为"**物理键仍按着**"（`Held`），这样 DOWN 丢了保活仍能把摇杆推出去。
- **验收**：单测：构造"物理按着但无按下记录" → 补 DOWN 一次；保活在 `pressed=false` 但 `held=true` 时仍重试。
- **风险**：中（补 DOWN 要防闪烁重按 → 必须带时间宽限与幂等保护）。

## 8 风险与边界（诚实说明做不到的事）

1. **拦不住游戏自己的输入处理**：我们注入的是 `MotionEvent`（`control.rs:492-509`），游戏可以任意平滑/预测/丢弃我们的触摸。模拟器能改引擎，我们不能 —— 这是原理性差距。
2. **"完全消除跳变"不可承诺**：能承诺的是"消除我们自己造成的跳变"（重复计入已修、归中假手势 DF-3、零可用方向空转 DF-2、空间错位 DF-5）。
3. **触点池 10 是设备端硬上限**（`engine.rs:63`），不是我们能放宽的；只能优化优先级与提示。WASD+开火+开镜+瞄准+宏同时按很容易到顶。
4. **`S-9` 组合键 45/120ms 门控**与 **`S-12` 瞄准纯线性**属于既有未修项（V2-4 / V2-3），本方案不动。
5. **投屏帧率**不是本程序的问题（`§4.10@1077` 已定案），但会在观感上与"跳变"混淆，判断时请以自检数字为准。
6. **"锁定光标"并未实现**：`src/help.md:114` 声称 FPS 模式内"隐藏并**锁定**光标"，实际只有"隐藏 + 漂出短边 1/4（≥96px）才拉回中心"；`capture.rs` 全文件无 `ClipCursor`（grep 命中 0）。因此"甩到屏幕边就丢位移"在用户态只能**缓解**、不能**杜绝**（原理性边界见 `Windows-grab可行性-2026-10-10.md` §3.6）。
7. **`recenter_threshold` 一个字段两种语义**：既是"阈值归中的阈值"，又是"无边界的回转半径"（`keymap.rs:1569`；界面两个入口 `app.rs:11338` / `:11451`）。切换边界模式或归中策略时这个数字会**跨语义沿用**，调参极易混淆 —— 建议在 DF-7 里顺手拆成两个字段，或在界面上明确标注"共用"。
8. **`help.md:234` 说"触摸板不能用于瞄准"**，但 `capture.rs:2308-2310` 明确绝对坐标设备会退回"光标差"路径、照常出位移。文字与实现不一致，需按实测修正。
