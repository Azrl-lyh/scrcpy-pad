# 主题重开后键盘/鼠标映射完全失效：根因与修复

- 记录时间：2026-10-03（Asia/Shanghai）
- 范围：Android 主程序 Windows 输入捕获、主题切换重启链路、发布构建
- 未修改：HarmonyOS 两条产品线

## 症状

- 主题切换后，键盘和鼠标映射完全无法控制手机。
- scrcpy 控制通道能正常建立，但按键事件似乎没有进入引擎。
- 诊断日志显示 Windows 键盘/鼠标低级钩子确实安装成功。

## 根因

主题切换采用同一进程内的 eframe 重启循环：

```text
request_style_restart -> ViewportCommand::Close
-> run_native 返回 -> main 循环再次 run_native -> 再次 Capture::start
```

Windows 捕获层原先使用：

```rust
static SHARED: OnceLock<WinShared> = OnceLock::new();
```

`WinShared` 里包含 `raw_tx: Sender<RawEvent>`。第二次 `Capture::start` 时：

- `OnceLock::set` 失败，因为静态状态已经初始化；
- 新钩子安装成功，但仍然使用第一次启动的 `raw_tx`；
- 第一次启动的接收线程已经退出，通道断开；
- 所有新键鼠事件被送入死队列并静默丢弃；
- 结果就是：钩子显示已安装，但映射完全失效。

## 修复

- 将 Windows 钩子共享状态从 `OnceLock<WinShared>` 改为可替换的：

```rust
static SHARED_PTR: AtomicPtr<WinShared>
```

- 每次 `Capture::start` 都创建新的 `WinShared` 并原子换入；
- 旧 `WinShared` 故意保留到进程结束，避免退出中的旧钩子线程发生悬垂访问；
- 新增 `install_shared()` 统一完成状态安装，避免启动路径再次分叉；
- 新增回归测试 `restart_replaces_windows_hook_shared_transport`：连续安装两套共享状态，验证第二次的 `raw_tx` 确实能把事件送进第二套接收端；
- 保留上一批修复：退出时有界等待 hook 线程执行 `UnhookWindowsHookEx`，`run_native` 返回后兜底恢复系统光标方案。

## 与触摸板副作用的关系

- 代码没有写入 `AAPThreshold`、触摸板驱动设置、注册表或鼠标加速参数。
- `AAPThreshold` 是系统/触摸板层设置，`scrcpy-pad` 没有相关 API 调用。
- 程序仅涉及两处全局 Windows 状态：
  1. 低级键鼠钩子；
  2. FPS 指针消隐时的临时系统光标方案。
- 钩子退出清理和光标恢复已加强；正常关闭主窗口后进程会立即退出。
- 如果旧版本曾异常强杀，仍建议彻底结束旧的 `scrcpy-pad.exe` 进程；必要时重启一次 Windows 清理残留输入状态。
