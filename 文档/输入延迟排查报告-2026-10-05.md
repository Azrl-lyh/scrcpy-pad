## 1. 摘要（结论先行）

1. **客户端输入链本身是微秒级的**：钩子入口→socket 写完 全链路 p50 ≈ 0.13ms、p99 ≈ 0.18ms（真机冒烟，n=42/版本）；两版量级相同。**没有发现"很多"新增延迟**——正式矩阵（§5，40 个校验通过的块 + 噪声底线判定）确认：唯一稳定分离的版本差是引擎自身分发 t4-t2 = 11.5 vs 9.1µs（**+2.4µs，本分支新增功能的分发成本**）；端到端 +2.2µs / 按下→写完 +4.5µs 均在块间噪声内。
2. **宏与组合键"配置了但未启用/未触发"时确实存在每事件开销，但量级为 ns**：真实配置实测 ≈51ns/事件（其中 82% 是轮盘方向匹配的堆分配）；配 2 条切换键再加 ≈39ns/事件。折算 600 事件/秒 ≈ 30µs/秒，**不足以造成可感知延迟**（见 §4）。原静态审计怀疑的"公共消息时间被大量占用"不成立；但其中确有两处**确定性浪费**已修复（§6 第 2/3 项）。矩阵复测（§5）：宏配置未触发 **0 影响**（S4）；组合键开启后非成员键 **0 代价**（S5-D2）；成员键的延迟是功能设计代价本身——按下→首命令被扣留到抬起或 45ms deadline（实测 8.00ms@p50，封顶 45ms，S5-D1），非公共开销。
3. **找到了一个此前完全没被注意的真问题（H14，已确证、已修复、已复测）**：未调用 `timeBeginPeriod` 时，Windows 把 `mpsc::recv_timeout`/`park_timeout` 的超时**量化到 ~10.2ms 网格**——引擎快档 4ms 实测变 10.245ms（与真机心跳 97 iters/s 逐位吻合）。这不影响按键事件的响应（事件到达即唤醒），但**所有"计划动作"的执行时刻**（点按定时抬起、Hold 连发、Swipe 步进、宏的每一步、组合键判定窗口）都带 ±6~10ms 误差，空闲轮询也从 250 次/秒掉到 97 次/秒。修复后 4ms 档回到 4.25ms、空闲 222 次/秒（2.29×）；45ms deadline 实测 p50 **55.58→45.71ms**、最坏 59.32→46.23ms、抖动 11.51→1.05ms（§8）。这是"宏/组合键感觉不准、不跟手"的头号元凶，且**新旧版本同时受害**。
4. 其余已实施的修复：轮盘每事件堆分配归零（`ActiveDirs`）、切换键扫描分配归零（`EffectiveKeys`）、输入链四类线程优先级提升（满载机器下的调度抖动）、等待扫描 `Instant::now()` 去重。全部零行为变化、可独立回滚（§6）。
5. GUI 持锁争用（宏页每帧深克隆）经 S7 实测**不构成可感知问题**（§5.8）：宏页常开 vs 默认页 p50 完全一致，最坏单次 <0.6ms（一帧 16.7ms），无 ≥300µs 的 gui 持锁堆积——静态审计中该项的优先级据此下调，不再列为修复项（原因与量级见 §6 备注）。

## 3. 静态审计结论

（详见方案文档 §2；此处只列结论）

| 环节 | 结论 |
|---|---|
| 钩子线程 | ✅ 独立线程+消息循环+极简回调（`Instant::now` + 2 原子 + 无界 send），绝不阻塞 |
| 消费线程 | ✅ `recv_timeout(50ms)` 事件即醒；每事件 +1 次 `GetForegroundWindow`（~百 ns 级） |
| 控制写线程 | ✅ 专线程阻塞 `rx.recv()`；`TCP_NODELAY`；每条消息一次 `write_all` |
| 引擎每事件 | ⚠️ 6+ 处独立加锁 + 每事件重算结构签名；实测均为 ns~百 ns 级（§4），未构成瓶颈 |
| GUI 持锁 | ⚠️ 宏页展开行每帧 2 次深克隆 + 1 次深比较；以用户当前配置量化为 µs 级/帧，S7 实测最坏 <0.6ms、无 ms 级尖峰（§5.8） |
| `space_recheck` | ✅ 已证伪：只置一个 bool，adb 查询在新 spawn 的后台线程 |
| 诊断日志 | ✅ 全局 Mutex + BufWriter + 独立刷盘线程，热路径无逐事件日志 |
| 宏/组合键未启用 | ✅ 静态核对无阻塞、无 sleep；逐事件成本见 §4 微基准 |

**新旧版本功能差异（影响 A/B 归因）**：本分支新增和弦门控（45/120ms 判定窗口）、宏（`Action::Macro` + 调度）、轮盘类型（Custom/Execute + `directions`）、快切开关（`fast_switch_enabled`）；旧版已有：Aim/FPS、切换键、标准轮盘、Tap/Hold/Swipe/AndroidKey。

## 5. 真机端到端矩阵（已定稿）

数据源：`scrcpy-pad-bench\results\10-matrix\matrix-report.md`（702 行）；场景 S1 未绑定键 / S2 绑定键版本对比 / S3 摇杆（W→驱动 1 号标准轮盘 up）/ S4 宏配置未触发 / S5 组合键开 vs 关（成员键/非成员键）/ S7 GUI 宏页常开 / S8 持续负载。时间单位除注明外为 **ms**。

### 5.4 S1 未绑定键（F7/evdev 65）

t2-t0 25.4 vs 24.4µs、t4-t2 **6.0 vs 3.5µs**、t4-t0 31.0 vs 28.0µs；两侧 cmd_writer 均 **0 行**。绑定键的 t4-t2(11.5/9.1µs) 明显高于未绑定键(6.0/3.5µs) → 绑定查表+构造动作本身约 3~8µs；版本差同样只有 ~2.5µs、方向上与 S2 一致。

### 5.5 S3 摇杆（W 驱动 1 号标准轮盘 up）

按下→首命令 46.5 vs 42.5µs（cur/old），t4-t0 55.3 vs 50.1µs——**无回归**（差 4~5µs 在噪声量级）。按下→socket 写完 p50 ≈ **0.17~0.19ms**、p99 ≈ 1.1~1.2ms。口径注意：旧版每事件写 4 条命令、当前版 2 条（cmd 行 264 vs 128），cmd-writer **全体行**的 t6-t4 不可直接比；按"每事件第一条命令"比两版一致（0.119~0.133ms）。

### 5.6 S4 宏"配置了但未触发"（P-user 含 `!Macro` vs P-nomacro）

t4-t0 35.5 vs 36.3µs、t6-t4 86.0 vs 83.5µs、按下→首命令 30.4 vs 31.2µs——**全部在噪声内，零影响**。key 45 上的 `!Macro` 只要不被按下就不参与分发。

### 5.7 S5 组合键开 vs 关

- **D1 成员键（H 是组合 [113,35] 的成员，combos_enabled=true）**：按下事件本身分发很快（press 行 t4-t0 p50 29µs，甚至低于无组合时），但真正的控制命令要等门控重放——**按下 → 第一条命令进入发送路径 = 8.00ms (p50) / 8.51ms (p99) / 21.0ms (max)**；同一颗键在 P-nomacro 仅 31µs → **代价 +7.97ms**。机制：`ComboGate` 把成员键当 leader 缓冲，直到 (a) 组合补齐、(b) 该键抬起、(c) `CHORD_FAST_MS=45ms` deadline 才 `flush_leader()` 重放；本次注入 hold-ms=8 → 抬起即重放。**按住超过 45ms 则代价封顶 45ms。** 该 8ms 在 cmd-writer 的 t5-t4/t6-t4 里完全看不到（95.7 vs 83.5µs，只差 12µs）——只看写线程会漏判，必须按"事件 t0 → 命令 t4_in"配对。
- **D2 非成员键（O/evdev 24）**：按下→首命令 30.6 vs 33.2µs，t4-t0 35.3 vs 39.0µs——**零代价**（组合键功能开启本身不给非成员键增加任何延迟）。

### 5.8 S7 GUI 宏页常开 vs 默认页

t4-t0 p50 36.3 vs 36.5µs、t6-t4 85.1 vs 86.8µs——中位数完全一致；p99 一致地高 +10.8µs（67.7 vs 56.9µs，3/3 块分离）；单块出现 1 次 0.59ms 毛刺（默认页 max 0.14ms）。gui `frame` 两侧均只有 1 行、16.5~17.5ms，**无 ≥300µs 的 gui 持锁或 ≥50µs 的引擎持锁堆积**。结论：150 键 + 宏页常开下最坏单次 <0.6ms，远低于一帧（16.7ms）——静态审计怀疑的"宏页持锁争用"在本配置下不构成可感知尖峰。

### 5.9 S8 持续负载（H，600 次 @4ms）

命令 1200 条（600 按下 + 600 抬起）、事件 1202 条，**计数完整、无队列堆积**；按秒分桶 t5-t4 p50 稳定 ~10µs、t6-t5 ~45µs、事件 t4-t0 ~28.5µs，3 秒窗口无上升趋势；整体反而比 20ms 间隔场景更快（t6-t4 p50 57.8 vs 86.5µs）。注：`--interval-ms 4 < --hold-ms 8` 产生重叠重按（down,down,up），引擎对重复 down 不重发命令，该块"按下→首命令"仅 9/601 可配对，已在原报告注明。

### 5.10 本层结论

**客户端链没有"很多"新增延迟**：可归属版本的功能性增量只有引擎分发 +2.4µs（新增功能的分发成本）；事件驱动路径无回归；宏未触发零开销；组合键成员键的延迟是**功能设计本身的代价**（按住时长，上限 45ms），非成员键零代价；GUI 无 ms 级争用。**真正跨版本、可优化的延迟来源是 H14 定时器量化（§7），它不体现在本矩阵的事件驱动数字里，但其影响面是全部计划动作（本节 S5-D1 的 45ms 封顶值本身就在受它影响的路径上）。**

## 7. H14 实验：等待原语被量化到 ~10.2ms 网格（已定稿）

工具：`scrcpy-pad-bench\tools\sleepbench`（独立小基准；每组 300 次）。

| 等待原语 | 未调 `timeBeginPeriod` | 调 `timeBeginPeriod(1)` 后 |
|---|---|---|
| `mpsc::recv_timeout(4ms)`（引擎快档） | **10.245ms**（p10 9.96 / p90 10.57） | **4.253ms** |
| `mpsc::recv_timeout(16ms)`（慢档） | 20.479ms | 16.457ms |
| `thread::park_timeout(4ms)` | 10.295ms | 4.119ms |
| `thread::sleep(4ms)` | 4.112ms（本来就准，走另一条路径） | 4.135ms |

- 与真机心跳对照：`iters_per_sec` 空闲稳态实测 96~98/s（**当前版与旧版完全一致**），1/10.245ms=97.6 —— 逐位吻合；
- 机制：`recv_timeout` → `park_timeout` → WaitOnAddress 相对超时被向上取整到 ~10.2ms 网格；
- **影响面**：按键事件本身（事件到达即唤醒）不受影响；受影响的是所有"定时/轮询"动作——点按定时抬起、Hold 连发、Swipe 步进、宏每一步、组合键判定窗口、瞄准维护节拍。修复后计划动作派遣误差 ~±6-10ms → ~±0.25-1ms；
- 备注：`timeBeginPeriod` 在 Windows 10 2004+ 为进程级效果；进程退出自动清除，仍显式配套 `timeEndPeriod`。

## 9. 对用户问题的直接回答

**① 当前版本是否比旧版增加了按键延迟？增加在哪？**
**没有可感知的增加。** 正式矩阵（40 个有效块 + 噪声底线判定）给出的全部差异：钩子→引擎 0.4µs 以内、钩子→分发完 +2.2µs、按下→socket 写完 +4.5µs（均小于噪声底线 2.6/13.7µs）、**唯一稳定分离的是引擎自身分发 t4-t2 = 11.5 vs 9.1µs（+2.4µs）**。该 2.4µs 是本分支新增功能（和弦门控检查、轮盘类型匹配、结构指纹）的分发成本，绝对量 <3µs，处于客户端链 p50 ≈0.13ms 的 2% 以内；摇杆路径同样无回归（+4~5µs 在噪声内）。**旧版与新版的差距不在代码效率上，而在两版共同受害的 H14 定时器量化上（§7）。**

**② 宏和组合键"不启用"时，有没有占用公共的消息时间、浪费无用功？**
**有确定性浪费，但量级是 ns，不是可感知延迟；矩阵证实未启用时零可测影响。** 逐事件开销实测 ≈51ns（其中 82% 是轮盘方向匹配的堆分配），配 2 条切换键再加 ≈39ns/事件；600 事件/秒折算 ≈30µs/秒。矩阵：宏配置未触发 0 影响（S4：t4-t0 35.5 vs 36.3µs）、组合键开启后非成员键 0 代价（S5-D2：30.6 vs 33.2µs）。**"浪费了很多无用功"不成立**——但其中两处堆分配（`active_dirs`、`effective_keys`）确实是纯浪费，已归零修复（§6）。组合键的成员键延迟（按下被扣留 8ms~45ms 上限）是**门控功能本身的设计代价**，只对组合成员键生效，不是公共开销。

**③ 摇杆路径（旧版 vs 当前版）？**
无回归：W 驱动轮盘 up 的"按下→首命令" 46.5 vs 42.5µs、t4-t0 55.3 vs 50.1µs（噪声量级内）；按下→socket 写完 p50 ≈0.17~0.19ms、p99 ≈1.1~1.2ms。轮盘方向匹配的每事件堆分配已归零（§6 第 2 项）。

**④ 修复收益（H14 为主，已复测验证）？**
- **空闲唤醒 97→222 iters/s（2.29×）**：每迭代 10.31ms→4.50ms，10.2ms 量化网格消除；
- **计划动作派遣误差**（组合键 45ms deadline 实测）：p50 **55.58→45.71ms（−9.87ms）**、最坏 59.32→46.23ms、抖动（极差）**11.51→1.05ms**——同样量级的改善适用于所有计划动作（定时抬起、Hold 连发、Swipe 步进、宏步进、组合判定窗）；
- **per-event 热路径无回归**（S2/S7 同矩阵抽测，唯一达阈值的差异是"按下→首命令"**快 3~5µs**）；`cargo test` 107/0 通过；真机冒烟（Tap/Hold/轮盘/组合/宏/开关）全过；
- 另有零分配两处（轮盘方向/切换键扫描）与线程优先级、等待扫描去重共 4 项"顺带"修复，均为确定性与满载鲁棒性收益（量级 ns~µs）。
- **建议**：release 包（`release\` 目录）尚未包含本次修复，需要时可用 `release\build.ps1 -Target all` 重打（先确认无 `scrcpy-pad` 进程在运行）。
