## 0. 任务与验收标准

1. **对比新旧二进制**：按键、摇杆（轮盘）操作在旧版（0.1.4 / 0.1.3）与当前版的端到端执行速度，判定当前版是否新增延迟、新增在哪一段链路。
2. **重点量化**：宏、组合键在未配置 / 配置未启用 / 启用但空闲 三种状态下，是否消耗公共消息时间。
3. **精细**：静态估计必须用动态实测数字证实或证伪；结论要落到 `文件:行`。
4. **产出**：本文档（方案）+ 测量数据 + 修复 + 最终详实报告（见 §7 交付物）。

判定采用三态：**确认回归**（p50 或 p99 差异超过噪声底线）、**无显著差异**、**待定（数据不足）**。噪声底线由 A/A 对照（同版本自比）标定。

### 0.1 目标修订（2026-10-05，用户指示）

> “就算没找出宏、组合键的延迟，原本的代码也很可疑，你干脆把降低按键延迟为目的得了。”

## 2. 已完成的静态审计结论（两名 agent，只读）

### 2.1 组合键 / 快速切换（对照 136d736，无此功能）

引擎热路径新增（均在 `src/engine.rs`）：

| 项 | 位置 | 代价 |
|---|---|---|
| 每迭代 1 次 `lock_shared` + `combo_gate.poll` | 2052-2055 | +1 Mutex/迭代（映射开 ≈250 次/s，关 ≈62 次/s）；disabled 分支内部为 O(1) 字段写，无分配、无时钟调用 |
| 每 Button 事件 +1 次 `lock_shared` + `ingest_button` | 2064-2071 | +1 Mutex/事件（按下与抬起都走） |
| `switch_keys.iter().any(\|s\| s.effective_keys()...)` | 191-193 | **每事件 K 次 `Vec<u16>` 堆分配**（K=切换键条数），且发生在 `combos_enabled` 早退之前，未启用也照跑 |
| `fast_switch_enabled=true` 时同事件第二轮 `effective_keys()` | 2509-2519 | 再 +K 次分配/事件 |
| `gui_tx.send` 改为按下+抬起都发 | 2063（旧 1176 仅按下） | channel 消息量约 ×2（为宏录制服务，非组合键） |
| 快切开关关闭时切换键块 | 2504-2521 | 1 锁 + 1 bool，无分配（比旧版更省） |

`ComboGate` 空闲稳态（无 leader、队列空）：无堆分配、无哈希、无 `Instant::now()`；成本几乎全在 Mutex。

### 2.2 宏（对照 136d736，无宏）

- **引擎热路径（映射开、无宏触发）宏开销 ≈ 0**：
  - `macro_events` 在 `if !due.is_empty()` 内声明（1745），空时不分配；
  - `macro_active_android_keys` 空 HashSet 零分配（1689）；
  - `Action::Macro` 分支不可达（3405-3411）；普通绑定路径与旧版逐字一致；
  - 宏 payload 仅在 `schedule_macro` 触发时访问，`virtual_profile` 用 `as_deref()` 借用不克隆（3427）。
- **可感知浪费集中在 GUI 宏页（每帧、与是否触发无关）**：
  1. `app.rs:5957-5967`：每条"嵌套宏"设置项**每帧在持 shared 锁内克隆配置里全部宏**（含 `Box<Profile>`）——最可疑；
  2. `app.rs:5293-5327`：展开的宏行每帧 3 次 `MacroAction` 深克隆 + 1 次全量 `PartialEq`（写回在锁内）；
  3. `app.rs:5120 / 5187-5198 / 5236-5249`：宏页每帧深克隆虚拟层、全 steps 建 HashSet、持锁遍历全部 binds。
- 次要：`app.rs:3845-3855` 键位列表每 bind 每帧 +1 锁；`engine.rs:2045-2050` 等待扫描对 `scheduled` **每元素一次 `Instant::now()`**（长宏数百条时放大）；映射关闭时每迭代 `cancel_macro_scheduled`（2021-2034，空转 +1 锁）。
- 行为风险（非性能，待动态确认）：宏重放键重新进 `combo_gate.queue`（1902-1904），无来源标记，理论上可自我重触发使 `scheduled` 无界增长。

### 2.3 审计共同结论

- 引擎侧新增开销均为**常量级（µs 以下/事件）**，静态上不足以单独解释明显体感延迟；
- 唯一能产生 **ms 级尖峰**的候选是 GUI 持锁深克隆（宏页/键位页/可视化页）与引擎抢同一把 `shared` 锁；
- 捕获层（钩子 → 消费线程 → channel）是否有回归，静态未发现，需动态测量。

### 2.4 原始代码人工复核（按“全面降低延迟”目标重查）

对原始代码链路逐段复核，**Windows 关键路径上没有发现轮询/睡眠**，但有两处与版本无关的设计问题：

| 链路环节 | 复核结论 | 位置 |
|---|---|---|
| 钩子线程 | ✅ 独立线程 + 消息循环 + 极简回调（`Instant::now` + 2 原子 + 无界 send），绝不阻塞，钩子交付不经 GUI 帧 | `capture.rs:1396-1495` |
| 消费线程 | ✅ `recv_timeout(50ms)` 事件即醒；每事件仅多 1 次 `GetForegroundWindow` 与 2 个原子读 | `capture.rs:1705-1798` |
| 控制写线程 | ✅ 专线程阻塞 `rx.recv()`，事件即醒；`TCP_NODELAY` 已设（无 Nagle 延迟）；每条消息一次 `write_all` | `control.rs:91, 107-133` |
| socket→设备 | t6→设备响应在扫描端不可测，视为常数项（版本间同一设备、同一 adb） | — |
| **引擎每事件** | ⚠️ 每 Button 事件仍有 6+ 处独立加锁（2065/2173/2215/2257?/2505/2546），且**每事件重算 `binds_signature`/`wheel_signature`**（2634，O(键位数)）——可合并/可脏标记 | `engine.rs` |
| **GUI 持锁** | ⚠️ 原设计即存在：`stash_active` 每帧在锁内做**整份 Profile 深比较**（1468-1475）+ 各页每帧持锁克隆/扫描（宏页 5957/5293 最重）——GUI 卡顿/复杂宏时直接顶住引擎加锁 | `engine.rs`, `app.rs` |

结论：**引擎每事件多锁 + GUI 持锁争用**是"原始代码也可疑"的最实锤两处，纳入本轮优化主线（需探针数据量化占比）。

### 2.5 H9/H14 已证实：等待原语被量化到 ~10.2ms 网格（独立实验，2026-10-05）

工具：`D:\GitHub\scrcpy-pad-bench\tools\sleepbench`（独立小基准，`recv_timeout`/`park_timeout`/`sleep` × 有无 `timeBeginPeriod(1)`，各 300 次）。

| 等待原语 | 未调 timeBeginPeriod | 调 `timeBeginPeriod(1)` 后 |
|---|---|---|
| `mpsc::recv_timeout(4ms)`（引擎快档） | **10.245ms**（p10 9.96 / p90 10.57 / max 13.3） | **4.253ms**（p90 5.01） |
| `mpsc::recv_timeout(16ms)`（慢档） | 20.479ms | 16.457ms |
| `thread::park_timeout(4ms)` | 10.295ms | 4.119ms |
| `thread::sleep(4ms)` | 4.112ms（本来就准：走可等待定时器另一路径） | 4.135ms |

- 与真机 heartbeat 对照：实测 `iters_per_sec` ≈ **76→97/s**（当前版与旧版 7769923 **完全一致**）——即 1/10.245ms=97.6，**逐位吻合**，H14 确证；两版同等受害，属"原始设计"问题而非本分支回归。
- 机制：`recv_timeout`→`park_timeout`→WaitOnAddress 的相对超时被向上取整到 **~10.2ms 网格**（4→10.2、16→20.4）；`thread::sleep` 走高精度路径不受影响。
- **影响面**：只影响"定时/轮询"类动作——`scheduled` 计划动作（点按定时抬起、Hold 连发、Swipe 步进、宏每步、组合键 leader 超时 45/120ms 的判定、Aim 维护节拍）。按键事件本身由 `send` 信号即醒，不经此延迟。修复后（`timeBeginPeriod(1)`）计划动作派遣误差 ~±6-10ms → ~±0.25-1ms。
- 修复动作已并入 §5 第 13 项；实施后须复测 heartbeat（目标 ~245-250 iters/s）与宏步进抖动。

| 全链路 t0→socket | ≈134 (p50) | ≈129 (p50) |

- 锁等待记录最大 ~42 µs（旧版 toolbar_release）；两版均是**微秒级热路径**，未见版本性大幅回归；
- 已知问题：旧版无法解析含 `!Macro` 的配置（回退默认配置）→ 公平对比统一用 `P-nomacro`/`*-nm` 变体；宏相关对比只在当前版内做（P-user vs P-nomacro）；
- 冒烟中发现首次注入批次可能未被记录（脚本自动重试覆盖），正式矩阵需校验每块事件计数。

### 4.4 层 D：GUI 干扰证明（H1 专项）

宏页打开 vs 关闭（同版本、同注入），比较 t4-t0 的 P99 与 locks CSV 中 GUI 持锁记录；必要时对 `app.rs:5957-5967` 做"临时加大克隆规模"的压力放大实验验证因果。

### 4.5 判定标准

- 每格数据：记录数一致、CSV 完整、无异常退出；否则重跑。
- 三态结论 + 置信说明（方差、块间漂移）。
- 所有"µs 级"静态估计必须由层 A 数字证实；所有"尖峰"必须由层 C/D 数据证实。
