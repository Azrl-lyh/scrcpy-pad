## 3. K2er 的核心结论

### 3.1 不是“电脑端完整映射”架构

K2er 的总体结构是：

```text
电脑端键盘/鼠标
  -> scrcpy / ADB 输入通道
  -> Android 输入系统与 /dev/input
  -> 手机端 K2er daemon + CoreService
  -> 按配置转换为触摸、滑动、摇杆、宏等操作
```

电脑端主要负责：

1. 通过 ADB 连接手机。
2. 执行激活或停用脚本。
3. 启动手机端 K2er App。
4. 启动 scrcpy 投屏和输入桥接。

真正的映射逻辑主要在手机端。

### 3.2 电脑端内置组件

K2er Desktop 是 Flutter 应用。展开后确认内置：

```text
adb.exe
AdbWinApi.dll
AdbWinUsbApi.dll
scrcpy.exe
scrcpy-server
avcodec-61.dll
avutil-59.dll
libusb-1.0.dll
libmpv-2.dll
media_kit 相关 DLL
```

静态字符串中可见：

```text
sh /sdcard/Android/data/com.k2tap.master/files/exe/activate.sh
sh /sdcard/Android/data/com.k2tap.master/files/exe/deactivate.sh
--start-app=com.k2tap.master
--mouse-bind=++++
```

没有发现 `--no-control`。因此电脑端会把输入交给 scrcpy 控制通道，而不是在电脑端重新实现完整的映射引擎。

### 3.3 手机端 daemon 与输入读取

APK 中包含：

```text
assets/exe/activate.sh
assets/exe/deactivate.sh
assets/exe/arm64-v8a/daemon
assets/exe/arm64-v8a/libreader.so
assets/exe/armeabi-v7a/daemon
assets/exe/armeabi-v7a/libreader.so
assets/exe/x86/daemon
assets/exe/x86/libreader.so
assets/exe/x86_64/daemon
assets/exe/x86_64/libreader.so
```

activate.sh 会：

- 停止旧 k2daemon 和 com.k2tap.core:i；
- 根据 ABI 选择 payload；
- 将 libreader.so 复制到 `/data/local/tmp/k2reader.so`；
- 将 daemon 复制到 `/data/local/tmp/k2daemon`；
- chmod/chown；
- 使用 nohup 启动 k2daemon；
- 检查进程是否成功存活。

daemon 内部可见：

```text
app_process
K2Tap.daemon
com.k2tap.core.Portal
/data/local/tmp/k2core
com.k2tap.core:i
```

libreader.so 导出：

```text
getevent_main
Java_com_k2tap_core_ReaderService_reader
Java_com_k2tap_core_ReaderService_setReaderEnable
Java_com_k2tap_core_ReaderService_getDeviceParameters
```

并包含：

```text
/dev/input/event%d
ABS_MT_POSITION_X
ABS_MT_POSITION_Y
KEY_LEFTCTRL
BTN_LEFT
```

这说明手机端会直接读取 `/dev/input/event*`，获取键盘、鼠标、手柄或触摸事件。普通 Android App 通常没有这个能力，因此需要 ADB shell、Shizuku 或其他特权通道。

### 3.4 CoreService 是手机端翻译层

APK 清单中的 CoreService 属性明确写到：

> Keeps the user's key mapping running: holds the connection to the local input daemon, translates keyboard, mouse and gamepad events for the game in the foreground, and shows the on-screen control bar the user stops it from.

其进程为：

```text
:engine
```

因此可以确认：

- 手机端存在本地输入 daemon；
- CoreService 负责连接 daemon；
- CoreService 负责把键盘、鼠标、手柄事件转换为游戏操作；
- 电脑端不是唯一映射执行者。

### 3.5 特权与激活方式

APK 清单中存在：

```text
android.permission.SYSTEM_ALERT_WINDOW
android.permission.SYSTEM_OVERLAY_WINDOW
android.permission.FOREGROUND_SERVICE
android.permission.FOREGROUND_SERVICE_SPECIAL_USE
android.permission.POST_NOTIFICATIONS
android.permission.REQUEST_IGNORE_BATTERY_OPTIMIZATIONS
android.permission.WAKE_LOCK
moe.shizuku.manager.permission.API_V23
```

并声明：

```text
rikka.shizuku.ShizukuProvider
com.k2tap.master.activation.WirelessActivationService
com.k2tap.master.activation.ActivationActionReceiver
com.k2tap.master.PairService
com.k2tap.master.CoreService
```

没有发现真正的 AccessibilityService。K2er 不是单纯依赖无障碍点击，而是使用 ADB/Shizuku/本地 daemon 特权体系。Root 可能是兼容路径之一，但不是必要条件。

官方激活文档确认：

- 无线调试激活需要 Wi-Fi 局域网；
- 激活后可以关闭无线调试和 Wi-Fi；
- USB 调试必须保持开启，否则激活可能失效；
- 华为没有无线调试，只能使用电脑激活；
- 荣耀部分情况也必须使用电脑激活；
- 电脑激活过程中可能需要华为手机助手或荣耀手机助手协助建立驱动连接。

- MOBA：虚拟中心、技能范围、定向/瞬发/无方向、技能取消位置。

## 4. K2er 值得 scrcpy-pad 借鉴的改进

### 4.1 第一位：可选设备端 helper

这是最重要的借鉴方向，不是照抄某一个游戏功能。

可增加一个完全可选的手机端 helper，使桌面端可以：

- 只负责投屏和原始输入转发；
- 让手机端直接读取 /dev/input；
- 让手机端执行映射与触摸注入；
- 降低电脑端 touch 注入的时序、触点上限和副作用问题；
- 避免 scrcpy 窗口焦点、鼠标抓取和指针消隐相互干扰；
- 支持蓝牙键鼠直接连接手机；
- 为未来华为/荣耀设备做更贴近系统的输入方案。

建议原则：

- 默认关闭；
- 不安装也能使用现有功能；
- 通过 ADB 或 Shizuku 激活；
- 不强制 root；
- 与现有电脑端映射引擎并存；
- 作为独立目录和独立发布分支开发，不污染主程序。

### 4.2 映射动作库

优先级较高：

1. Tap 的间隔、连发、单发、长按。
2. Swipe 的三种模式和时间轨迹录制。
3. 鼠标中键、侧键、滚轮方向的映射源。
4. FPS 瞄准的边界、归中模式、归中延迟、释放延迟、自动释放、偏移矫正。
5. 后坐力控制和随机摇晃。
6. 鼠标右键行走。
7. 手柄控制虚拟鼠标。
8. MOBA 向量技能和取消键。
9. 多输入设备来源、死区、反转、交换轴。

### 4.3 配置和体验

- 每个游戏独立配置。
- 前台应用自动切换场景。
- 宏内部切换场景。
- 本地预设导入导出。
- 连接、设备、激活、日志的四步式向导。
- 输入模式选择矩阵：触摸拖动 / 虚拟手柄 / 开放世界 / 设备端 helper。
- 更清晰的鼠标抓取、指针消隐、暂时退出状态指示。

### 4.4 桌面端流程

K2er Desktop 的清晰流程是：

```text
连接设备 -> 激活手机端服务 -> 启动映射和投屏
```

scrcpy-pad 可借鉴：

- ADB/USB 环境一键自检；
- 驱动、授权、端口占用检查；
- 激活分阶段提示；
- 每阶段日志与失败原因；
- 可选 Wi-Fi ADB；
- 连接后自动启动前台游戏。

## 5. scrcpy-pad 已有的优势

### 5.1 不需要手机端 App

当前 scrcpy-pad 只需：

```text
电脑 + scrcpy + ADB + USB 调试
```

不需要：

- 手机安装 APK；
- 手机端 daemon 常驻；
- Shizuku；
- 账号；
- 云端配置。

这是最重要的部署优势。

## 6. 最终建议

不建议把 scrcpy-pad 直接改成 K2er 的复制品。

最合理路线是：

1. 先把 K2er 的动作库和参数体系搬进现有电脑端映射引擎。
2. 增加游戏配置、场景切换和多输入设备来源。
3. 再设计一个完全可选的手机端 helper。
4. helper 作为独立分支、独立发布目录开发。
5. 保持纯 scrcpy 模式继续可用。
6. 保留 scrcpy-pad 的开源、跨平台、本地配置和可视化优势。

一句话总结：

> K2er 的强项是手机端特权输入链路和成熟的动作库；scrcpy-pad 的强项是零手机端安装、开源、跨平台和可视化配置。最值得借鉴的是“可选设备端 helper”，而不是照搬其商业化双端架构。
