## 0. 导言：这个项目的设计起点

项目的第一句话就把全部约束压缩进了一段话里。用户（Azrl-lyh）在第 1 次交互开场即写明：

> "我要用电脑上已有的 scrcpy 来开发一个二次程序，这个程序必须启动简单，他依附于 scrcpy，可以通过电脑设置快捷键位来操控手机，可以创建轮盘设置轮盘键位，也可以实现长短按等常用模拟器功能。你实现一个基于 scrcpy 的具备模拟器初步功能的二次程序，用什么语言什么架构你来定，不过要开销不高，至少我现在的硬件可以轻松跑动，并且要方便复制，最好可以推到某个包平台实现发布的功能，或者是跨平台发布等等。我推荐使用 rust。"
> —— 对话记录·第 1 次交互

这段话里已经埋下了本项目的**六个原始设计约束**：启动简单、依附 scrcpy、键鼠映射、轮盘、长短按、低开销 + 易分发。后续 20 余次交互没有改变这六个约束，只是在它们之上不断添加新的**次级约束**——而这些次级约束几乎全部来自同一个源头：**用户真实的使用体验**，而不是任何架构教科书。

用一句话概括 scrcpy-pad 的设计品格：

> **它是一部"以用户资产（键位布局）为中心、以可诊断性为防线、以 scrcpy 为地基"的薄控制台。**
> 薄，是指它绝不做 scrcpy 已经做好的事（画面、编码、传输）；控制台，是指它必须比 scrcpy 本体更懂"玩家想怎么按"。

### G1 启动简单：一键脚本 + 单二进制

**原话依据**

> "第一：我不是很明白程序应该怎么启动，你把启动过程详细告诉我，包括编译。"
> —— 对话记录·第 7 次交互

> "第二：又出现了无法控制键盘的情况，我上一次运行命名很成功，难道我需要 sudo 运行程序才可以吗？"
> —— 对话记录·第 7 次交互

**代码如何满足**

| 手段 | 落地 | 设计意图 |
|---|---|---|
| 自动编译 | `启动.sh` 检测 `target/release/scrcpy-pad` 不存在就先 `cargo build --release`；`启动.bat` 同理检测 `release\windows-x86_64\scrcpy-pad.exe` | 用户不需要知道 cargo 的存在 |
| 自动借权限 | `启动.sh`：先直接试读 `/dev/input/event0`；失败则查 `id -nG` 是否含 `input`，含则 `exec sg input -c "$PWD/$BIN"`；都不行才打印指引 | "已加组但没重新登录"这个**最容易卡住新手**的中间态被脚本吃掉 |
| 单二进制 | `Cargo.toml` 的 `lto="thin" / codegen-units=1 / strip=true`，对话记录第 2 次交互记为"release 版，9.4MB 单二进制" | 拷走一个文件就能用，无运行时装包 |
| 图标/许可证编译期嵌入 | `main.rs` 的 `include_bytes!("../icons/scrcpy-pad.png")`、`app.rs` 的 `include_str!("../LICENSE")` | 运行期不依赖任何外部文件，"单独拷走一个可执行文件图标也正常"（第 14 次交互） |

> 这里有一个后来固化下来的原则：**编译产物必须自包含**。第 14 次交互把运行期按目录查找图标改成 `include_bytes!` 后，程序对"当前目录"再无任何隐含依赖——这也解释了为什么 `README.md` 可以说"解压后运行启动脚本，无需安装 Rust"。

### G2 依附 scrcpy，而不是重写 scrcpy

**原话依据**

> "这个程序必须启动简单，他依附于scrcpy……"
> —— 对话记录·第 1 次交互

> "程序完全开源，理论支持任何兼容rust的操作系统编译并安装使用。"（README 的自我定位）
> —— `README.md` 第 59 行

**代码如何满足**

- **不重写画面链路**：画面完全交给用户自己的 scrcpy 窗口。`adb.rs::launch_scrcpy` 只是 `spawn` 一个 scrcpy 子进程，注释明确写着"独立子进程，关闭本程序时不强杀，由用户自行关闭窗口"。
- **只复刻控制协议**：`control.rs` 文件头写着"消息格式参照 scrcpy 源码 `app/src/control_msg.c` 的 `sc_control_msg_serialize()`"，只实现 32 字节 `INJECT_TOUCH` 与 14 字节 `INJECT_KEYCODE`。
- **复用官方 server 二进制**：`start_control_server` 把用户本机的 `scrcpy-server` push 到 `/data/local/tmp/scrcpy-server-pad.jar`，注释注明"scrcpy 官方行为相同，推入 /data/local/tmp"。不自己写设备端。
- **好处**：跟着 scrcpy 升级就行，不需要维护设备端与编解码。

### G3 低开销：低配硬件能轻松跑

**原话依据**

> "不过要开销不高，至少我现在的硬件可以轻松跑动"
> —— 对话记录·第 1 次交互

**代码如何满足**

| 手段 | 落地 | 说明 |
|---|---|---|
| 无 GC、无虚拟机 | Rust 原生二进制 | 没有运行时抖动 |
| 引擎线程阻塞式等待 | `engine.rs` 用 `rx.recv_timeout(wait)`，无事件时最多睡 4ms | 不是忙轮询，CPU 占用接近 0 |
| 输入链路无缓冲 | `TCP_NODELAY` + 专用写线程 + `mpsc` 无锁入队 | 不引入额外队列延迟 |
| 控制通道独占 | `video=false audio=false` | 不与视频流争带宽/解码 |
| 依赖精简 | `eframe` 关闭 `default-features`，`image` 只开 `png`/`jpeg` | 见 `Cargo.toml` |

对话记录第 17 次交互开发者给出的延迟分解也印证了这个设计的开销刻度：

> "我们这一层附加延迟约 1–3ms（其中 2ms 来自 evdev 的轮询 sleep），相对 adb/USB 链路的 10–30ms 属于噪声级。"
> —— 对话记录·第 17 次交互

### G4 方便复制、方便分发、跨平台发布

**原话依据**

> "并且要方便复制，最好可以推到某个包平台实现发布的功能，或者是跨平台发布等等。"
> —— 对话记录·第 1 次交互

> "新建子文件夹叫release，在里面添加rust编译和发布相关的代码和配置文件，使得我在这个文件夹里进行构建的时候，将linux下和windows下的可执行程序编译完方在此文件夹内部，方便我直接发布二进制包供其他人直接用，降低门槛。"
> —— 对话记录·第 12 次交互

**代码如何满足**

- `release/` 自成体系：`build.sh`（Linux/macOS 主机）、`build.bat`（Windows 主机）、`Makefile`（封装 `build.sh`），支持 `all / linux / windows / clean`。
- 产物是"自包含目录 + 压缩包"：`linux-x86_64.tar.gz`、`windows-x86_64.zip`，内含可执行文件、`icons/`、`README.md`、`LICENSE`、启动脚本。
- **容错设计**：`release/README.md` 明确"未安装工具链时，`./build.sh` 会跳过 Windows 部分并继续完成 Linux 构建，不会中断"——第 12 次交互实测：mingw 缺失时"Windows 分支正确检测到工具链缺失并跳过而非中断，同时打印三个发行版的安装命令"。
- **版本号单一来源**：压缩包名从 `../Cargo.toml` 读取，避免手工改版本漏改。

### G5 配置可传递：另存为 / 选用 / 新建 / 校验

**原话依据**

> "然后增加另存为配置的功能，方便传递配置文件。"
> —— 对话记录·第 9 次交互

> "键位保存都是一个名字，如果我想备份，或者使用别人的键位，有些麻烦，得改名……我们可以：指定某个目录下某个文件为键位（这个文件可以没有，没有就创建新的，有就选择已有，这可以做成两个按钮。），然后这个文件名字我们也不作要求，只要是符合我们要求的json就行，然后我们顺便增加一个检测键位json文件是否合法的功能。"
> —— 对话记录·第 10 次交互

**代码如何满足**

| 入口 | 实现 | 意图 |
|---|---|---|
| 保存配置 | `save_profile()`，写入 `self.profile_path` | 就地保存 |
| 另存为… | `DialogPurpose::SaveProfileAs` | 给别人用 |
| 选用配置… | `DialogPurpose::ChooseProfile` → `read_profile_at` 严格校验 | 拿别人的用 |
| 新建配置… | `write_default_profile`（父目录不存在自动创建） | 从零开一份 |
| 检测当前 json | `check_current_profile()` | 出问题时能自证格式合法 |

两个细节值得单独标注，因为它们体现了"配置是用户资产"的态度：

1. **检测对象从"某个文件"改成"当前文件"**。用户第 11 次交互纠正："检测json功能是检测当前的json符合格式要求，而不是检测某个指定的json。更改之。" —— 这是把多余的一次文件选择砍掉。
2. **切换配置时清空撤销栈**。`app.rs` 注释："撤销/重做栈指向旧文件数据，与当前上下文无关，一并清空避免误操作。"

### G6 可诊断：日志、自检、错误信息不误导

**原话依据**

> "为什么我现在显示输入捕获不可用：未找到键盘设备？"
> —— 对话记录·第 3 次交互

开发者的回应直接点明了问题性质：

> "你看到的'未找到键盘设备'是个误导性报错（evdev 枚举会静默吞掉权限错误，真正原因是权限没生效）。"
> —— 对话记录·第 3 次交互

**代码如何满足**

- **无头自检 `--selftest`**：`main.rs::selftest()` 按序检查「evdev 读取权限 → 鼠标设备(REL_X/REL_Y) → 自动寻找 scrcpy → scrcpy 版本 → 定位 scrcpy-server → 定位 adb → adb 设备在线 → 读取分辨率 → 启动 control server → TCP 连接控制通道 → 协议注入(hover)」，逐项 `[PASS]/[FAIL]`，失败时**直接给出下一步动作**（如 `→ sudo usermod -aG input $USER 后重新登录`）。
- **FPS 生效条件自检**：`app.rs::ui_aim_body` 逐条打勾/打叉，并算出 `blocker`——"→ 现在没反应,因为: 映射未开启:按总开关键才生效"。
- **保存日志**：导出设备型号、Android 版本、分辨率、序列号、主机环境与全部运行日志（`device_info` + `build_log_text`）。
- **日志固定在左栏底部**，配置区独立滚动——这条来自一次真实抱怨（第 19 次交互："密度选择标准或宽松后，下面的日志就找不到了"）。

### G7 用户体验优先：不要每次重新寻找路径

**原话依据（这是项目最激烈的一次反馈，也是最有价值的一次）**

> "windows端仍然找不到我的设备，尽管点击启动scrcpy时显示出手机，就算刷新了也不行，无论怎样！都不行，，，。我每次启动的时候都需要手动选择scecpy.exe和scrcpy-server，我在想，scrcpy-server默认和scrcpy.exe一个目录，为什么还要选两次。并且，我启动的时候，scrcpy，并没有找到，这会不会也导致了adb并不会自己同时被找到；严峻的是，我手动执行寻找scrcpy后，adb会不会一并被顺带着找到呢？我们需要另外添加一个adb目录路径指定的功能呢？我们就算添加了adb指定的功能，我们可否这样，确定了adb，scrcpy-server或scrcpy其中之一的时候，如果另外两个或一个为空，是否应该自动试着寻找填充呢？你这样过于影响用户体验了！"
> —— 对话记录·第 10 次交互

**代码如何满足**

| 诉求 | 落地 |
|---|---|
| 三者同目录，选一个补齐其余 | `app.rs::sync_suite`：每帧调用，仅在三元组文本变化时执行，从已填路径的同目录推导补齐另外两者 |
| 手动指定 adb | 左栏 adb 一行支持 [浏览]/[自动]，并可测试运行 |
| 先选 scrcpy，server 自动补齐 | 初始化时 `server_path` **有意留空**；`app.rs` 注释解释："server 找不到就留空：后续用户选定 scrcpy.exe 后，由 sync_suite 按其同目录自动补齐（官方发行包三者同目录），避免预先填入的相对路径阻塞自动发现" |
| 每台机器只配一次 | 这是**用户最新提出的痛点**：路径仍未被记住（详见 §6.3）。工作区已出现一份未接入的 `src/settings.rs`（见 §6.3 备注） |

这次交互还暴露了一个更根本的教训：**开发者在 Linux 上"逻辑上正确"的推理，不足以替代 Windows 上的真实体验**。开发者的第一版修复（进程级统一 adb）在静态逻辑上是完整的，但仍然没有解决"用户必须选两次"的体验问题。

### G8 长按语义的严格定义

这是全项目**唯一一次用户直接纠正语义定义**，也是理解整个动作模型的关键。

**原话依据**

> "增加键位的长按功能，注意灵敏度要保证。"
> —— 对话记录·第 5 次交互

开发者按模拟器惯例实现了"定时长按"（按一下 → 触点按住 N ms → 自动抬起），并把原有语义改名为"按住"。用户立刻纠正：

> "不是的，我从按下键盘的那一瞬间开始，直到抬起之前，都算按下这区域！"
> —— 对话记录·第 5 次交互

**代码如何满足**

| 类型 | 语义 | 代码 |
|---|---|---|
| `Action::Hold` | **键盘按下的瞬间触点落下，键盘抬起的瞬间触点抬起**（全程实时跟随） | `engine.rs`：`if ev.pressed { try_down → touch_down } else if release { touch_up }` |
| `Action::Tap { duration_ms }` | 按下后 `duration_ms`（默认 40ms）自动抬起；`duration_ms == 0` 表示"按住不松手，直到再按一次" | `engine.rs` Tap 分支 + `SchedAct::Up` 定时队列 |
| 一键互转 | UI 行尾 `[转长按]/[转点按]`，坐标保留 | 第 7 次交互 |

值得注意的是**开发者当时并没有改代码**——因为要的语义正是既有的 `Hold` 实现，需要改的只是"注释与命名"。这本身是一条设计教训：**命名错了，用户就会以为功能错了**。第 5 次交互的结论是"不用改代码——你要的这个语义就是现有的长按类型"，并补充了延迟链路说明：

> "键盘 → evdev 捕获(≤2ms 轮询) → 引擎(事件到达即处理) → TCP(Nagle 已关) → 手机……全程无缓冲、无定时器，按下和抬起都是事件驱动即时发送，典型延迟 3~5ms，最坏 ~10ms"
> —— 对话记录·第 5 次交互

### G9 键位是用户资产：宁可拒绝升级，也不许算坏

这条目标不是用户"提"出来的，而是用户**用一次真实损失换来的**。

**原话依据**

> "我暂时把手机竖起来截屏了，可能由于纵向的话宽度不够，这个时候鼠标拖动并不能放大键位，ctrl才可以。但是更严峻的是，这个时候我再换回横版，键位就变了，就不是我之前在横版上设置好了的键位了，但程序重启就好了。我的建议是，键位本身让他允许超过边界，不要搞什么无所谓的检查了，没必要。"
> —— 对话记录·第 20 次交互

**根因（开发者在其机器上确认）**：磁盘上的 `profile.json` 还是 v1 像素坐标（`"x": 2462`），程序用**竖屏截图的 1280 宽**去除横屏布局的 2462，算出 1.92 的"相对值"——换算"成功"了，但键位在内存里被整体算坏；重启重新读盘（还是像素）就又对了。

**代码如何满足**

- `keymap.rs::pixels_fit_space`：升级前先判断"这份像素布局装不装得进当前坐标空间"。
- `keymap.rs::upgrade_profile`：装不进就**拒绝升级、保持像素模式**。函数注释写得很重：

  > "像素坐标是原样使用的,不该为了换个单位就把用户辛苦调好的布局算坏。"
  > —— `src/keymap.rs` 第 638–639 行

- 单测 `upgrade_refuses_mismatched_orientation` 把这个场景**锁死**：竖屏空间 `(1280,2772)` 必须拒绝升级且坐标一字不变；横屏空间 `(2772,1280)` 才升级，且落点像素完全相同。
- 配套：坐标编辑框放开边界（`COORD_RANGE = -8192..=8192`），注释"这里不做越界'纠正'，免得程序擅自改动用户调好的坐标"。

**这是一条保守迁移哲学**：迁移的正确性标准不是"能不能换算"，而是"**换算后用户还认得自己的布局吗**"。当答案不确定时，选择不动。

## 2. 设计动机（Why）

本节回答"为什么选它，而不选另一个"。

### 2.1 为什么不用 `adb shell input`

| | `adb shell input` | 自建 scrcpy 控制协议客户端 |
|---|---|---|
| 能否真正"按住" | **不能**。它是一次性的命令式注入，无法表达"按下 → 保持 → 抬起" | 可以。`INJECT_TOUCH` 有 `ACTION_DOWN/MOVE/UP` |
| 能否连续移动 | 不能（每次都要起一个新进程） | 可以，事件驱动写 socket |
| 延迟 | 每次一条命令，毫秒级进程开销 + adb shell 往返 | 单条 TCP 消息，`TCP_NODELAY` |
| 多点触控 | 极其困难 | 每个触点有独立 `pointer_id` |

对话记录第 1 次交互的原话：

> "源码树可用来读它的控制协议——这意味着我可以直接复刻 scrcpy 的触控注入协议，获得与 scrcpy 本体相同的低延迟按下/抬起/移动控制（`adb shell input` 做不到真正的"按住"）。"
> —— 对话记录·第 1 次交互

**结论**：这不是"更优雅"的选择，而是**唯一能满足"长按语义严格定义"（G8）的选择**。

### 2.2 为什么自建 control-only server，而不复用 scrcpy 窗口

| 方案 | 问题 |
|---|---|
| 复用用户已开的 scrcpy 窗口 | scrcpy 的 socket 是它自己与 server 的私有通道，第三方无法插进去注入；且用户可能还没开窗口、或开了多台设备 |
| 自己写设备端注入程序 | 要处理 Android 权限、隐藏 API、各版本差异，等于重写 scrcpy 的设备端 |
| **启动一个 control-only scrcpy-server** | 官方 server 支持 `video=false audio=false control=true`，只开控制通道；用独立的 `scid` 与本地端口，与用户的画面窗口**完全互不干扰** |

落地细节（`adb.rs::start_control_server`）：

```
scid=0x1a2b3c4d（app.rs::SCID）      →  socket 名 scrcpy_1a2b3c4d
tcp:28383（app.rs::LOCAL_PORT）      →  adb forward 到 localabstract:scrcpy_1a2b3c4d
video=false audio=false control=true
send_device_meta=false send_frame_meta=false send_stream_meta=false
send_dummy_byte=true cleanup=false power_on=false log_level=warn
```

并配 `Drop` 实现：进程结束时 `kill` 子进程并 `adb forward --remove`——**不留脏状态**。

这条设计同时保护了用户的正常使用："与用户正常的 scrcpy 画面窗口并存"（第 1 次交互）。

### 2.3 为什么 Rust + eframe/egui

| 候选 | 取舍 |
|---|---|
| Python + Qt | 运行时要装一大堆包，与 G1/G3/G4 冲突 |
| Electron/Tauri | 体积与内存开销与 G3 冲突 |
| C++ + Qt | 工具链与跨平台发布成本高，与 G4 冲突 |
| **Rust + eframe/egui** | 单二进制、无 GC、依赖树可控、交叉编译到 Windows 只需 `x86_64-pc-windows-gnu` 目标 |

用户明确推荐了 Rust（第 1 次交互："我推荐使用rust"），开发者据此定案：

> "方案定型：**Rust + eframe/egui（界面） + evdev（全局键捕获，可 grab 屏蔽原键） + 自研 scrcpy 控制协议客户端**……单二进制、可 `cargo install`、可发 crates.io。"
> —— 对话记录·第 1 次交互

egui 的选型还与"界面即调试器"（G10）天然契合：**它的绘制是即时模式，画在截图上的浮层可以逐帧跟随配置变化**——"改任何坐标、半径，浮层立刻跟着变"（第 4 次交互）。

### 2.4 为什么 Linux 走 evdev

环境勘察的结论直接决定了这一点：

> "**Wayland 会话 + 用户不在 input 组**：全局键位捕获只能走 evdev（读 `/dev/input/event*`），需要一次性权限配置，程序里做检测和引导。"
> —— 对话记录·第 1 次交互

**为什么 Wayland 下没有别的路**：Wayland 的合成器协议刻意不提供"全局键盘监听"能力（这是它的安全模型），X11 的 `XGrabKey` 那套在 Wayland 下不适用。evdev 直读内核设备是唯一与显示服务器无关的途径，而且附带两个收益：

1. **与焦点无关**——Linux 上从未出现 Windows 那样的焦点 bug（第 9 次交互："而在fedora linux上没有这个问题"）；
2. **可以 `EVIOCGRAB`**——映射开启时真正"屏蔽原键"，避免 W/A/S/D 漏到系统输入框。

代价是权限（`input` 组）与"必须重新登录"这个坑，这由 `启动.sh` 与诊断逻辑共同消化（见 G1/G6）。

### 2.5 为什么 Windows 走 rdev 低级钩子

用户的硬要求是**免管理员**：

> "1.帮我搞定本代码在windows下的编译问题，并在代码里实现自动判断环境执行不同代码段的编译用来跨平台。"
> —— 对话记录·第 6 次交互

对话记录第 13 次交互给出结论：

> "全局键盘捕获用的是 rdev 的低级键盘钩子（`WH_KEYBOARD_LL`），按设计无需管理员权限；不触发 UAC，不需要改系统设置。"
> —— 对话记录·第 13 次交互

**代价被明确记录在案**：`capture.rs` 文件头写着"rdev 的 grab 在 Windows 未实现"——勾了"屏蔽原键"也不生效，这是**功能限制而非权限问题**（第 6、13 次交互均明确说明）。

### 2.6 为什么要有独立的瞄准触点

FPS 瞄准**不能**塞进普通的按键映射池，理由有三层：

1. **语义不同**：普通绑定是"一次事件 → 一次触点动作"，瞄准是"持续位移流 → 一个持续存在的拖动触点"，需要独立状态机（Idle → 按住锚点 → 归中）；
2. **生命周期不同**：瞄准触点在鼠标静止时仍按在屏幕上（视角保位），归中时才抬指重按；
3. **配额独立**：设备端 `PointersState.MAX_POINTERS = 10`；瞄准、轮盘、普通键位各自占用。`engine.rs` 因此为三者分配了明显分离的 id 空间：

   | 用途 | pid | 常量 |
   |---|---|---|
   | 普通绑定 | `1000 + idx` | `bind_pid()` |
   | 轮盘 | `2000 + idx` | `wheel_pid()` |
   | 瞄准 | `3000` | `AIM_PID` |

   而 `MAX_CONCURRENT_KEYS` 从 5 提到 8，理由写在注释里："瞄准指针与轮盘指针另计，因此这里留出余量，便于 FPS 场景同时按住开火/蹲/跳等多个键"。

**归中（recenter）的存在理由**也值得记录——它不是可选优化，而是物理必然：

> "手指拖动无法无限持续（会被屏幕边界挡住），所以偏移过大时要「抬指 + 在锚点重按」。"
> —— `src/keymap.rs` 第 514 行注释

三种归中策略（静止/阈值/不归中）都实现了，因为"手感"没有唯一正确答案（第 15 次交互的方案论证即持此立场）。

## 3. 设计思想 / 设计原则（How to think）

本节把代码里体现的原则**命名**并论证。每条都给出"原则 → 证据 → 为什么这样做"。

### 3.1 单一数据源与唯一换算入口

**原则**：任何"值 → 另一种表示"的转换，全项目只能有一个地方做。

**证据**：`keymap.rs::Mapper`。

> "这是**唯一**做坐标换算的地方:注入、绘制、取点、界面显示都走它。"
> —— `src/keymap.rs` 第 59 行注释

**收益（可验证的）**：把坐标单位从像素换成相对比例，只改了 `Mapper` 与调用点，而**注入、浮层绘制、取点、界面显示四处自动一致**。第 18 次交互的审计表逐项确认："图层过滤 / 截图取点 / 浮层绘制 ✅ 全部改走 `Mapper` 唯一换算入口"。

**代价**：`Mapper` 构造需要读配置锁，于是产生了一条必须在每个调用点遵守的纪律：

```rust
// 坐标换算器必须**先**构造好(它内部会加配置锁);
// 若先拿到配置锁再调 self.mapper() 会自锁,界面会直接卡死。
let m = self.mapper();
let g = self.shared.lock().unwrap();
```

这条注释出现在 `draw_overlay` 中，是**一次真实死锁事故**的纪念碑（见 §5.7）。同一纪律在 `keymap.rs` 里也写了一遍："调用方若已持有配置锁,必须先取好 Mapper 再加锁,否则会自锁"。

### 3.2 自由坐标（相对坐标）优先 —— 一种"用户资产优先"的保守迁移哲学

**原则**：坐标存**相对比例**而非像素；升级时**宁可拒绝，也不毁掉布局**。

**证据链**：

| 环节 | 代码 | 说明 |
|---|---|---|
| 数据模型 | `CoordUnit::{Pixel, Rel}`，`PROFILE_VERSION = 2` | v1 = 像素，v2 = 相对 |
| 兼容读取 | `default_version() -> 1` | **没有 `format_version` 字段的老 json 一律按像素解释** |
| 升级时机 | `upgrade_profile()` 在"得知屏幕尺寸"时调用（连接成功 / 截图 / 开打） | 未升级前 `Mapper.legacy == true` **直通像素**，"行为与升级前逐一相同" |
| 升级守门 | `pixels_fit_space()` | 所有点都在画面内才允许换算 |
| 单元测试 | `upgrade_profile_keeps_pixel_positions`、`upgrade_refuses_mismatched_orientation`、`legacy_json_still_loads_as_pixels` | 三个测试分别锁住"同分辨率不变形""方向不匹配拒绝升级""老 json 必须能读" |

**为什么这叫"哲学"而不是"实现细节"**：它确立了一条判断优先级——

> **兼容性 > 一致性 > 简洁性。**
> 当"统一成相对坐标"（一致性）与"用户已有的布局不能变形"（兼容性）冲突时，程序选择保留像素模式、推迟升级。相对坐标的收益（换分辨率/换手机自适应）可以等，用户的布局不能丢。

这条原则还有一个漂亮的副产品（第 18 次交互发现并验证）：**撤销栈存的是整份配置快照，而坐标单位由每份快照自己的 `format_version` 推导**——所以撤销回到一份"旧格式快照"时，它会按像素解释，与当时的行为完全一致，不会出现"旧数字被当比例用"的错乱。

### 3.3 失败要说人话

**原则**：错误信息必须指向**用户能执行的动作**，而不是指向程序内部的判断结果。

**反面案例（真实发生）**：

> "为什么我现在显示输入捕获不可用：未找到键盘设备？"
> —— 对话记录·第 3 次交互

真实原因是权限没生效，但 `evdev::enumerate()` **会静默跳过打不开的设备**，于是 `opened == 0` 被翻译成了"未找到键盘设备"。

**修复方式（`capture.rs`）**：`opened == 0` 时**不立即报错，而是直接探测 `/dev/input`**，数出打不开的 `event*` 数量，据此区分两种情况：

```rust
if denied > 0 {
    bail!("无权限读取输入设备(/dev/input/event*)。\
           请确认已执行 sudo usermod -aG input $USER 并【重新登录】,\
           且本程序是在重新登录后启动的");
}
bail!("未找到键盘设备");
```

**同类修复还有三处**，构成一条稳定的"说人话"模式：

| 场景 | 不这么做的后果 | 现在的做法 |
|---|---|---|
| FPS 勾了没反应 | 用户只看到"勾了没用" | `ui_aim_body` 逐条自检 + 明确 `blocker` 原因 |
| Windows 找不到设备 | 用户以为程序坏了 | 启动日志打印 `adb: <绝对路径>`，"测试并刷新"打印 adb 版本行 |
| 锚点越界 | 用户不知道注入了却被系统丢弃 | 面板显示"触摸坐标空间: WxH(横屏)"并红色告警 |

### 3.4 安全兜底式释放：绝不"卡键"

**原则**：任何"状态突变"都必须先**释放已经按下的东西**，再切换状态。

**证据**：`engine.rs` 中关闭映射的收尾现在抽成了**一份共用实现** `engine::release_all()`，按顺序做：

1. `aim_lift()` —— 抬起瞄准触点；
2. 遍历所有绑定索引 `fingers.release(idx)` → `ctl.touch_up(...)`；
3. `active_android_keys.drain()` → 逐个 `key(false, kc)`；
4. 遍历所有轮盘 → 先 `touch_move` 到圆心再 `touch_up`；
5. `fingers.free_all()`、轮盘 `active = false`、`pressed = [false;4]`。

**为什么要抽成共用实现（一次真实的"原则被违反"复盘）**：这条原则最初只在**总开关键**这条路径上落实 —— 顶栏那个"映射: 开/关"按钮是直接改 `Shared.enabled` 的，于是"用按钮关映射"会把仍按着的长按触点永久留在手机上（典型的卡键）。根因不是疏忽，而是**触点状态由引擎线程独占**：界面线程拿不到 `Fingers` / `WheelState` / `AimState`，想释放也释放不了。修法没有让界面线程去碰引擎内部状态，而是让界面只置一个请求位 `Shared.toolbar_release`，由引擎在下一轮（≤4ms）走**同一份** `release_all()` 收尾；总开关键那条路径也改成调用它。教训可以概括为：**"安全兜底"这类不变量必须收敛到唯一实现，否则迟早会有一条路径绕过它**。

对话记录第 4 次交互向用户解释这一点：

> "它的作用是：按下后映射引擎才开始把键盘事件翻译成手机触控；再按一下完全关闭。**关闭瞬间会自动释放所有按住不放的触点，不会在手机上"卡键"**。"
> —— 对话记录·第 4 次交互

**同一原则的其他落点**：

- **临时轮盘启用瞬间**：`release_conflicting_binds(...)` —— "启用瞬间,释放与方向键冲突的普通绑定,避免触点卡死"；
- **Ctrl+Alt 交还鼠标**：`aim.released = true` 时既**不瞄准**也**不捕获光标**，且"每次重新开打（按 F8 开启映射）自动恢复捕获，不会把上一局的'交还'状态带过来"；
- **鼠标捕获的成立条件**：只在"映射开启 + 控制通道在线 + 瞄准启用 + 已设锚点（+ 门控键按住）"时才捕获——注释："避免出现'光标被冻结但什么都做不了'"。

**这条原则的极端案例**是鼠标捕获的**逃生设计**。第 15 次交互的方案论证里就写明了风险：

> "**必须留逃生方式**（总开关键或指定组合键），否则鼠标被 grab 后系统完全不可用，用户会'锁死'。"
> —— 对话记录·第 15 次交互

落地为：Linux `EVIOCGRAB` 可随时由总开关键解除；Windows 用 `SetCursorPos` 回中而非系统级锁定。第 16 次交互用户报告"按下字母键后鼠标指针怎么都抖不动"时，开发者的判断是："这是**捕获生效的正常表现，不是 bug**"——但也顺势把门控键的语义改精细：**只在真正瞄准期间捕获，松手立刻把光标还给系统**。

### 3.5 优先级显式化：谁赢必须是规则，不能是偶然

**原则**：同一物理键可能被多个功能引用，此时"谁生效"必须有**明文规则**，且规则要在 UI 里对用户可见。

**明文的优先级链**（`engine.rs` 事件分发的顺序即规则）：

```
总开关键（任何时候都生效，最先判断）
   ↓
临时轮盘启用键（被消费 → continue，不再走后续分支）
   ↓
轮盘方向键（仅"生效中"的轮盘：永久 或 已启用的临时）
   ↓
普通绑定（点按 / 长按 / 滑动 / 系统键）
```

对话记录第 4 次交互把这个规则原样讲给了用户：

> "轮盘和按键会不会互相干涉：不会，但有个优先级——引擎先查'这键是不是轮盘方向键'，是就给轮盘，不是再查普通绑定。**唯一会冲突的情况是你把同一个物理键既设为轮盘方向又设为普通绑定**（比如 W 既是摇杆'上'又是点按），此时轮盘赢。"
> —— 对话记录·第 4 次交互

**其他被显式化的规则**：

| 规则 | 出处 | 说明 |
|---|---|---|
| 取点 / 改键 / 修改响应范围三种"交互态"互斥，**以最后一次操作为准** | 第 20 次交互 | `begin_pick()` / `begin_resize()` 两个统一入口，任何入口切换都先终止另一种 |
| 拖动数值控件只在**开始拖动/聚焦那一帧**记撤销点 | 第 18 次交互 | 避免"每帧塞一条把撤销栈冲爆"；同一帧多改动合并成一条（`pending_undo` 帧末入栈） |
| 检测到"无按下记录的抬起"一律忽略 | `Fingers::release` | "绝不误抬其它键" |
| 同键未抬起时的重复按下被忽略（点按除外） | `Fingers::try_down` | 拦截全局钩子的自动重复；点按走抢占式连点 |

### 3.6 平台差异隔离在最小面

**原则**：平台相关代码集中在最少的地方；**业务逻辑一行 `#[cfg]` 都不该有**；跨平台共享物是**统一键码空间**与**配置文件**。

**实际分布**（`grep '#\[cfg('` 结果）：

| 文件 | cfg 分支数 | 内容 |
|---|---|---|
| `capture.rs` | 8 | Linux evdev / Windows rdev 两套实现 + Windows 常量与工具函数 |
| `keymap.rs` | 2 | 仅 `key_name()`（键码 → 可读名）按平台取名字 |
| `main.rs` | 3 | 自检项的平台差异（Linux 查 evdev 权限与鼠标设备；Windows 直接 PASS） |
| `filedialog.rs` | 2 | 文件对话框后端（xdg-portal / Win32） |
| `engine.rs` / `control.rs` / `adb.rs` / `theme.rs` / `app.rs` | **0** | 完全平台无关 |

**关键设计：统一键码空间**。`capture.rs::map_win_key` 把 rdev 的约 90 个按键枚举映射到 **Linux evdev 键码**；鼠标键同理（`B::Left => 272`、`B::Right => 273`、`B::Middle => 274`）。

> "关键设计：**rdev 按键统一映射到 evdev 键码空间**……这样配置文件在两个平台通用，`key_name` 反向映射取各自平台的键名。"
> —— 对话记录·第 6 次交互

**这条设计的一个额外红利**（第 15 次交互）：鼠标按键复用 evdev 码空间，于是"**现有的绑定 UI 一行未改**就能把'开火'绑到鼠标左键、开镜绑到右键"。

**注意一处诚实记录**：`capture.rs` / `main.rs` / `keymap.rs` / `filedialog.rs` 之外无 `#[cfg]`，但 Windows 上有一个**行为差异**（不是编译差异）：`grab`（屏蔽原键）不生效。项目选择"照实写在文件头注释 + README 跨平台表 + 程序内说明"，而不是假装支持。

## 4. 设计手法（How to do）

本节是具体的工程技巧清单。每条写清"做什么 → 为什么 → 用到哪里"。

### 4.1 通道与连接

| 手法 | 实现 | 解决的问题 |
|---|---|---|
| **control-only server 与画面窗口并存** | 独立 `scid = 0x1a2b3c4d`，本地端口 `28383`，`video=false audio=false` | 不干扰用户自己的 scrcpy 窗口；控制通道独占 |
| **dummy 字节握手** | `send_dummy_byte=true` + `ControlClient::connect` 必须先 `read` 到 1 字节 | 识破 `adb forward` 的"假连接"（见 §5.1） |
| **`set_nodelay(true)`** | `control.rs` 连接后立即设置 | 避开 Nagle 最多 40ms 的合包延迟 |
| **专用写线程 + `mpsc` 队列** | `ControlClient` 持有 `Sender<ControlCmd>`，写线程独占 socket | 注入调用方（引擎线程）永不阻塞在 socket 上 |
| **读线程丢弃下行消息** | 单独线程 `read` 到 4096B 缓冲并丢弃 | 避免接收缓冲填满导致阻塞（剪贴板等下行消息） |
| **`Drop` 清理** | `ControlServer::drop`：`kill` 子进程 + `adb forward --remove` | 不留端口与设备端残留 |
| **连接存活性用原子标志** | `Arc<AtomicBool> connected`，读写线程任一失败即置 false | 引擎可无锁判断通道状态（`is_connected()`） |

### 4.2 延迟与时序

| 手法 | 实现 | 效果 |
|---|---|---|
| **定时动作队列 + 动态超时** | `wait = min(4ms, 距最近到期动作的时间)` | 点按定时抬起与滑动每一步的误差从 **0~4ms（只会偏晚）** 降到 **~1ms**；无计划动作时仍是 4ms 轮询，不增加 CPU |
| **点按抢占式连点** | 上一击未抬起时再按下 → `cancel_up_for(pid)` + 立即 `touch_up` + 开新一轮 | **任何速度连点都完整触发、一击不丢**（12 连/21 连能精确打出先后顺序） |
| **斜向归一化** | 轮盘方向合成后归一化 | 斜向移动不因同时按两个方向而"更快" |
| **按下即发 DOWN** | 事件到达即处理，无防抖、无定时器 | 典型 3~5ms，最坏 ~10ms（第 5 次交互） |
| **鼠标位移合并** | evdev 同一次 `fetch_events` 内的 REL_X/REL_Y 合并为一个 `Motion` | 减少消息数与引擎唤醒次数 |
| **Windows 回中阈值化** | 光标离屏幕中心超过 `CURSOR_RECENTER_PX = 64.0` 才 `SetCursorPos` | 回中次数降一个数量级 → 钩子回调量减半 → 降低触发 `LowLevelHooksTimeout` 丢键的风险 |
| **跳过回中自触发事件** | `skip_next` 标记 | "第一次真实移动不再被丢掉" |

> 延迟优化的取舍依据来自第 17 次交互开发者主动交底的分析：**真正的大头不在代码里**——"无线 adb 换 USB 线可省 30–60ms；设备端关掉电池优化/开游戏模式。这两个的收益比上面所有代码优化加起来还大。"

### 4.3 输入捕获

| 手法 | 实现 |
|---|---|
| **双通道键盘绑定** | 全局钩子（engine 转发 `gui_rx`）+ **egui 本窗口回退**（`egui_key_code()` 把 egui 的 `Key` 映射到 evdev 码）；两者以 `waiting_key.take()` 竞争，只消费一次，天然去重 |
| **优先取 `physical_key`** | 与全局捕获上报一致，"映射不会随输入法/布局漂移" |
| **过滤 `repeat` 与抬起** | 长按不会重复触发绑定 |
| **键码空间统一** | rdev → evdev 约 90 个键；鼠标 `BTN_LEFT/RIGHT/MIDDLE = 272/273/274` |
| **Linux `EVIOCGRAB`** | 键盘 grab（屏蔽原键）+ 鼠标 grab（冻结光标），均由 `AtomicBool` 标志跨线程控制，`device_loop` 内同步 grab 状态 |
| **非阻塞 + 2ms 短睡** | `set_nonblocking(true)` + `WouldBlock → sleep(2ms)` |

### 4.4 配置与文件

| 手法 | 实现 | 解决的问题 |
|---|---|---|
| **三件套联动自动补齐** | `sync_suite`：`scrcpy.exe / scrcpy-server / adb.exe` 任一填好，其余留空自动从同目录推导 | "为什么还要选两次"（第 10 次交互） |
| **便携目录扫描** | `find_scrcpy_portable`：程序目录内 + 程序目录的父目录（同级）下，名字以 `scrcpy` 开头的文件夹，向下最多 3 层；可执行文件按**精确文件名**匹配 | 让"解压到程序旁边"这种最自然的摆法直接可用；`scrcpy-pad.exe` 不会被误认 |
| **路径不经 shell 直传子进程** | `Command::new(path).args([...])` | 空格、中文路径、正反斜杠**全都安全** |
| **绝对路径 adb 全链路** | `ADB_BIN` 进程级静态 + `set_adb_bin()` / `find_adb()` | 一处统一，`devices/分辨率/截图/push/forward/server 启动/断开清理`全部生效 |
| **配置重定向 + 严格校验** | `read_profile_at` / `write_default_profile` / `check_current_profile` | 别人的 json 直接能用，不合法给出中文错误 |
| **编译期嵌入资源** | `include_bytes!`（图标）、`include_str!`（LICENSE） | 完全自包含；LICENSE 缺失会**编译失败**（`release/build.sh` 的提示已相应改准） |
| **`look.json` 静默外观缓存** | 与 `profile.json` 同目录；内容变化才落盘；写入失败只提示一次 | 外观改动不必点"保存配置"也能跨重启保留（第 19 次交互） |
| **后台线程查询屏幕方向** | `refresh_display_space()` 起线程跑 `dumpsys window displays`，结果经 channel 回传 | UI 不因 `dumpsys`（数百毫秒级）而卡顿 |
| **撤销栈 50 层** | 顶栏 ⟲/⟳ + `Ctrl+Z`/`Ctrl+Y`；`pending_undo` 帧末统一入栈 | 连续拖动不会冲爆栈；同一帧多改动合并为一步 |
| **自实现时间格式化** | `fmt_timestamp` / `civil_from_days`（Howard Hinnant 民用历算法） | 为了日志时间戳不引入 `chrono` 这类重依赖 |

### 5.1 `adb forward` 的"假连接"骗过了第一轮验证

**现象**

> "过程中的关键发现：**adb forward 存在'假连接'**——TCP 握手在本地 adb 监听层就完成了，设备侧 server 还没起来时连接会被立即 EOF，且**写方向仍然可用**（极具迷惑性，我最初的验证就被骗过）。"
> —— 对话记录·第 3 次交互

**代价**：第一轮"验证通过"是**假阳性**——如果照此交付，用户侧的表现会是"程序说连上了，但按什么都没反应"，而开发者会找不到原因。用户随后报告的"server 在收到消息后关闭了连接"正是这个问题的下游症状。

**教训与固化**

1. **协议自带的自证机制要用**。scrcpy 官方 server 有 `send_dummy_byte` 参数，客户端读到这 1 字节才算真正建立。修复方式：

   > "启用 scrcpy 协议自带的 dummy 字节机制（`send_dummy_byte=true`），客户端必须读到这 1 字节才认定连接真实建立。**这正是 scrcpy 官方设计该机制的用途。**"
   > —— 对话记录·第 3 次交互

2. **"写成功"不等于"连接有效"**。`control.rs` 的注释把这条永久记录下来：

   > "必须读取 server 的 dummy 字节以确认设备侧 socket 真的被接受（adb forward 在本地总是先完成 TCP 握手，设备侧未就绪时随即 EOF）。"

3. **验证本身要可重跑**。`--selftest` 的"TCP 连接控制通道"项现在走的是完整握手路径，第 3 次交互确认"这次 TCP 连接是读完 dummy 字节的真实连接"。

### 5.3 F6/F8 键码错误

**现象**（开发者自查发现，非用户报告）

> "注意到一个既有 bug：默认开关键 64 实际是 F6（F8=66），一并修正。"
> —— 对话记录·第 6 次交互

**代价**：用户按 F8 没反应，必须按 F6——而所有文档、UI 提示都写着 F8。更麻烦的是**已保存的配置里还是旧值 64**，所以"按 F8 无效"会持续存在，直到用户重新绑一次开关键。

3. **UI 不写死键名**：开关键按钮的标签是**动态**取当前键名渲染的（第 6 次交互："继续 app.rs 的动态开关键标签"），避免"配置改了、提示还写着 F8"。

### 5.4 Windows 焦点依赖：主程序失焦就无法设置键位

**现象**

> "新的bug：我在windows设置的时候，我的scrcpy界面失去焦点的时候，我的主程序是无法设置键位的，具体表现在我设计按键的时候，点击键盘上的键位无反应，只有调出来scrcpy的手机界面，也就是他获得焦点后，才能设置，而在fedora linux上没有这个问题。"
> —— 对话记录·第 9 次交互

**代价**：Windows 用户设键位时必须让 scrcpy 窗口盖在主程序前面，"设置键位的时候很挡视野"——而这个程序的**主交互就是在截图上取点**，等于主路径被堵死。

**根因**：等待绑定时 GUI **只消费一条事件通道**（`全局捕获(hook) → engine 转发 → gui_rx`），而 Windows 上 rdev 的全局钩子在实践中受窗口焦点影响。

**教训与固化**：**关键路径不要有单点依赖**。修复是"双通道"：

> "只要处于'等待绑定'状态，就直接读 egui 本窗口的按键事件并绑定……点'绑定'按钮时焦点必在主窗口，egui 稳定收到按键，完全不依赖全局钩子与 scrcpy 窗口；优先取 `physical_key`；与全局通道以 `waiting_key.take()` 竞争，只消费一次，天然去重，Linux 上也不会双绑。"
> —— 对话记录·第 9 次交互

**这条改动的普适价值**：它把"平台特性差异"转化成了"两条通道的竞争"，从而**不需要按平台分支**——业务逻辑仍然平台无关（呼应 §3.6）。

### 5.6 rfd / zbus 的"特性地狱"

**现象（连续三轮）**

1. "zbus 缺 async 运行时特性（rfd 的 xdg-portal 后端关掉了 zbus 默认特性）。特性统一可解：给本包加一个带默认特性的 zbus 依赖。"
2. "rfd 的 xdg-portal 后端还要求启用 `tokio` 或 `async-std` 特性之一。选 async-std（纯 Rust、较轻），并移除我手动加的 zbus 统一依赖。"
3. 修完依赖才露出**真实的借用错误**（"guard 未释放就调 self.log"）。

**代价**：三轮编译往返，其中前两轮是纯粹的依赖特性探索；更要紧的是**第一轮的"Linux 构建通过"被后来的检查证明可疑**——"这行在 Linux 也该报错——之前的'通过'可疑，重新完整构建核实"。

**教训与固化**

| 教训 | 固化 |
|---|---|
| Linux 文件对话框要**无 GTK 构建依赖** | 选 `rfd` + `xdg-portal` + `async-std` + `pollster`，并把这套组合**连同理由**写进 `Cargo.toml` 注释："（rfd 的 xdg-portal 后端要求配套 async 运行时特性,选 async-std）" |
| "构建通过"必须先排除缓存干扰 | 出现矛盾结论时**做一次完整重建核实**，而不是相信增量结果 |
| 依赖特性问题的解决方式要写进注释 | 否则下一个人（或下一轮对话）会再踩一次 |

**最终形态**（`Cargo.toml`）：

```toml
[target.'cfg(target_os = "linux")'.dependencies]
rfd = { version = "0.15", default-features = false, features = ["xdg-portal", "async-std"] }
pollster = "0.4"
```

### 5.7 自锁：点一下截图，界面直接卡死

**现象**

> "1.有个情况：新的程序，我点击截图后，会立刻卡死，无论怎么尝试解决都不可以。请修复这个bug。"
> —— 对话记录·第 19 次交互

**根因（100% 确定）**

> "是我上一版（主题+相对坐标那一版）引入的**自锁**：`draw_overlay()` 里我先持有了配置锁，又在同一作用域内调用了 `self.screen_size()` —— 而它内部会**再次获取同一把锁**，同线程二次加锁 = 永久阻塞。而 `draw_overlay` **只在有截图时才被调用** —— 所以表现就是'点截图 → 截图一出现 → 整个界面立刻卡死'。"
> —— 对话记录·第 19 次交互

**代价**：程序的**核心功能（截图取点）完全不可用**；更糟的是这类死锁**没有错误信息**——用户只看到窗口失去响应。

**教训与固化**

1. **纪律写成注释，放在现场**：`draw_overlay` 里保留了三行警告注释："坐标换算器必须**先**构造好(它内部会加配置锁);若先拿到配置锁再调 self.mapper() 会自锁,界面会直接卡死。" `keymap.rs` 的 `Mapper` 文档也写了一遍。
2. **同类隐患要全量排查，而不是只修一处**：

   > "修复后我把**所有**会加锁的辅助方法（`mapper/theme/look/screen_size`）的 **24 个调用点**逐一审了一遍，确认没有第二处同类隐患。"
   > —— 对话记录·第 19 次交互

3. **同一类错误此前已经犯过一次**（第 11 次交互）：`ChooseProfile` 分支里 `format!` 参数中连续两次 `self.shared.lock().unwrap()`，第一个 `MutexGuard` 的生命周期延长到整条语句结束，导致第二次 `lock()` 永久阻塞——"这是 Rust 经典陷阱"。当时的修复是"先取数、释放锁，再写日志"。

   **两次同源事故**说明：`Mutex` + 即时模式 UI 的组合下，"持锁期间调用会加锁的方法"是一个**系统性风险**，不是偶发失误。真正的固化手段是 §3.1 那条"唯一换算入口 + 先构造后加锁"的调用纪律。

### 5.8 从"怀疑代码"到"查证上游"：大 pid 误判

**现象**：用户报告"按住一个键不动的时候，再连续点按另一个键，另一个键无论怎么样都不生效"。开发者的第一反应是怀疑 pid 空间：

> "这让我强烈怀疑一个此前未验证的点——我们用的 `pid = 1000 + idx` 大 id，而模拟器多点注入往往只认 scrcpy 官方风格的小 id（0、1、2…）。"
> —— 对话记录·第 11 次交互

**查证结果**：读 scrcpy server 源码后推翻了这个假设——`PointersState` 会把网络侧任意 pointer id 映射到内部 0..10 的小 id，"所以此前怀疑的'大 pid 不被模拟器接受'不成立"。

**真正的根因**：开发者**自己上一轮引入的 40ms 防重锁**吞掉了连点：

> "点按键 2 的上一击要等 40ms 自动抬起后，下一击才被接受。你'按住 1 后连续点按 2'（为排序组合技快速连点）时，每次新按下若撞进上一个 40ms 窗口就被吞掉——表现为'2 怎么都按不出来'。"
> —— 对话记录·第 11 次交互

**教训与固化**

| 教训 | 固化 |
|---|---|
| 怀疑外部（模拟器/协议）之前，先怀疑**自己上一轮的改动** | 修复表里明确写着"上一轮我加的 40ms 防重锁" |
| 上游源码是可以查的，查证优于猜测 | 直接读 `PointersState.java` / `Controller.java` / `control_msg.h` 定论 |
| "防重复"这类防御性逻辑必须区分**抖动**与**合法的快速重复** | 点按改为抢占式连点：`cancel_up_for(pid)` + 立即 `touch_up` + 开新一轮 |
| 位置类缺陷要用**位置无关的跟踪器**解决 | `Fingers`：每个绑定索引独立 `down` 状态 + 计数上限，`try_down` 拦抖动、`release` 防误抬 |

**并且保留了一个诚实的边界**：

> "代码层的并发现在是无干扰的。若你换真机验证仍正常，而模拟器上依旧只出单技能，那属于模拟器底层多点注入只认单指的限制，代码无法绕过。"
> —— 对话记录·第 11 次交互

### 5.9 用错方向的坐标空间（`wm size` vs `dumpsys ... cur=`）

**现象**（用户报告"FPS 功能勾了没反应，鼠标还被定住"）

> "1.你真的实现了fps的功能了吗？不会都被拦截了把？2。我手机上没有安装fps游戏……他们统统滑动不了，只是拖动鼠标并没有按下左键的前提下。"
> —— 对话记录·第 16 次交互

**根因（在用户真机上实测出证据）**

```
adb shell wm size                 → Physical size: 1280x2772   ← 程序一直在用的
adb shell dumpsys window displays → cur=2772x1280              ← 真实的触摸坐标空间
```

`wm size` 返回的是**设备物理分辨率（永远按自然方向）**，而触摸注入使用**当前屏幕方向**下的坐标空间。后果是环环相扣的：

1. 自动放置的锚点落在屏幕外；
2. `aim_target()` 按错误的尺寸钳制，落点仍在屏幕外；
3. Android 输入分发在该坐标找不到窗口 → **整条触摸被丢弃**；
4. 捕获光标、门控键、灵敏度全都正常 → 程序显示"已捕获"、鼠标被冻住，**"不是被拦截，是注入了但被系统扔了"**。

**为什么键位却一直正常**：键位坐标是用户在**截图上点出来的**，截图就是当前方向，坐标本就在正确的空间里——只有瞄准用了 `wm size` 去钳制和自动放点，于是全错。

**教训与固化**

| 教训 | 固化 |
|---|---|
| 一个物理量可能有**多个"正确"的值**，取哪个取决于用途 | `adb.rs::display_size()` 优先 `dumpsys window displays` 的 `cur=WxH`，取不到才回退 `wm size`；注释把这个区别写清楚 |
| 单位/空间错了不会报错，只会"静默丢弃" | 注入前**必须钳制**：`aim_anchor()` + `aim_target()` 双保险 |
| 界面要自报坐标空间 | FPS 面板显示"触摸坐标空间: 2772x1280(横屏)" |
| 解析上游文本输出要有单测 | `parse_display_size_prefers_current_orientation`（含"每行多个 cur=，取最后一个物理显示器"的真实样本） |

### 5.10 竖屏截图把横屏布局算坏：一次"破坏用户资产"的事故

**现象**

> "我暂时把手机竖起来截屏了……但是更严峻的是，这个时候我再换回横版，键位就变了，就不是我之前在横版上设置好了的键位了，但程序重启就好了。"
> —— 对话记录·第 20 次交互

（根因与固化已在 §3.2 详述，此处只强调**教训的性质**。）

**代价**：用户在内存中的布局被**整体算坏**；只有重启（重新读盘）才能恢复。而用户当时并不知道"重启就好"是运气——如果程序在算坏后保存过一次，损失就永久了。

**教训（这是全项目最重的一条设计教训）**

> **任何"自动迁移/自动纠正"逻辑，都必须先证明它不会毁掉用户已有的东西；做不到就拒绝执行。**
> 迁移的验收标准不是"换算是否成功"，而是"换算后用户是否还认得自己的布局"。

**后续连锁修正**（第 20 次交互一并完成）：

1. **删掉"锚点越界就自动重置"**——它同属"擅自改动用户配置"的同类错误。用户的质问一针见血：

   > "你的'截图即校正……锚点若落到空间外（转过屏）自动重置并写日志。'是否忘记了手机除了横屏还有竖屏模式？我在横屏设置了键位，临时弹到竖屏再切回来，按照你的逻辑岂不是乱套完了？"
   > —— 对话记录·第 16 次交互

   现在的 `sync_display_space()` **只写 `ctl.screen_w/h`，不碰锚点、不碰任何键位坐标**。

2. **注入前钳制兜底**：空间临时不对时，注入被钳进屏幕内（无害），而不是去改配置。
3. **开打前重新确认方向**：映射由关到开时后台跑一次 `dumpsys`，把坐标空间刷成当前方向——**用"刷新环境"替代"改写用户数据"**。这是本条教训最漂亮的一次落地。
4. **坐标编辑框放开边界**：`COORD_RANGE = -8192..=8192`，"键位允许落在画面之外，程序不做越界纠正"。

**还有一次同源的"过度自动化"事故**（第 20 次交互）：点[添加]后代码里留了一段"自动再次进入取点"，用户抱怨"取点操作之后就不再有关系了"。修复：删掉自动重取点，并引入 `begin_pick`/`begin_resize` 两个统一入口实现交互态互斥。

> **模式总结**：这个项目里两次最严重的用户体验问题（算坏键位、停在取点），根源都是**程序"自作聪明"地替用户延续或修正了一个状态**。用户想要的是"我说的才算"。

### 5.11 其他值得记录的小弯路

| 现象 | 代价 | 固化 |
|---|---|---|
| 背景图"选完几乎看不见"，只能察觉底色变化 | 功能形同虚设 | 选图时先算**可见度** `(255-面板不透明度) × (255-压暗)`，低于阈值自动调到能看见的档位并写日志；解码失败也写日志且不刷屏（第 19 次交互） |
| 密度选"标准/宽松"后日志被顶出屏幕、翻不下去 | 用户看不到日志＝失去诊断能力 | 左栏拆成两个独立 `ScrollArea`：配置区高度 = 可用高度 − 150，日志固定底部保留 200 条（第 19 次交互） |
| `Ctrl++/-` 与拖动都改不了响应范围 | 新功能完全失效 | 根因是复位阈值写成**绝对差 0.5**，而半径只有 0.03 量级，"`< 0.5` 永远成立"；修复为**按比例判断（±2%）**，并抽出 `keymap::zoom_radius` + 回归单测（第 19 次交互） |
| "已取点、按键未设置时"找不到取消按钮，黄圈永久遮挡截图 | 观感与判断受干扰 | 新增 `draft_active` 状态，使取消按钮在草稿存在时始终可用；`cancel_draft()` 统一清理（第 11 次交互） |
| 选择 json 后界面立即卡死 | 配置重定向功能不可用 | `MutexGuard` 生命周期陷阱，先取数释放锁再写日志（第 11 次交互，见 §5.7） |
| 选 4K 但画面没有变 4K | 用户以为程序没生效 | `--max-size` 是**上限**，scrcpy 只缩小不放大；界面文案改为"4k 上限(最长边 ≤3840)"，并在上限高于设备实际分辨率时日志提示（第 19 次交互） |
| 外观设置重启丢失 | 每次都要重调 | `look.json` 静默缓存，内容变化即落盘（第 19 次交互） |
| Windows 上"scrcpy 画面正常但顶栏无设备" | 核心流程走不通 | adb 不在 PATH：进程级 `ADB_BIN` + `find_adb`（scrcpy 同目录优先） |

## 6. 程序优化目标方向（Where to go next）

本节只列**从材料中能推出依据**的方向。每条按 **现状 → 问题 → 建议做法 → 预期收益 → 代价/风险** 五段展开。分三类：正确性/健壮性、性能/开销、体验/可维护性。

### 6.1 正确性与健壮性

#### O1. Windows `grab`（屏蔽原键）未实现

| 项 | 内容 |
|---|---|
| **现状** | `capture.rs` 的 Windows 分支里 `let _ = (grab, stop);`，键盘 grab 标志保留但不生效；文件头与 README 跨平台表都注明"不支持" |
| **问题** | Windows 用户勾了"映射时屏蔽原键"没有效果，按 W 时字符仍会漏进系统输入框（Linux 上同样的勾选是生效的）。这是一个**平台间功能不对等**，而 UI 上目前无法表达"这个勾在你这个平台上没用" |
| **建议做法** | 用 Win32 低级键盘钩子自行吞掉事件（`WH_KEYBOARD_LL` 回调返回 1 表示已处理），rdev 本身不暴露这个能力，需要引入 `windows-sys` 的 `SetWindowsHookExW` 或换用能吞事件的钩子库。回退方案：至少在 UI 上按平台把这个复选框置灰并给出说明 |
| **预期收益** | 消除平台功能落差；Windows 用户在游戏内打字/聊天时不再误触发 |
| **代价/风险** | 钩子回调里"吞事件"会改变系统级输入行为，一旦逻辑出错可能导致键盘在某程序内完全失效；必须在 catch_unwind 类保护与超时约束下实现，且**必须有逃生路径**（总开关键仍可关闭映射）。对话记录第 6 次交互已给出承诺："等你真机测试时如果要屏蔽原键，我再用 Win32 钩子实现" |

#### O2. `ShowCursor` 引用计数风险

| 项 | 内容 |
|---|---|
| **现状** | `capture.rs::set_cursor_visible` 直接调用 `ShowCursor(1/0)`，仅靠 `if want_grab != hiding` 保证成对；代码注释已标注"ShowCursor 内部是引用计数,必须成对调用" |
| **问题** | `ShowCursor` 是**显示计数器**而非布尔值。若进程在隐藏状态下异常退出、或钩子回调中路径被跳过（`want_grab != hiding` 判断与实际调用之间出现提前返回），计数器会失衡，表现为**系统光标永久消失**（需要重启或其它程序调 `ShowCursor` 才恢复）。第 15 次交互开发者已明确把这列为待真机验证项："`ShowCursor` 引用计数行为，需要你在 Windows 上实测" |
| **建议做法** | ① 用 `GetCursorInfo`/`ShowCursor` 的返回值把计数器**读到已知状态**再操作；② 记录已调用次数，在 `Capture::drop` 与进程退出钩子上补偿；③ 更稳的方案是改用 `SetCursor(NULL)` + `ClipCursor` 组合（不改显示计数器） |
| **预期收益** | 消除"光标消失且无法自愈"的严重体验事故 |
| **代价/风险** | `SetCursor(NULL)` 需要处理 WM_SETCURSOR 消息，可能在某些应用下失效；三种方案都需要 Windows 真机验证 |

#### O3. 跨平台字节序与尺寸假设

| 项 | 内容 |
|---|---|
| **现状** | `control.rs::serialize` 用 `to_be_bytes()` 写大端（协议正确）；但屏幕尺寸在 `ControlClient::connect` 里被**截断成 u16**：`let w = screen_w as u16;`；另外 `engine.rs` 的 `Swipe` 固定采样 64 点 |
| **问题** | ① 若未来支持超宽屏或投屏分辨率超过 65535（现实中极不可能，但 `as` 截断是**静默**的）会出现坐标错乱且无任何提示；② `samples = 64` 对超长/高分辨率滑动或极短时长的滑动都不是最优——短滑动过采样（无意义的消息）、长滑动欠采样（步进可见） |
| **建议做法** | ① 把 `as u16` 改成带范围校验的转换，超限时明确报错并提示；② 采样数按路径长度与时长计算（如 `clamp(8, 128, 时长ms / 4)`），或按"每步移动不超过 N 像素"反推 |
| **预期收益** | 消除静默截断；滑动在长短两种极端下都更自然 |
| **代价/风险** | 采样数变化会改变定时队列长度（`scheduled` 的规模），需要确认对引擎每轮扫描成本的影响（见 O6） |

#### O4. 错误提示仍可更精确

| 项 | 内容 |
|---|---|
| **现状** | 已区分"无权限 / 无设备"（§3.3），`--selftest` 与 FPS 面板都有明确 blocker；但仍有若干"笼统"之处：`ControlClient::connect` 的失败信息是"连接本地转发端口失败(scrcpy-server 是否已就绪?)"，`list_devices()` 失败时**静默返回空 Vec**（`let Ok(out) = out else { return Vec::new() };`） |
| **问题** | 当 adb 路径错误或 adb 无法执行时，`list_devices()` 返回空 → UI 显示"无设备"，用户无法区分"没有手机"与"adb 跑不起来"。这正是 Windows 那次"顶栏一直无设备"事故的同一类盲区（当时靠人工加日志才定位） |
| **建议做法** | 让 `list_devices()` 返回 `Result<Vec<String>>`，把 adb 的 stderr 透出到日志面板；"测试并刷新"已有 adb 版本行的做法可以推广为**启动时的三件套验证块**（scrcpy 版本 / server 存在 / adb 版本 ×3 行） |
| **预期收益** | 用户第一次遇到问题就能自己定位；减少一轮"把日志发我"的往返 |
| **代价/风险** | 签名改动会波及多个调用点；需注意不要让错误日志在每帧刷新时刷屏（现有 `log` 已有一定节流需求） |

#### O5. 并发上限与配额是硬编码，且与设备端上限未联动

| 项 | 内容 |
|---|---|
| **现状** | `MAX_CONCURRENT_KEYS = 8`，注释依据"设备端 `PointersState.MAX_POINTERS = 10`"；轮盘与瞄准指针另计，但**没有总量校验** |
| **问题** | 若用户配置了多个轮盘 + 瞄准 + 8 个并发按键，理论并发指针数可能超过设备端的 10，此时表现会是"某些键按下去没反应"——而这不会有任何提示 |
| **建议做法** | 在配置校验（`check_current_profile`）里做一次**并发预算检查**：`binds 并发上限 + 轮盘数 + (aim.enabled ? 1 : 0) ≤ 10`，超限时给出警告（不阻止保存） |
| **预期收益** | 把"按键没反应"从玄学变成可解释的配置问题 |
| **代价/风险** | 需要维护设备端上限常量（scrcpy 升级可能变化），建议作为可配置项并注明来源 |

### 6.2 性能与开销

#### O6. 引擎 4ms 轮询的 CPU 代价与阻塞式等待

| 项 | 内容 |
|---|---|
| **现状** | 主循环 `rx.recv_timeout(wait)`，`wait = min(4ms, 距最近到期动作的时间)`，无计划动作时**固定 4ms**；每轮还要做一次"瞄准维护 + 鼠标捕获状态同步"的加锁块 |
| **问题** | 空闲时每秒 250 次循环，每次都要抢一次配置锁（`shared.lock()`）；在"界面正在重绘并持锁"时段会形成**两个线程争一把锁**的稳定争用。虽然单次开销极小，但它是**永续的**（哪怕用户没开映射、没连设备） |
| **建议做法** | 分两条路：① 当"映射开启且瞄准启用"时必须保持 4ms 节奏（瞄准维护依赖它）；② 当**映射关闭**时改为**长超时阻塞**（如 200ms）或干脆阻塞在 `recv()` 上，仅由事件与总开关键唤醒；③ 鼠标捕获状态同步可只在**状态将要翻转**时做 |
| **预期收益** | 空闲 CPU 占用与锁争用显著下降（尤其在"程序开着但没玩"的常见状态下）；对电池与低配机器友好，与 G3 一致 |
| **代价/风险** | 状态切换（映射开/关）的唤醒路径必须正确，否则会出现"按了总开关键但引擎还在长睡"的延迟；`aim_tick` 的静止归中依赖 4ms 节奏，关闭映射时需确保相关状态被清干净 |

#### O7. UI 每帧、每行对整份 `Profile` 做一次 clone

| 项 | 内容 |
|---|---|
| **现状** | `ui_binds` 在**每一条键位行**内执行 `let before = g.profile.clone();`（`app.rs` 约 2088 行与 2122 行），用于"编辑开始那一帧"记录撤销快照；轮盘行同理（约 2503 行） |
| **问题** | 复杂度是 **O(按键数) 次 Profile 深拷贝 / 帧**。Profile 含 `Vec<KeyBind>`（每项含 `String` 描述、枚举、`Swipe` 等）与 `Vec<Wheel>`，在 50 条键位 × 8.3 帧/秒（120ms 重绘）下是每秒约 400 次全量深拷贝；键位越多越慢，而键位多正是重度用户的状态 |
| **建议做法** | 只在**真的需要记撤销点的那一帧**才 clone：现在 `point_edit` / `swipe_edit` 的判定发生在 clone **之后**，把顺序倒过来——先用不可变借用判断是否需要（或改为"编辑开始时置一个 `want_snapshot` 标志，帧末统一 clone 一次"）。更彻底的做法是让撤销栈存**增量**而非全量，但收益/风险比不如前者 |
| **预期收益** | 大幅降低每帧内存分配与拷贝；键位数量对 UI 流畅度的影响从线性变为近似常数 |
| **代价/风险** | 需要小心保持"快照必须是**修改之前**的状态"这一语义（现有注释已写明），顺序调整若出错会导致撤销回到错误状态——必须有测试或手动核对覆盖 |

#### O8. `point_at_progress` 每次调用都重建累积长度表

| 项 | 内容 |
|---|---|
| **现状** | `engine.rs::point_at_progress(points, progress)` 每次调用都新建 `cum: Vec<f32>` 并扫描一遍折线求累积弧长；而滑动触发时会**循环调用它 `n-1` 次**（n 为采样点数，圆形/方形轨迹可达 64 点） |
| **问题** | O(n²)：每个滑动动作要做约 63 次表重建，总计约 2000 次浮点开方（实际上 `hypot`/`sqrt` 次数 = n(n-1)/2）。滑动越多（音游、连招）开销越明显，而这全部发生在**持锁的引擎循环内**，会直接推迟其它按键的注入 |
| **建议做法** | 把累积长度表在**进入滑动分支时构建一次**，循环内只做查表插值；或改写成 `point_at_progress_cached(cum, points, prog)` |
| **预期收益** | 滑动触发的引擎内耗时从 O(n²) 降到 O(n)，释放持锁时间；对手速快、滑动多的场景是直接收益 |
| **代价/风险** | 纯函数签名变化，改动面小；但需保持"总长为 0 时返回首点"等边界行为不变（现有代码已处理） |

#### O9. 每次鼠标位移多次加锁 + 每次都重新构造 `Mapper`

| 项 | 内容 |
|---|---|
| **现状** | `CaptureEvent::Motion` 分支：一次加锁读配置 → `s.profile.aim.clone()`（`Aim` 结构体按值复制）→ `s.profile.mapper(...)` → `aim_on_motion(...)`；`aim_on_motion` 内还会再算一次 `aim_anchor()` |
| **问题** | 1000Hz 鼠标下每秒 1000 次：一次锁、一次 `Aim` 复制、一次 `Mapper` 构造、两次锚点换算。虽然单次都是纳秒级，但这是在**最高频的事件路径**上；且 `Aim` 的克隆是为了绕开借用检查（先 clone 再可变借用 `aim` 状态） |
| **建议做法** | 把"锚点像素 + 灵敏度 + 归中参数"缓存为一个小的 `AimRuntime`，**只在配置变更时重建**（配置变更已有明确入口，可置 dirty 标志）；`aim_on_motion` 直接消费该缓存 |
| **预期收益** | 高频路径上的分配与重复计算基本归零；延迟更稳定 |
| **代价/风险** | 引入缓存一致性风险：配置改动后必须可靠重建，否则会出现"改了灵敏度但引擎还用旧值"。需要在配置变更入口（`pending_undo` 那套已经很集中）挂上失效逻辑 |

#### O10. Windows 每次鼠标事件都调用 `GetSystemMetrics`

| 项 | 内容 |
|---|---|
| **现状** | Windows 分支中 `cursor_center()` 在**进入 rdev 监听线程时调用一次**（`let center = cursor_center();`），看起来已经是一次性；但 `capture.rs` 中该函数仍是每次调用都走两次 `GetSystemMetrics` 的形式，且屏幕分辨率/多显示器变化时 `center` 不会更新 |
| **问题** | ① 多显示器或分辨率改变后仍用旧中心，回中会偏；② 已有一次性的正确性，但没有"分辨率变化"的失效路径 |
| **建议做法** | 监听 `WM_DISPLAYCHANGE`（或按需每隔 N 秒/每次进入抓取时刷新一次 `center`），并在进入抓取时重算一次 |
| **预期收益** | 多显示器/改分辨率后光标捕获仍然正确 |
| **代价/风险** | 需要额外的窗口消息或定时刷新；收益场景相对小众，优先级低于 O1/O2 |

#### O11. `dumpsys window displays` 的调用延迟

| 项 | 内容 |
|---|---|
| **现状** | `display_size()` 通过 `adb shell dumpsys window displays` 取 `cur=`；`refresh_display_space()` 已经在**后台线程**执行，结果经 channel 回传，UI 不卡 |
| **问题** | 单次 `dumpsys` 输出可达数百 KB，解析与传输在 adb 链路上有可感延迟（数十至数百毫秒级）；当前"开打前刷新一次 + 每次截图后同步"的频率已经不低，若未来增加刷新点会叠加 |
| **建议做法** | ① 用更轻的查询替代：`dumpsys display` 或 `wm size` + `dumpsys input | grep` 之类的窄化查询；② 给 `display_size` 加**短时缓存**（例如 1 秒内复用结果），并只在 `enabled` 状态翻转或截图时强制刷新 |
| **预期收益** | 减少 adb 往返与解析开销；开打瞬间更快进入可操作状态 |
| **代价/风险** | 缓存可能让"刚转过屏就开打"取到旧方向——必须保留"开打前强制刷新"这一条（现有实现已经有，不能因为加缓存而弱化） |

### 6.3 体验与可维护性

#### O12. 配置文件分散（`profile.json` / `look.json` / 未来的 `settings.json`）可统一

| 项 | 内容 |
|---|---|
| **现状** | `profile.json`（键位，可传递）与 `look.json`（外观，程序自用、静默读写）分属两个文件；`Profile` 内**同时**含 `look` 字段（随配置保存/传递）；启动时 `look.json` 覆盖 `profile.look` |
| **问题** | "外观到底以哪份为准"存在**双来源**：随配置保存的 `look` 与缓存 `look.json`。第 19 次交互已经出现一次交互语义的解释成本："它是'最后一次用的外观'，所以重启后以缓存为准；[选用配置] 时仍会一并切换成该配置的外观（并成为新的缓存内容）。" 这套规则是对的，但**依赖用户理解两套存储的优先级** |
| **建议做法** | 保持"键位可传递 / 本机环境不传递"这一**有价值的分离**，但把规则显式化：① 在 UI 上标明"外观：随配置 / 本机缓存（当前生效：缓存）"；② 或把 `look.json` 更名为语义更明确的名字并在使用说明里画一张优先级小表 |
| **预期收益** | 消除"为什么我选了别人的配置，外观没变/变了"的困惑 |
| **代价/风险** | 纯 UI/文档层改动，风险低；但若改成单一文件则会**破坏"配置可传递"这一目标**（用户的绝对路径/外观会跟着配置文件发给别人），不建议 |

#### O13. 路径记忆缺失：每次重启都要重新寻找 scrcpy（**用户最新提出的痛点 → 已实现**）

> **状态：已实现（本次落地）**。下面保留"问题 → 方案 → 取舍"的完整推理，便于日后理解为什么是这样做的，而不是重新发明一遍。

| 项 | 内容 |
|---|---|
| **原现状（痛点）** | `PadApp::new` 每次都从 `adb::find_scrcpy()` 重新开始；`scrcpy_path` / `server_path` / `adb_path` 只存在于内存（`PadApp` 字段），**不落盘**。在"scrcpy 装在非标准位置"的机器上（尤其是 Windows 用户把 scrcpy 解压到任意目录），用户每次启动都要重新指定路径——这正是第 10 次交互"你这样过于影响用户体验了！"的同类问题 |
| **已实现的做法** | 独立一份 `settings.json`（与 `profile.json` / `look.json` 同目录，见 `app::config_dir()`），保存 `scrcpy_path` / `server_path` / `adb_path` / `scrcpy_args` / `selected_serial`，并配一个 `remember_paths` 开关（左栏 scrcpy 管理区，另设[打开配置目录]按钮）。设计要点：<br>① **为什么单独一份**——"键位配置是**可传递、可另存**的用户资产，而'我这台电脑上 scrcpy 装在哪'是本机私有的环境信息"，混在一起会导致"用户把配置发给别人时就会带上自己的绝对路径"；<br>② **死路径必须清空**——`Settings::sanitize()` 只保留确实存在的文件，"死路径比空路径更糟——空路径还能走'同目录推导 + PATH'的自动逻辑"；清空后启动仍然回落到自动寻找；<br>③ **延迟到帧末写盘 + 内容未变则跳过**（`SettingsCache`），因此每帧调用也安全；时间戳字段不参与"内容是否变化"的比较，否则会退化成每帧写盘；<br>④ **恢复上次设备**——`selected_serial` 若仍在设备列表中就自动选中，省掉每次重连都要在下拉里挑一次 |
| **启动顺序的改动** | `PadApp::new` 现在先在读配置阶段读 `settings.json` 并校验路径；记住的 scrcpy 路径**优先于**自动寻找；adb 定位顺序变为"记住的手动路径 > scrcpy 同目录 > PATH"（新增 `adb::find_adb_explicit`）。也就是说：**记住的路径是加速手段，不是唯一手段**，任何一步失效都自动回落到原有的自动发现逻辑 |
| **预期收益** | 直接消灭本线中最顽固的一条体验痛点；把"启动即可用"从口号变成事实；与 G1/G7 完全一致 |
| **代价/风险** | ① 引入第三份配置文件，需同时接受 O12 的说明成本（缓解：三者同目录 + 界面上一键打开配置目录）；② 保存路径后**必须保留自动寻找的回落**（用户换机器/移动目录时），`sanitize()` 已覆盖；③ 需要同步"使用说明 / README"（已在程序内说明中补入本轮新增内容） |

> **实现要点备忘**：`remember_now()`（帧末登记）+ `persist_settings()`（帧末落盘）成对出现，写在 `ui()` 的收尾处，与外观缓存 `persist_look()` 的处理方式一致 —— 这样"界面线程中任何位置改了路径"都不必关心落盘时机。`settings.rs` 自带 4 个单元测试（缺字段兼容、死路径清理、内容比较语义、路径辅助方法），其中"时间戳不参与比较"这条正是防止"每帧写盘"退化的回归锁。

## 7. 结语：三条贯穿始终的主线

回看 20 余次交互，这个项目真正稳定的东西只有三条，而所有具体设计都是它们的投影。

### 主线一：薄依附 —— 不重复造地基

scrcpy 已经解决了视频、编码、传输、设备端注入；scrcpy-pad 只做两件事：**复刻控制协议**（`control.rs`，173 行）与**理解玩家意图**（`engine.rs` + `keymap.rs` + `app.rs`）。
证据：整个 `control.rs` 只有 173 行，却能提供与官方客户端同级的按下/移动/抬起；`adb.rs::start_control_server` 的参数表里 `video=false audio=false` 一句话宣告了"画面不归我管"。

### 主线二：用户资产优先 —— 宁可不升级，也不动你的布局

`pixels_fit_space` 的拒绝升级、`COORD_RANGE` 的放开边界、`sync_display_space` 的"只校正空间不碰坐标"、删掉"锚点越界自动重置"和"添加后自动重新取点"——**这四处改动是同一条原则的四次执行**：

> **当程序想"帮"用户改点什么的时候，先停下来问一句：他同意吗？**
> 用户的原话是最好的注脚："取点操作之后就不再有关系了"、"键位本身让他允许超过边界，不要搞什么无所谓的检查了，没必要。"

### 主线三：可诊断 —— 让失败自己解释自己

从"未找到键盘设备"的误导报错（第 3 次交互），到 `AimLive` 的实时状态行（第 16 次交互），再到 FPS 面板的逐条自检与 `blocker` 原因（第 16 次交互），最后到"控制区独立滚动、日志固定底部"（第 19 次交互）——每一次体验事故的修复方向都是同一个：**把用户看不见的中间状态变成看得见的东西**。

而这条主线也解释了为什么这个项目能在开发者无法接触真机注入、无法复现 Windows 环境、甚至两次丢失源码的条件下仍然推进：**它把"我猜不到"变成了"程序会告诉你"**。
