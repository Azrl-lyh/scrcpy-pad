## 一、概念名词体系（术语表）

### 1.1 配置与总控

| 中文名 | 代码标识符 | 一句话定义 | 它存在的原因 |
|---|---|---|---|
| 配置 | `Profile`（`keymap.rs:1209`） | 一份完整的映射方案：总开关键、键位列表、轮盘列表、瞄准参数、外观 | 让"一套手感"可以被保存、分享、切换；也是撤销栈与 JSON 持久化的基本单位 |
| 键位列表 | `Profile::binds: Vec<KeyBind>` | 普通绑定的有序数组，**索引即身份** | 索引被用于触点 id（`1000+idx`）与并发跟踪表下标，因此删除条目会导致后续索引整体前移（见 4.2） |
| 轮盘列表 | `Profile::wheels: Vec<Wheel>` | 虚拟摇杆数组，索引同样被用于触点 id（`2000+idx`） | 同上 |
| 配置格式版本 | `Profile::format_version` / `PROFILE_VERSION = 2`（`keymap.rs:5`） | 1 = 坐标存屏幕像素（旧格式）；2 = 坐标存相对比例 0..1 | 让"改单位"这种破坏性变更可以对老配置文件安全降级处理 |
| 坐标单位 | `CoordUnit::{Pixel, Rel}`（`keymap.rs:1407-1413`） | 由 `format_version` 推导（`Profile::coord_unit`，`keymap.rs:1407-1413`） | 是 `Mapper` 唯一的输入开关，决定"配置里的数字怎么变成像素" |
| 总开关键 | `Profile::toggle_key`（`keymap.rs:1219`，默认 `66` = KEY_F8） | 映射总开关的键盘按键 | 打游戏/打字之间需要一个"一键收手"的闸门，且必须能在任何状态下生效 |
| 映射开关 | `Shared::enabled`（`engine.rs:1790`） | 运行时唯一的使能标志 | 所有注入路径的总闸；引擎靠它决定"继续处理事件"还是"整条丢掉" |
| 配置元信息 | `Profile::screen`（`keymap.rs:1209`） | 记录这份布局是按哪个分辨率设计的 | 只作显示参考；相对坐标本身已自适应，但它能帮助排查"这份配置是给谁调的" |
| 共享状态 | `Shared` / `SharedState = Arc<Mutex<Shared>>`（`engine.rs:1834-1865`） | 界面线程与引擎线程唯一的交汇点，含 `profile / enabled / control / aim_live / live / notices / space_recheck / toolbar_release` | 引擎与 egui 是两个线程，必须有一处受锁保护的共同真相 |
| 按键上升沿 | `rising_edge(pressed, was_down)`（`engine.rs:836-838`） | "这一次事件是不是这个键**刚被按下**"，而不是自动重复送来的第 N 个 KeyPress | "按一下翻一次"的判定（总开关键、切换模式的临时轮盘启用键）若每个事件都翻一次，长按半秒就能翻十几次——用户看到的是"按了 F8 却没反应 / 状态跟自己以为的不一样，必须再关一次开一次才恢复"（第二轮） |
| 引擎运行状态 | `EngineLive`（`engine.rs:570`）：`pointers / refused / last_refused` | 当前占用的注入触点数、因触点池满被放弃的按下次数、最近一次被放弃的是哪个键 | "按了没反应"最常见的原因是设备端触点池满了；把这个数字与那个键显示出来，用户才知道该少按一个键，而不是以为程序坏了（`app.rs:8445-8477`） |
| 物理按键镜像 | `Held`（`engine.rs:550`）：`set(code, pressed)` / `has(code)` | "此刻物理上真的按着"的键码集合，只认按键事件，不受配置与轮盘启用状态影响 | 键盘事件是边沿触发的：属主切换（启用/停用临时轮盘、开关映射）那一瞬间，引擎必须知道某个键还按着没有，否则只能等用户"松开再按一次" |

### 1.2 动作语义（一个键按下后做什么）

| 中文名 | 代码标识符 | 一句话定义 | 它存在的原因 |
|---|---|---|---|
| 绑定 / 键位 | `KeyBind { key, action }`（`keymap.rs:1752-1756`） | "某个键码 → 某个动作"的一条规则 | 映射的最小可编辑单位；界面上的每一行、撤销栈里的每一个改动都围绕它 |
| 点按 | `Action::Tap { x, y, duration_ms, radius }`（`keymap.rs:528`） | 按下时触点落下，`duration_ms` 后自动抬起 | 绝大多数游戏按钮只需"点一下"；定时抬起把"按多久"从人手交给程序 |
| 长按 | `Action::Hold { x, y, radius }`（`keymap.rs:538`） | 按下键盘瞬间触点落下，抬起键盘瞬间触点抬起（全程实时跟随） | 需要"按住多久就按多久"的动作（开镜、蓄力、持续移动） |
| 按住切换 | `Action::Tap { duration_ms: 0 }`（`keymap.rs:528`；`engine.rs:4149-4161`） | 点按的特殊档：按下不松手，直到再次按同一键才抬起 | 用键盘实现"开关式"操作，省去一直按住的手部负担 |
| 共享触点池 | `DEVICE_MAX_POINTERS = 10`（`engine.rs:62`）+ `Fingers::try_down(idx, others)`（`engine.rs:505`） | 普通绑定、轮盘、瞄准、**宏**四个子系统**抢同一个** 10 触点池；`others` 就是"别的子系统此刻已占用几个"（宏触点在 2026-10-06 W2-8 起计入同一预算，见 2.12 / 3.14） | 设备端 `PointersState.MAX_POINTERS = 10`，超出的按下会被服务端**直接丢弃**（不是排队）。客户端必须自己先算这笔账，否则用户看到的是"按下没反应、原因不明" |
| 滑动 | `Action::Swipe(Swipe)`（`keymap.rs:545`、`keymap.rs:614-620`） | 按下时沿一条轨迹滑动一次 | 对应 QtScrcpy 的 `KMT_DRAG`；用于技能划屏、镜头甩动等 |
| 滑动曲线 | `Easing`（`keymap.rs:219`）+ `easing_apply`（`keymap.rs:251-265`） | 把"时间 t"映射为"沿轨迹的进度"，即速度分布 | 起终点相同、速度分布不同的滑动，在手感与（在部分游戏中）识别结果上并不等价；曲线让这两件事可以分开调 |
| 滑动轨迹 | `SwipePath`（`keymap.rs:301`）+ `swipe_points`（`keymap.rs:332-347`） | 决定路径的空间形状：条形 / 方形 / 圆形 | 有些手势必须画出特定形状（画圈、画方），直线轨迹无法表达；采样点由起终点派生，所以配置里只需存两个端点 |
| 系统键 | `Action::AndroidKey { keycode }`（`keymap.rs:547`） | 直接向设备注入 Android keycode（返回=4、主页=3 等） | 触摸注入无法表达"返回键"，必须走 keycode 通道 |
| 宏 | `Action::Macro(MacroAction)`（`keymap.rs:549`、`keymap.rs:503-514`） | 触发键点一下，按顺序执行一串预编排的动作（录制时间线或设置步骤） | 连招/连点无法用单个点按表达；宏把"一串动作 + 时间轴"打包成一条绑定，与其它动作同列一行 |
| 录制宏 | `MacroAction::steps: Vec<MacroStep>`（`keymap.rs:466`、`keymap.rs:504-506`） | **字面时间线**：每次按下/抬起的键码 + 距上一步的间隔毫秒；回放时照原时间轴（没有长按语义） | 用户要的是"录制什么就释放什么"——存原始时序，长按/连点都由按下-抬起间隔自然表达，回放时不需要猜意图 |
| 设置宏 | `MacroAction::instructions: Vec<MacroInstruction>`（`keymap.rs:1705`、`keymap.rs:507-509`） | **自包含动作**列表（八种：`delay` / `key` / `combo` / `wheel` / `fps` / `click` / `swipe` / `macro` 嵌套）；每条自带"持续"时长，执行时按下 → 持续 → 抬起 | 有些连招不方便录（键位本机没有、或要精确控制时长）；自包含语义让每一步能单独看、单独调，也便于坐标取点 |
| 扩展宏 / 虚拟键位层 | `MacroAction::virtual_profile: Option<Box<Profile>>`（`keymap.rs:512-515`） | 宏自带的一份微型配置：录制步骤与按键/组合键/轮盘设置步骤先按它解析，再注入设备 | "想按的键位上没有绑定"或不想占用真实键位时，给宏一套临时虚拟键盘/轮盘即可；随宏保存、取消即零残留 |
| 键码空间 | `KeyBind::key: u16`（`keymap.rs:660`） | 全平台统一的 evdev 键码空间 | 让配置在两平台可互换；Windows 由 `vktable` 模块（虚拟键码 ↔ evdev：`map_vk` / `evdev_name`，`capture.rs:1104` 起）映射到同一空间 |
| 右键常量 | `BTN_RIGHT = 273`（`keymap.rs:33`） | 鼠标右键的 evdev 码 | 瞄准门控键最常用的一档，单独给出便于"用右键"一键设置 |

### 1.3 虚拟摇杆（轮盘）

| 中文名 | 代码标识符 | 一句话定义 | 它存在的原因 |
|---|---|---|---|
| 轮盘 / 虚拟摇杆 | `Wheel`（`keymap.rs:823-854`） | 四个方向键驱动一个以 `(cx, cy)` 为圆心、`radius` 为半径的虚拟摇杆 | 对应 QtScrcpy 的 `KMT_STEER_WHEEL`；键盘无法直接产生"模拟量方向 + 力度" |
| 圆心 | `Wheel::cx / cy` | 触点落下的中位坐标（相对值） | 摇杆的"回中点"，也是每次推杆的起点 |
| 响应范围 / 半径 | `Wheel::radius`（`keymap.rs:830`）；点按/长按另有同名字段 | 既决定截图浮层上圆环的大小，也决定手指被推出的距离 | 一个数字同时承担"看得见"和"推得动"，便于对着截图调参 |
| 影响范围 / 范围系数 | `Wheel::scope`（`keymap.rs:1048-1050`，`#[serde(default = "default_wheel_scope")]`，默认 `1.0`，代码内 `clamp_scope` 到 `0.2..=4.0`） | 手指实际推出距离 = `radius × scope`，唯一定义在 `Wheel::push_px`（`keymap.rs:1043-1045`） | 游戏的摇杆判定圈往往与"看得见的圆环"不一致：圆环要够大才好点选/好辨认，但手指推太远会被判成另一个方向。解耦这两个量，才能在不改变视觉与响应圈的前提下微调真实推动距离 |
| 新建轮盘半径 | `NEW_WHEEL_RADIUS_PX = 150.0`（`keymap.rs:755`）+ `Wheel::new_default`（`keymap.rs:1130-1147`） | 点[添加轮盘]新建的摇杆半径固定 150 **像素**，按当前坐标空间换算成相对值后入配置 | 旧版写死"屏宽的 1/9"（2772 宽横屏上就是 307px），比用户手调的大一圈；固定像素才能让"界面显示的半径"与"新建出来的半径"一致 |
| 新建轮盘落点 | `next_wheel_spot(wheels)`（`keymap.rs:1230`）+ `WHEEL_SPOTS` / `WHEEL_MIN_GAP`（`keymap.rs:1152`） | 在候选点里挑一个与所有已有轮盘圆心距离 ≥ `WHEEL_MIN_GAP` 的落点，候选点用尽则沿网格错开 | 两个摇杆圆心重合时，浮层上的两个圆环与两个编号会糊成一团，用户分不清哪个是刚建的那个（第二轮起画布上只留编号，细节在信息卡里） |
| 永久轮盘 | `Wheel::temp == None`（`keymap.rs:851-853`；`engine.rs:3476`） | 任何时刻都生效的摇杆 | WASD 走路这类"一直在用"的方向输入 |
| 临时轮盘 | `Wheel::temp: Option<TempWheel>`（`keymap.rs:851-853`） | 仅在启用期间生效的摇杆 | 让同一批方向键在不同时刻归属不同摇杆（走路 vs 开车 vs 开镜） |
| 启用键 | `TempWheel::key`（`keymap.rs:814`） | 激活/关闭该临时轮盘的按键；**无论该轮盘是否生效，这个键都归它自己**（`key_owned_by_wheel`，`engine.rs:717-727`） | 区分"这一批方向键现在归谁"的开关 |
| 启用模式 | `TempMode::{Hold, Toggle}`（`keymap.rs:730`） | `Hold` = 按住启用键期间生效，松开即失效；`Toggle` = 按一下开、再按一下关 | `Hold` 适合"临时切一下"，`Toggle` 适合"长时间换模式" |
| 归属对账 | `reconcile_binds`（`engine.rs:592-642`）/ `reconcile_wheels`（`engine.rs:652-691`） | 把"谁该有触点"完全重算成 `该轮盘此刻是否生效 × 对应物理键是否按着`，然后补按/补抬 | 归属切换是边沿事件，只靠事件流会让"仍按着的键"失去触点；对账让切换**即时生效**，不需要用户松手重按 |

### 1.4 FPS 鼠标瞄准

| 中文名 | 代码标识符 | 一句话定义 | 它存在的原因 |
|---|---|---|---|
| 鼠标瞄准 | `Aim`（`keymap.rs:1277`） | 把鼠标的**相对位移**映射成手机上一根手指的持续拖动 | 对应 QtScrcpy 的 `mouseMoveMap`；FPS 转视角靠手指拖动，而鼠标天生只有相对位移 |
| 锚点 | `Aim::anchor_x / anchor_y` + `anchor_set()`（`keymap.rs:1365-1367`） | 手指落下的起点（相对坐标）；`(0,0)` 视为未设置 | 拖动必须有起点；锚点取在视角区中央空白处，才不会误触 UI |
| 灵敏度 | `Aim::sensitivity_x / sensitivity_y` | 每 1 个鼠标计数对应多少设备像素 | 不同游戏、不同 DPI 需要不同换算比 |
| 反转 Y | `Aim::invert_y` | 纵向位移取反 | 飞行/载具类游戏的常见需求 |
| 归中 | `RecenterMode::{Idle, Threshold, Never}`（`keymap.rs:1244`）+ `aim_recenter`（`engine.rs:1561-1578`） | 手指拖动无法无限持续（会被屏幕边界挡住），偏移过大时"抬指 + 在锚点重按" | 这是把"无限鼠标位移"投影到"有限屏幕"的唯一办法；三种策略是手感取舍 |
| 静止归中 | `RecenterMode::Idle` + `Aim::recenter_idle_ms` | 鼠标停止移动一小段时间后归中（"停止"按位移事件的**捕获时刻**算，W1-1） | 顿挫最不易察觉，默认档 |
| 阈值归中 | `RecenterMode::Threshold` + `Aim::recenter_threshold` | 偏移超过阈值立即归中 | 适合不停转圈的打法 |
| 门控键 / 按住才瞄准 | `Aim::hold_key`（`keymap.rs:1294`，`0` = 始终瞄准） | 仅当该鼠标键按住时才瞄准 | 对应"开镜才转视角"；同时也避免平时误触 |
| 捕获鼠标 | `Aim::capture_mouse`（`keymap.rs:1297`）+ `Capture::mouse_grab`（`capture.rs:659`） | 瞄准期间隐藏/冻结系统光标 | 否则鼠标会顶到屏幕边缘、位移丢失，且光标乱跑影响观感 |
| Ctrl+Alt 交还鼠标 | `AimState::released`（`engine.rs:1155`）+ `ctrl_alt_chord`（`engine.rs:203-205`） | 按一次 Ctrl+Alt 把鼠标交还系统，再按一次收回 | 打游戏中途要切出去点别的窗口，不能把鼠标锁死 |

### 2.2 输入捕获组

- **包含的功能**：Linux 侧 `capture.rs` 的 `linux` 模块——evdev 设备枚举与键盘/鼠标识别、按键事件转发、鼠标相对位移合并、键盘 grab 与鼠标 grab 的状态同步；Windows 侧 `capture.rs` 的 `windows` 模块——低级钩子（键盘/鼠标按键/滚轮，键盘用 `map_vk_ex` 带 `LLKHF_EXTENDED` 判别小键盘与导航区、滚轮按齿累加，W1-5）、Raw Input 位移通道（W1-2，`raw_wnd_proc` / `handle_raw_input` / `setup_raw_input`）、1ms 位移合并器（W1-3，`MotionCoalescer`）、钩子心跳自愈（W1-4，1s 往返心跳 + VK 0xFF 探针，连续 3 次无回音或消息泵卡顿就就地重装并上报 UI；键盘钩子没装上时不发探针，连续 2 轮重装仍无回音则停用探针自愈只留泵检测）、光标回中与透明系统光标。两条路产同一种 `CaptureEvent`。
- **组内协作**：Linux 侧 `linux::start` 为每个识别出的设备起一个 `device_loop` 线程，共用同一个 `Sender<CaptureEvent>`；grab 标志由界面/引擎写、由设备线程读并落到 `EVIOCGRAB`。Windows 侧 `windows::start` 起两个线程：钩子线程（装钩子 + 消息循环，回调里只塞队列）与中转线程（差分 / 回中 / 对账）。鼠标的 `REL_X/REL_Y` 在同一次 `fetch_events` 内累加后合成**一条** `Motion`，减少下游消息数；W1-2 起 Windows 默认用 Raw Input 的设备计数（不经光标）。W1-3 起 Windows 侧又加了一层 `MotionCoalescer`：1ms 窗口（从第一条位移的捕获时刻起算）内的多条位移合成一条 `Motion`（`dx/dy` 求和、时刻取最后一条，净位移为 0 不发），窗口等待折进 `recv_timeout`，按键/另一路位移/退出等顺序点无条件 flush——8000Hz 鼠标的消息数降到 ≤1000/s，1ms 上限的延迟不叠加在排队的旧延迟上。W1-4 起两个线程之间还有一条心跳：中转线程每秒 `PostThreadMessage(WM_APP_HB)`（并把自测的循环间隔写进 `consumer_gap_ms`，睡眠/被抢 CPU 时不冤枉钩子线程），钩子线程装钩成功后先种一拍、处理到心跳就回写 `pump_ms` 并 `SendInput` 一枚被自己回调吞掉的 VK 0xFF 探针；上一拍间隔 >3s 或探针连续 3 次无回音 ⇒ `reinstall_hooks` 卸装重来（`hook_ok` 同步更新、探针期望跟着新结果走、`dead_ms` 事件由中转线程取走上报 UI；连续 2 轮重装仍无回音则停用探针自愈）——系统静默摘钩不再等于"按键突然全部失灵、只能重启"。W1-5 起这条链路上还有两处保真：小键盘/导航区按 `LLKHF_EXTENDED` 判别（同一物理键 NumLock 开/关报不同 VK；小键盘 Enter 与主 Enter 由此分开），滚轮按 120 一齿累加（不足一齿的余量跨事件保留），每 400ms 的对账改为"同一物理键的**全部别名 VK 任一按着就算按着"（NumLock 状态变化不再把按住的键误判成已释放）。
- **输入**：物理键盘/鼠标事件、`grab` / `mouse_grab` 两个 `AtomicBool`。
- **输出**：`CaptureEvent::Button{code, pressed, at}` 与 `CaptureEvent::Motion{dx, dy, at}`（W1-1 起每个事件都带捕获时刻）两条流，其中 `Button` 同时进入引擎与界面（`gui_tx`），`Motion` 只进引擎。

### 2.3 动作语义组

- **包含的功能**：五种 `Action`（Tap / Hold / Swipe / AndroidKey / Macro）的语义实现（派发在 `engine.rs:3379-3588`；宏的展开与发射另成一组，见 2.12）、并发跟踪 `Fingers`（`engine.rs:479`）、定时动作 `SchedAct`（`engine.rs:1886`、`engine.rs:2166-2224`）、系统键去重（`engine.rs:4231-4239`）、触点抢占取消 `cancel_up_for`（`engine.rs:3725-3728`）、**共享触点池预算**（`Fingers::try_down` 的 `others` 参数，`engine.rs:4154/4168/4190/4203`）。
- **组内协作**：
  - `Fingers` 为每个绑定索引记录"是否已按下"，`try_down` 同时负责三件事：去抖、普通绑定并发上限 `MAX_CONCURRENT_KEYS = 8`（`engine.rs:56`）、以及"加上轮盘/瞄准已占用的触点后不得超过设备端 `DEVICE_MAX_POINTERS = 10`"（`engine.rs:62`）。`release` 只在确有按下记录时才允许注入 UP——队列两端严格成对。
  - **被拒绝的按下会说话**：挤不进触点池时不再"发出去让服务端悄悄丢掉"，而是由 `refuse`（`engine.rs:786-804`）记一次 `EngineLive.refused` 与 `last_refused`，界面左栏据此显示"因触点池满被放弃 N 次（最近是哪个键）"。
  - `Tap` 按下时把抬起动作排进 `scheduled`；`Swipe` 按下时一次性把整条轨迹的 `Move` 与终点的 `Up` 排进 `scheduled`；调度循环在每次事件等待前先处理到期动作，并把等待时间精确对齐到"最早到期时刻"（上限 4ms），使定时抬起误差从 ~4ms 降到 ~1ms（`engine.rs:2608-2626`）。
  - `Tap` 的 `duration_ms == 0` 走"按住切换"分支，完全不进 `scheduled`。
  - **结构变化先抬手**：`sync_structures`（`engine.rs:909-989`）用 `binds_signature`（`engine.rs:997-1021`）识别"绑定表数量/键码/动作类型"的变化，一旦变化就 `release_all_binds`（`engine.rs:877-895`）把在按的触点全部抬起并补发 UP（连被删掉的槽位也遍历到），再按新长度重建按下表。若重建前确有触点按着，还会留一条引擎通知（第二轮，`engine.rs:3268-3272`）。
- **输入**：`CaptureEvent::Button`、`Profile::binds`、`Mapper`、`ControlClient`。
- **输出**：`touch_down / touch_move / touch_up / key` 四类控制消息；`Fingers` 与 `active_android_keys` 两个内部状态表、`EngineLive` 诊断快照。

### 2.4 虚拟摇杆组

- **包含的功能**：永久与临时轮盘的判定（`engine.rs:3421`）、启用键与两种模式（`engine.rs:3396-3467`，**第二轮起切换模式只认上升沿**）、触点推杆与回中（`update_wheel`，`engine.rs:5315-5382`）、斜向归一化（`engine.rs:3421`）、停用释放（`deactivate_wheel`，`engine.rs:3914-3925`）、冲突绑定强制释放（`release_conflicting_binds`，`engine.rs:3929-3957`）、影响范围 `scope`、**归属对账**（`reconcile_wheels`，`engine.rs:652-691`；`key_owned_by_wheel`，`engine.rs:717-727`）、**轮盘结构指纹与重建**（`wheel_signature`，`engine.rs:1069-1103`；`sync_structures`，`engine.rs:909-989`）、新建轮盘的固定半径与落点、**画布标注瘦身 + 摇杆信息卡**（第二轮，见 2.4.3）。
- **组内协作**：
  - `WheelState`（`engine.rs:1937`）保存四方向按下位、触点是否落下、上次落点与临时轮盘是否激活。`update_wheel` 由 `pressed[4]` 计算出 `dx = right - left`、`dy = down - up`；两者同时非零时乘 `1/√2` 归一化，保证斜向不会比直向"推得更远"。
  - **方向状态不是"自己记的"，而是重算出来的**：`reconcile_wheels` 把每个方向位直接写成 `该轮盘此刻是否生效 × 对应物理键是否按着`，然后调 `update_wheel` 补推/回中。于是"按下启用键的瞬间，已经按着的方向键立刻推动摇杆"不需要任何特判。
  - 触点落下采用"**先按圆心、再移到目标**"两步（`engine.rs:5372-5373`）：游戏看到的是从中位推出去的过程，而不是手指凭空出现在边缘。
  - 四方向全部松开时，`update_wheel` 先 `touch_move` 回圆心再 `touch_up`（`engine.rs:5346-5354`）；`deactivate_wheel` 同理（`engine.rs:3914-3925`）。**这个"先回中再抬起"不是多余的**：抬起坐标与落下坐标不一致时，部分游戏会把它判成一次滑动。
  - **触点池预算**：轮盘申请新触点前要看 `reserved`（普通绑定 + 瞄准 + 其它轮盘已占用的触点数，`wheel_pointers`，`engine.rs:736-738`）；挤不进去就由 `update_wheel` 返回 `true`（`engine.rs:5366-5371`）放弃这一次按下，调用方据此 `refuse` 计数并留一条引擎通知（`engine.rs:685-689`）。
  - **结构变化先抬手**：`wheel_signature` 只认"数量 + 四个方向键 + 启用键与模式"，**只改圆心/半径/scope 不会触发重建**（避免一边打一边调参被反复抬手）；指纹一变就先按旧状态把落下的轮盘触点回中再抬起，然后 `vec![WheelState::default(); 新长度]`（`engine.rs:958-987`）。
- **输入**：`CaptureEvent::Button`、`Profile::wheels`、`Mapper`、`ControlClient`、`Held`（物理按键镜像）。
- **输出**：轮盘触点（pid = `2000 + 索引`）的 down/move/up；被强制释放的普通触点与系统键；`EngineLive` 诊断计数。

#### 2.4.1 影响范围 `scope`（本轮已落地，现状说明）

> 这一节原写作时 `scope` 尚未进代码，现在它已存在于 `src/keymap.rs`；下文按**真实实现**描述。

| 项 | 说明 |
|---|---|
| 字段 | `Wheel::scope: f32`（`keymap.rs:1048-1050`），`#[serde(default = "default_wheel_scope")]`，`default_wheel_scope()` 返回 `DEFAULT_WHEEL_SCOPE = 1.0`（`keymap.rs:746`） |
| 语义 | **摇杆触点实际推出的距离 = `radius × scope`**，唯一定义在 `Wheel::push_px`（`keymap.rs:1043-1045`） |
| `radius` 的职责 | 不变：仍然决定截图浮层上那个圆环的大小（视觉圈 / 响应圈） |
| `scope` 的职责 | "影响范围系数"，乘在半径上，决定手指真正被推多远 |
| 取值范围 | `clamp_scope` 收敛到 `SCOPE_MIN = 0.2 ..= SCOPE_MAX = 4.0`（`keymap.rs:743`、`keymap.rs:781-787`） |
| 界面 | 用 DragValue 编辑，并显示换算出的实际像素值（`app.rs:7212-7232`） |
| 浮层可视化 | 当推出距离与半径相差 > 1px 时，浮层额外画一圈橙色虚线外环表示"触点实际能推到的最大距离"，并在标签里显示像素值与倍数（`app.rs:7778-7810`） |
| 兼容性 | 老配置没有这个字段 → 反序列化得 `1.0` → **行为与老配置完全一致**（单测 `wheel_scope_defaults_and_clamps`、`wheel_push_px_is_a_radius_scale`，`keymap.rs:1865`、`keymap.rs:1865`） |
| 与坐标单位的关系 | `scope` 是无量纲系数，与坐标单位（Rel/Pixel）无关：任何换算路径都不该碰它；升级路径已删，像素配置直通时更是原值保留 |
| 它解决的问题 | 游戏的摇杆判定圈往往与"看得见的圆环"不一致：圆环要够大才好辨认、好拖拽，但手指推太远会被判成别的方向。把"视觉/响应圈"与"实际推动距离"解耦后，可以在不动视觉布局的前提下微调真实推杆距离 |

对应到注入代码，`update_wheel` 中的
`let wr = w.push_px(m);`（`engine.rs:5146`）
即 `m.len(w.radius * clamp_scope(w.scope))`
——**其余逻辑（归一化、两步落下、回中抬起、`st.last` 去重）一律不变**，因此这是一处纯参数化改动，不引入新的状态机分支。唯一新增的分支是触点池预算：`reserved >= DEVICE_MAX_POINTERS` 时放弃这次落下并计数（`engine.rs:5366-5371`）。

- **输入**：`Profile.look`、是否启用背景图、**手机截图的亮度网格**（`PadApp.shot_lum`）。

### 2.12 宏组（2026-10-06 W2-8 重建后补写）

> 本文此前**没有宏相关章节**；本节连同 §1.2 的宏术语、§3.14 的联动、§4.9 的边界条件一并补上。宏的语义在 2026-10-06 按用户指令整体重建（用户原话要点："录制什么释放什么，宏不需要长按"），重建动机与逐条证据见《全面审计与提升方案-2026-10-05.md》§W2-8；本节只描述**重建之后**的现状。

- **包含的功能**：录制宏（`MacroAction::steps: Vec<MacroStep>`，`keymap.rs:503-514`、`keymap.rs:504-506`）、设置宏（`MacroAction::instructions: Vec<MacroInstruction>`，`keymap.rs:503-514`、`keymap.rs:507-509`）、扩展宏虚拟键位层（`MacroAction::virtual_profile`，`keymap.rs:513-514`）、宏页与虚拟键盘上的宏窗口（`PadApp::ui_macro_page`，`app.rs:5469`；`ui_macro_virtual_window`，`app.rs:5845`）、排程与展开（`schedule_macro` / `schedule_macro_into`，`engine.rs:4362` / `engine.rs:4384`）、触点分配（`MacroPlan`，`engine.rs:4272`）、运行表（`macro_down`，`engine.rs:2107-2115`）、取消（`cancel_macro_scheduled`，`engine.rs:3766`）、坐标取点（`CoordSlot::MacroClickPoint` / `MacroSwipeStart` / `MacroSwipeEnd`，`app.rs:6359-6437`）。
- **两种宏，一份模型**：
  - **录制宏 = 字面时间线**。`MacroStep { code, pressed, delay_ms }` 只记"哪个键按下/抬起、距上一步多少毫秒"（没有坐标字段，鼠标**移动**不会被录进去）。回放时按下 = 落一根宏 lane 的手指（触摸 / 系统键 / 轮盘方向键手势），抬起 = 抬那一根——**没有长按语义**，"按住多久"就是录制里按下-抬起的间隔；键盘自动重复在录制端已合并，不会变成连点。录制里没有配对抬起的按下，在宏结尾兜底抬起（安全网，不改变已配对的步骤）。
  - **设置宏 = 自包含动作**。八种指令（`delay` / `key` / `combo` / `wheel` / `fps` / `click` / `swipe` / `macro` 嵌套）每条自带 `delay_ms` 与 `duration_ms`，执行时**按下 → 持续 → 抬起**，一步做完轮到下一步。`MacroInstruction::delay_ms()`（`keymap.rs:474`）给排程器算"本步骤相对上一事件的等待"。
  - 两部分可单独使用，也可并存于同一个宏。
- **组内协作**：
  - **触发键是一条普通绑定**，动作是 `Action::Macro`：只在**上升沿**（`fresh_press`）启动一次（`engine.rs:4241-4258`），整条宏在这一刻被**一次性展开**成具体动作排进 `scheduled` —— 录制的按键**不会**再回到输入流（旧实现经组合门控 + 物理镜像重新派发，正是"录了点击+滑动、回放不出来"的根因）。
  - **执行实例与触点号**：`run()` 的 `macro_exec_seq` 每触发一次 +1；`MacroPlan` 按 `pid = MACRO_PID_BASE(7000) + (exec % MACRO_EXEC_LANES(8)) × MACRO_EXEC_STRIDE(4096) + slot` 分配（`engine.rs:4284-4288`、`engine.rs:4272-4289`）。同一实例内不复用 slot、不同实例的 pid 段不重叠 —— 同一条宏连点、两个宏并发都不会互相顶掉触点。
  - **排程是"边规划边发射"**：所有动作先写进 `MacroEmit` 暂存区，`flush` 按 `(时刻, 排程序号)` 排序后并入 `scheduled`（`engine.rs:4334`）——"同刻先抬后按"的顺序由此钉死；嵌套宏必须共用同一个发射器，才能保证每个按下都有配对的抬起。
  - **`macro_down` 是宏触点的唯一真值表**（`engine.rs:2107-2115`）：落下时登记 `pid → 最近位置`；抬起**只对表里的 pid** 发（幂等：不会"只发 down 没 up"，也不会"up 没有 down"）；`MacroMove` 只更新表内实按着的触点。取消路径按**最近位置**逐个抬起表内触点，并过滤掉排程里的全部宏动作（三个调用点：关闭映射 / 截图通道断开 / 控制通道不可用）。
  - **活轮盘 vs 虚拟层轮盘**：按到**当前配置**的轮盘方向键时，驱动的是那个真的摇杆（`MacroWheel`，按下/抬起照录制时刻，按住期间由 `MacroMove` 推杆）；按到**虚拟层**的轮盘时，因为设备上并不存在这个摇杆，展开成**一次推离手势**（`live_wheels = virtual_ctx.is_none()`，`engine.rs:4395-4397`；`wheel_dir_of` / `wheel_part_at` / `wheel_part_angle`，`engine.rs:5022-5030`）。
  - **与用户操作隔离**：宏触点不共用绑定 pid、不写 `held` 物理按键镜像、不进 `combo_gate` 派发链路 —— 宏与"手上的键"各用各的手指，唯一共享资源是十指预算（见 3.14）。
- **输入**：`Action::Macro` 绑定（触发键）、宏页编辑出的 `MacroAction`、活配置 / 虚拟层配置（把录制键码解析成动作）、`Mapper`（坐标换算）、`ControlClient`（注入）。
- **输出**：宏 lane 的触点 down/move/up 与系统键、FPS 开关（`fps` 指令）、宏总时长（`schedule_macro` 的返回值，供嵌套宏与单测使用）。

## 三、联动关系（耦合与优先级）

### 3.0 共享触点池与"归属对账"（本轮新增的两条总则）

这两条是本节所有联动的前提，先单独说清楚。

**① 触点池是共享的，只有 10 个名额。**

设备端 scrcpy-server 的 `PointersState.MAX_POINTERS = 10`（`engine.rs:58-62` 的注释写明来源），超出这个数的按下会被服务端**直接丢弃**（不是排队）。因此普通绑定、轮盘、瞄准三个子系统抢的是同一个池子：

```mermaid
flowchart LR
    B["普通绑定<br/>MAX_CONCURRENT_KEYS = 8"] --> POOL
    W["轮盘<br/>每轮盘最多 1 个"] --> POOL
    A["瞄准<br/>AIM_PID = 3000，最多 1 个"] --> POOL
    POOL{"DEVICE_MAX_POINTERS = 10"}
    POOL -->|"放得下"| OK["注入 touch_down"]
    POOL -->|"放不下"| NO["放弃 + refuse(live, code)<br/>界面显示『因触点池满被放弃 N 次』"]
```

- `Fingers::try_down(idx, others)` 里的 `others` 就是"轮盘 + 瞄准此刻占用的触点数"（`engine.rs:498-520`）；调用点用 `wheel_pointers(&wheels) + usize::from(aim.down)` 算出来（`engine.rs:3544-3548`，消费点 `engine.rs:4154`/`engine.rs:4168`/`engine.rs:4190`/`engine.rs:4203`）。
- 轮盘与瞄准同理：`update_wheel(..., reserved)` 返回"是否因池满放弃"（`engine.rs:5366-5371`），`aim_on_motion(..., reserved)` 在"触点还没落下且池已满"时直接返回 true 让调用方计数（`engine.rs:1635`）。
- 8 这个普通绑定并发上限现在是**软上限**：真正的硬边界是 10，`MAX_CONCURRENT_KEYS` 只是"给 FPS 场景留出轮盘与瞄准的余量"（`engine.rs:52-56`）。
- 界面把这件事显式化：左栏的"引擎: 触点 n/10 · 因触点池满被放弃 N 次（最近是哪个键）"（`app.rs:8445-8477`，数据来自 `Shared::live: EngineLive`，`engine.rs:570`）。`last_refused == 0` 时显示"瞄准"（键码 0 不是合法 evdev 键）。**第二轮起，池满还会由引擎写一条通知进日志**（`engine.rs:3574-3586`，每秒最多一条）——左栏数字回答"发生了几次"，日志那句回答"刚才放弃的是哪个键、该怎么办"。

**② 归属一变，就按物理按键状态对账。**

键盘事件是边沿触发的，"某个键现在归谁"却可能在两帧之间改变。引擎因此维护一份**物理按键镜像** `Held`（`engine.rs:549-567`），所有按键事件在进入任何分支之前先写它（`engine.rs:2825`，在总开关键判定之前；同一行顺带算出 `fresh_press` 上升沿）：

```mermaid
flowchart TD
    EV["CaptureEvent::Button"] --> H["held.set(code, pressed) + rising_edge 上升沿<br/>（最先执行，不受配置/启用状态影响）"]
    H --> T{"总开关键（只认上升沿）?"}
    T -->|"关→开"| RC["sync_structures + reconcile_binds + reconcile_wheels"]
    T -->|"开"| W{"临时轮盘启用键?<br/>（Toggle 模式同样只认上升沿）"}
    W -->|"启用/停用"| RC2["release_conflicting_binds / deactivate_wheel<br/>再 reconcile_binds + reconcile_wheels"]
    W -->|"否"| D{"生效轮盘的方向键?"}
    D -->|"是"| RC3["reconcile_wheels"]
    D -->|"否"| BIND["普通绑定处理"]
```

- `reconcile_binds`（`engine.rs:592-642`）只对**状态型**动作对账：`Hold` 与 `AndroidKey`（按着就该有触点、松开就该抬起）；`Tap`（含时长 0 的开关档）与 `Swipe` 是一次性动作，由事件自己收尾——在这里对账会把它们反复翻转/重放。
- `reconcile_wheels`（`engine.rs:652-691`）把方向状态重算为"是否生效 × 是否按着"，因此**启用瞬间已按着的方向键立刻推杆**。
- 归属判定收敛成一个函数 `key_owned_by_wheel`（`engine.rs:717-727`）：生效中轮盘的方向键归它；**临时轮盘的启用键无论是否生效都归它**（事件路径上它总被消费掉）。对账与事件路径收敛到同一口径，两者不会打架。

由此带来的两种"用户能直接感受到"的行为：

1. **松开启用键的瞬间**，仍被按住的 `Hold` / 系统键立刻补上触点——不需要松手重按一次；
2. **按下启用键的瞬间**，已经按着的方向键立刻推动摇杆——同样不需要重按。

### 3.1 总开关键 → 所有功能的使能门

`engine.rs:1404-1487`。判定位于事件循环中**非常靠前**的位置，且不受 `enabled` 影响（因为它在 `if !enabled { continue; }` 之前），所以"关"和"开"都能被它捕获。**第二轮起它只认上升沿**（`ev.code == toggle_key && fresh_press`）：自动重复送来的后续 KeyPress 一律不算——否则长按 F8 半秒会翻转十几次，用户看到的是"按了没反应 / 状态跟自己以为的不一样"。

```mermaid
flowchart TD
    T0["ev.code == toggle_key && fresh_press<br/>（上升沿：只认按下的那一瞬间）"] --> T1["g.enabled = !g.enabled<br/>+ notify: 『映射已开启/已关闭』"]
    T1 --> T2{"变为关?"}
    T2 -->|"是"| T3{"控制通道在线?"}
    T3 -->|"在线"| T4["① aim_lift: 抬起瞄准触点 3000<br/>并清零 ox/oy、清 last_motion"]
    T4 --> T5["② 遍历全部 binds:<br/>fingers.release(idx) 成功 → touch_up(1000+idx)"]
    T5 --> T6["③ active_android_keys.drain()<br/>逐个 ctl.key(false, kc)"]
    T6 --> T7["④ 每个已落下的轮盘:<br/>touch_move 回圆心 → touch_up(2000+j)"]
    T7 --> T9["fingers.free_all()<br/>所有 WheelState: down=false, pressed=[false;4], active=false"]
    T3 -->|"不在线"| T8["只做本地清理<br/>active_android_keys.clear() + aim_release_local()"]
    T8 --> T9
    T2 -->|"否(重新开打)"| T10["aim.released = false<br/>恢复鼠标捕获"]
    T10 --> T11["sync_structures: 结构变了先抬旧触点再重建<br/>reconcile_binds + reconcile_wheels:<br/>按 Held 把此刻仍按着的键补回来"]
    T9 --> TC["continue: 本次事件不再走后续任何分支"]
    T11 --> TC
```

要点：

1. **共四处释放**，缺一不可：瞄准触点（否则松手后仍按在屏幕上）、绑定触点、系统键（否则设备上"返回键"一直处于按下）、轮盘触点。轮盘触点释放时先 `touch_move` 回圆心再 `touch_up`（`engine.rs:3914-3925`），与 `deactivate_wheel` 保持同一手法。释放完还会把 `live.pointers` 之类状态一并复位。
2. **无控制通道时也做本地清理**（`engine.rs:2041-2048`）：`active_android_keys.clear()` + `aim_release_local()`，再加 `fingers.free_all()` 与轮盘状态复位（含临时轮盘的 `active = false`）——本地状态绝不能残留，否则重新连上后会立刻注入一批错误的 UP。
3. **重新开启不只是复位 `aim.released`**（`engine.rs:3153`）：还会先 `sync_structures` 再 `reconcile_binds` + `reconcile_wheels`，**按物理按键状态补回触点**——所以你按住 W 再按 F8 开打，摇杆会立刻生效，不需要松手重按。
4. **总开关键本身不会落到绑定流程**：末尾的 `continue` 保证它不可能同时被当成普通绑定（即使配置里存在 `key == toggle_key` 的绑定，也不会生效）。
5. **总开关键与其它门控的相对顺序**：瞄准门控键（3.4）和 Ctrl+Alt（3.5）的处理都在它之前，而 `held.set` 与 `rising_edge` 又在它们之前（`engine.rs:837-839` vs 门控 `engine.rs:2841-2845`、Ctrl+Alt `engine.rs:3037-3052`）。因此若把 `hold_key` 与 `toggle_key` 设成同一个键，一次按下会**先**置 `gate_down = true`、**再**翻转 `enabled`。
6. **顶栏按钮走同一条收尾路径**（`app.rs:8615`、`engine.rs:2376-2413`）：按钮只置 `Shared.toolbar_release = true`（引擎按上升沿取一次），由引擎在下一轮执行**同一份** `release_all`（`engine.rs:1983-2061`）。早期版本按钮直接改 `enabled`，长按触点会永久留在屏幕上——这条已在 2026-09-19 那轮修复，第二轮未变。
7. **每次开/关都留一句话**（第二轮）：翻转 `enabled` 的同一处会 `notify` 一条"映射已开启(总开关键 \<键名\>) / 映射已关闭并抬起全部触点(\<键名\>)"（`engine.rs:3075-3083`；键名由 `key_name` 现场取，Linux 上形如 `KEY_F8`、Windows 上形如 `KeyF8`）——以前这一步在界面日志里**一点痕迹都没有**，用户只能靠反复按总开关键试。

### 3.2 临时轮盘的启用键 → 方向键归属切换 → 冲突绑定强制释放

流程见 `engine.rs:3396-3467`：

| 模式 | 按下启用键 | 松开启用键 |
|---|---|---|
| `TempMode::Hold` | `wheels[j].active = true` + `release_conflicting_binds(...)` | `deactivate_wheel(...)`（释放触点 + 清四方向位 + `active = false`） |
| `TempMode::Toggle` | **只在上升沿**（`fresh_press`）翻转：若已激活 → `deactivate_wheel`；否则 `active = true` + `release_conflicting_binds` | 无动作（自动重复不算"再按一下"） |

无论哪种模式，命中启用键后都会 `consumed = true` → `continue`，**启用键自身绝不会继续走到方向键或普通绑定流程**。

**关键的一步：切换之后立刻对账。** 两种模式在改变 `active` 之后都无条件执行一次 `reconcile_binds` + `reconcile_wheels`（`engine.rs:3415-3462`）。这一句同时修掉两个方向上的问题：

- **停用**：启用期间按着的 `Hold`/系统键在事件路径上收不到任何东西（那个键一直被启用键分支或轮盘方向键分支消费），对账会按 `Held` 把它们**补按回来**——所以"松开启用键的瞬间，原来按着不放的键立刻恢复功能"，不必松手重按（这是用户明确反馈过的痛点："松开启用键后，那个键必须松开手一次才能触发。战场是瞬息万变的"）；
- **启用**：对账会把已经按着的方向键立刻写成"按下"，摇杆当场开始推。

`release_conflicting_binds` 的必要性（`engine.rs:3929-3973`）——它遍历所有 `key ∈ {up, down, left, right}` 的普通绑定，把 `AndroidKey` 从 `active_android_keys` 移除并补发 `key(false)`，其余类型则 `fingers.release(i)` 后补发 `touch_up`。原因有两条，缺一都会出问题：

1. **防止触点永久卡死。** 绑定列表与轮盘列表彼此独立、没有任何唯一性约束，同一个键完全可能既是一条普通绑定的 `key`，又是某个临时轮盘的方向键。启用轮盘后，该键的事件在"方向键"分支就被 `handled = true; continue` 吃掉（`engine.rs:3469-3512`），普通绑定**永远收不到自己的 UP**——若它此前已经按下，触点就会一直落在屏幕上。
2. **防止普通绑定抢占方向输入。** 即使触点是在启用之前落下的，它依然是一个真实存在的设备触点：游戏看到的是"多了一根手指按在别处"，方向输入可能被判给错误的触点。

需要明确的是：**强制释放只在"启用瞬间"发生一次**。启用期间继续按方向键，事件只会走轮盘分支，普通绑定既不会 DOWN 也不会 UP——这正是"启用期间方向键归摇杆"的实现方式。而"停用瞬间把仍按着的键补回来"由紧随其后的 `reconcile_binds` 负责（见 3.0）。

### 3.3 焦点 / 优先级顺序

事件在同一次迭代中按固定次序尝试匹配，先命中者 `continue`，形成严格的优先级链：

```
held.set + rising_edge(物理按键镜像 / 上升沿)  →  瞄准门控键 / Ctrl+Alt（旁路）  →  总开关键  >  临时轮盘启用键  >  生效中的轮盘方向键  >  普通绑定
```

| 序 | 判定 | 代码位置 | 命中后的行为 |
|---|---|---|---|
| — | `Held::set(code, pressed)` + `rising_edge(pressed, was_down)` | `engine.rs:837-839`（`rising_edge` 本体 `engine.rs:837-839`） | 记录物理状态并算出 `fresh_press`，**不终止流程**；这是后面所有对账与"按一下翻一次"判定的依据 |
| 0 | `aim.hold_key` 匹配 | `engine.rs:2841-2845` | 仅置 `gate_down`，**不 return**（旁路监听） |
| 0 | Ctrl/Alt + 双键同按 | `engine.rs:3039-3052` | 仅翻转 `aim.released`，**不 return**（且要求 `aim_captured` 为真） |
| 1 | `toggle_key`（**仅上升沿**） | `engine.rs:3066-3114` | 翻转 `enabled` + 留一条通知 + 释放/对账流程 → `continue` |
| 2 | 临时轮盘启用键（`Toggle` 模式**仅上升沿**） | `engine.rs:3396-3467` | 切换激活态 + 冲突释放 + 对账 → `continue` |
| 3 | 生效中轮盘的方向键 | `engine.rs:652-691` | `reconcile_wheels` 重算方向状态 → `continue` |
| 4 | 普通绑定 | `engine.rs:4214-4261` | 按 `Action` 分派；申请触点时带上 `reserved`，池满则留一条限流通知 |

四处细节值得单独记住：

- **"按一下翻一次"的键只认上升沿**（第二轮）：`rising_edge(pressed, was_down)` 就是 `pressed && !was_down`，判定依据是 `held.has(code)`（`engine.rs:5999`）。自动重复的后续 KeyPress 会被这行挡掉——单测 `rising_edge_ignores_key_auto_repeat`（`engine.rs:5999-6009`）把这条锁死。
- **方向键分支只考虑"生效中"的轮盘**：`let engaged = w.temp.is_none() || wheels[j].active;`（`engine.rs:3476`）。未激活的临时轮盘方向键会**穿透到普通绑定**——这正是"临时轮盘没启用时，WASD 还能当普通键用"的原因。
- **方向键分支不会 `break`**：`handled` 用 `any()` 遍历所有生效轮盘，只表示"本次事件已消费"。因此**多个生效轮盘共用同一个方向键时会被同时驱动**，会同时落下多个轮盘触点（并一起争那 10 个名额）。这是配置层面需要避免的（代码中未见任何重复键校验）。
- **瞄准门控键的"特殊处理"就是"不特殊处理"**：它只在 `engine.rs:2841-2845` 记一次状态，之后**照常**参与总开关键、轮盘与普通绑定的匹配。用右键当开镜门控的同时，右键仍然可以被绑定成一个普通动作——这是刻意的旁路设计，不是遗漏。

> **W2-3(2026-10-06)**:表中第 2~4 行(临时轮盘启用键 / 方向键 / 普通绑定)的主干已抽成 `engine::dispatch_input`(`engine.rs:3379-3588`),`run()` 只留调用点(`engine.rs:3312-3332`),三行给出的行号即抽取后的位置;判定顺序与"命中即 `return true`(调用方 `continue`)"的消费语义保持原样。本表第 0/1 行的行号将在 W2-4 的"行号重锚"里统一刷新。

### 3.4 瞄准门控键的状态机

`gate_down` 只有两个写入点：`engine.rs:2843-2845`（跟随门控键的按下/抬起）与 `AimState::default()`。它向外影响三处：

1. `aim_active`（`engine.rs:1191-1196`）——不满足则 `aim_on_motion` 直接返回，位移被丢弃；
2. 鼠标捕获条件（`engine.rs:1191-1202`）——`hold_key != 0` 时只在按住期间捕获，松手立刻把光标还给系统；
3. 界面自检文案（`app.rs:9106-9113`）——"已就绪，但需按住 X 时才会转动视角"。

`Aim::anchor_set()` 以 `abs > 1e-6` 为判据（`keymap.rs:1365-1367`），所以 `(0,0)` 是"未设置"的哨兵值。升级路径已删，该哨兵值现只承担"未设置"判定本身。

### 3.5 鼠标捕获与 Ctrl+Alt 交还

| 状态 | `aim.released` | `mouse_grab` | 效果 |
|---|---|---|---|
| 正常瞄准 | `false` | `true` | 光标隐藏、位移持续累积 |
| 按下 Ctrl+Alt | `true` | `false` | 光标立刻归还系统，瞄准停止（`aim_active` 为假） |
| 再按 Ctrl+Alt | `false` | `true` | 收回 |
| 映射关闭 / 通道断开 / 锚点未设 / 门控未按 | 任意 | `false` | 绝不出现"光标被冻结但什么都做不了" |

`ctrl_alt_chord`（`engine.rs:203-205`）要求"按下的那一方是 Ctrl 或 Alt，且两者都在按住状态"，因此**一次组合只切换一次**，按住不放不会连发（`ctrl_alt_chord_fires_once_per_press`，`engine.rs:5900`）。且该分支被 `aim_captured = aim.enabled && aim.capture_mouse && aim.anchor_set()` 守卫（`engine.rs:5900-5915`、`engine.rs:3046-3052`）——不打算捕获鼠标时，Ctrl+Alt 不会被本程序改状态。

### 3.6 轮盘半径 / 影响范围 → 触点位移距离

```mermaid
flowchart LR
    R["Wheel::radius<br/>相对值"] --> ML["Mapper::len<br/>按屏幕宽度换算"]
    S["Wheel::scope<br/>默认 1.0, clamp 0.2..=4.0"] --> MUL["×"]
    ML --> MUL
    MUL --> WR["push_px = 实际推出距离(像素)"]
    WR --> U1["update_wheel: 斜向 ×1/√2 归一化<br/>tx = wx + round(fx × wr)"]
    WR --> U2["reserved >= 10 ? 放弃并计数 : touch_down"]
    R --> OV1["draw_overlay: 实线/虚线圆环<br/>r = m.len(radius) × scale"]
    WR --> OV2["与半径相差 > 1px 时:<br/>橙色虚线外环 r = push_px × scale"]
```

- **改造前**：`radius` 一个量同时决定浮层圆环与手指推出距离，二者被绑死。
- **改造后**：`radius` 仍然单独决定圆环（`app.rs:7678`），`scope` 只乘在注入距离上（`Wheel::push_px`，`keymap.rs:1043-1045`；消费点 `engine.rs:5084`）。于是"响应范围圈"与"触点实际可达范围"解耦。
- **为什么必须画那个橙色虚线外环**：解耦之后，光看圆环已经无法判断手指到底能推多远，调试时极易误判（"我把圈画得跟游戏摇杆一样大，为什么判定成反方向？"）。外环把不可见的注入距离重新变成可见的，并在标签里显示像素值与倍数，方便与游戏里真实摇杆的判定圈直接对照。**第二轮起这圈虚线也先垫一层反相粗虚线**（`app.rs:7714-7725`），免得它压在亮/暗画面上时消失。
- **与响应范围的耦合关系**：`scope` 不改变"哪个区域算命中"——它只改变推杆幅度。取点、改范围（Ctrl+`+/-`、拖动圆圈）操作的都是 `radius`；`scope` 走独立的 DragValue。两者在同一个轮盘行里并排显示，像素值 `= m.len(radius) × scope` 由界面即时算出，供对照。
- **与浮层过滤的耦合**：外环属于轮盘的一部分，随 `OverlayFilter` 一起显示/隐藏——选 `永久摇杆` 时只对 `temp == None` 的轮盘画外环，选 `临时摇杆` 时反之（筛选逻辑见 `app.rs:475`）。**第二轮新增的摇杆信息卡同样受这层过滤管辖**（它画在轮盘那一趟循环里，`app.rs:475`）。
- **与旧配置的耦合**：无该字段的 JSON 反序列化得 `1.0`，注入距离与改动前逐像素一致；任何坐标换算都不涉及 `scope`（升级路径已删，像素配置走 `legacy` 直通）。
- **与触点池的耦合**：推出距离变大不会多占触点（每个轮盘始终只占 1 个），但"要不要落下这个触点"要先过 10 个名额的预算（见 3.0）。

### 3.7 坐标单位 Rel/Pixel → Mapper → 四条出口的一致性

`Mapper` 是**唯一**做坐标换算的地方（`keymap.rs:148` 的文档注释明确写了这一点），四条出口全部经由它：

| 出口 | 位置 | 用到的方向 |
|---|---|---|
| ① 注入 | `engine.rs` 各处（`bind_point`、`Tap`/`Hold`、`Swipe` 起终点、`update_wheel` 圆心与半径、`aim_anchor` / `aim_target`） | 配置值 → 像素（`point` / `x` / `y` / `len`） |
| ② 绘制 | `draw_overlay`（`app.rs:7351` 构造、`app.rs:7390-7392`、`app.rs:7428-7429`、`app.rs:7504-7506`、`app.rs:7536-7537`、`app.rs:7614-7615`） | 配置值 → 像素，再乘浮层缩放 `scale` |
| ③ 取点 | `assign_coord`（`app.rs:2047`） | 像素 → 配置值（`rel_x` / `rel_y`） |
| ④ 界面显示与编辑 | `ui_binds`（`app.rs:4240-4245`）、`ui_wheels`（`app.rs:6970-7325`）、`ui_aim_body` | 双向：显示时 `x/y/len`，写回时 `rel_x/rel_y/rel_len` |

一致性由三点保证：`legacy` 开关只在 `Mapper` 构造时决定；`CoordUnit` 只由 `format_version` 推导；任何新增的坐标字段都必须同时接进这四条出口。**`DraftBind` 是唯一的例外**——草稿坐标刻意保持像素（`app.rs:674` 的注释），只在提交时换算，因为草稿还没有"正式单位"的语境，用像素最直观。

**第一轮新增的一条纪律（画布坐标空间）**：②这条出口用的屏幕尺寸来自 `PadApp::screen_size()`（`app.rs:8045-8058`），它**优先取截图尺寸**，取不到才退回控制通道尺寸。原因是控制通道尺寸会在"连接控制 / 手机转屏 / 后台刷新"时变化，而浮层是画在截图上的——用会变的尺寸去画一张不变的图，观感就是"同一个摇杆毫无征兆地突然变大/移位"。注入仍按控制通道尺寸单独计算（`inject_space()`，`app.rs:8062-8068`），两者**纵横比**不一致（偏差 >2%）时——这就是"手机转过屏"或"截图是上一次方向拍的"——取点面板给出醒目提示并**禁用取点**，附两个点击才生效的一键按钮（[以截图为准(重设坐标空间)] / [重新查询屏幕尺寸]）；对齐后提示与禁用自动消失。判定在 `space_mismatch`（W2-2，2026-10-06），拒绝入口在 `begin_pick` 与画布点击两处，详见 3.9。画布缩放系数也只依赖窗口高度与截图尺寸（`app.rs:10394-10405`），不再用"当前剩余高度"，否则右侧多出一行设置就会让整张浮层跟着缩放。

**第二轮在这条纪律上再加一层（④ 的取档也走同一张图）**：`draw_overlay` 的每个标注不再共用一个亮度档位，而是用 `tone_at(sx, sy)` **按它自己所在的截图像素**去查 `LumaGrid`（`app.rs:722`）；也就是说"圈画在哪张图的哪个位置"与"这一处该用深色还是浅色"用的是**同一套坐标**（都由截图尺寸派生的 `Mapper` 给出）。新增的摇杆信息卡命中判定（`wheel_at`，`app.rs:10680-10703`）同样以画布空间换算圆心与半径，因此"看到的位置"与"点得到的位置"一致。


关键约束：

- **只校正坐标空间，绝不改动已取好的坐标**（`app.rs:8178-8202` 的设计说明）。手机临时切到别的方向再切回来，配置必须原样可用。
- **坐标空间同步必须发生在任何注入之前**：连接成功后立刻 `sync_display_space`（`app.rs:8183-8202`），避免出现"按错误单位注入"的中间态。（v1→v2 升级路径已按 O-7=B 删除：格式不匹配一律直通、不换算，这条时序现只与屏幕方向变化有关。）
- **格式版本不匹配一律直通（O-7=B）**：v1→v2 自动升级路径已删除——像素坐标配置永远经 `Mapper::legacy` 直通使用，程序不做任何坐标换算，也就不会把用户辛苦调好的布局算坏。
- **锚点超界由注入前钳制兜底**：方向变化后锚点可能落在当前空间之外，`aim_anchor` 会把它钳进屏幕（`engine.rs:1478-1494`，回归测试 `aim_target_clamps_anchor_into_screen`，`engine.rs:5831-5844`），界面同时给出提示（`app.rs:9070-9076`）。
- **第二轮补上的第四条入口：空闲后自动重查**（`engine.rs:3054-3066` + `app.rs:3631-3637`）。`last_key_at` 记录"上一次按键"的时刻，空闲 **≥3 秒**后的第一批按键会把 `pending_space_recheck` 置位，在循环顶部（已经持锁处）写成 `Shared.space_recheck = true`；界面每帧取走并重新查询一次。**这条入口的意义不在"又一个刷新点"，而在于它解释了用户的现象**：以前只有"连接 / 截图 / 关开映射"三条路会刷新坐标空间，而用户"切到别的窗口待一会儿再回来"时唯一会碰到的就是"关一次开一次映射"——刷新恰好发生在那一刻，于是看起来像开关本身的毛病。现在引擎自己会在空闲后第一次按键时补上这次确认（同样是**只改空间、不改坐标**）。

```mermaid

    SCH -->|"到期时 lock: 取 control 注入"| SH
    DRW -->|"lock: 读 profile 绘制"| SH
```

**锁的约束（三条硬规则）**：

1. **`PadApp::mapper()` 会自锁**（`app.rs:8101-8104` 的注释原文点名了这一点）。它内部先 `self.shared.lock()` 读 `coord_unit`、再调 `self.screen_size()`（同样要锁，`app.rs:8045-8058`），最后构造 `Mapper`。因此**任何已经持有配置锁的地方，都必须改用 `Profile::mapper(space)`**（`keymap.rs:1417-1419`，纯构造、不加锁）。代码里的正确示范：`assign_coord` 在加锁前先 `let m = self.mapper();`（`app.rs:2049`）；`ui_binds` / `ui_wheels` 同样在 `self.shared.lock()` 之前取好 `m`（`app.rs:4681`、`app.rs:7162`、`app.rs:7305`）；`ui_picker` 与自检面板里则改用 `g.profile.mapper((w, h))` / `g.profile.mapper(space)`（`app.rs:10481`、`app.rs:10596`、`app.rs:10615`）；`draw_overlay` 的注释直接把"先构造 Mapper 再加锁"写成了硬要求（`app.rs:7360-7361`）。
2. **`format!` 里不要出现两次 `lock()`**。`app.rs:2502` 的注释记录了这个坑："先取数、释放锁，再 log：避免 format! 参数里两次 lock 死锁"。同类风险存在于任何"在持锁表达式里调用另一个也会加锁的方法"的写法。
3. **持锁期间不能压撤销栈**。`push_undo()` 自己会加锁（`app.rs:2263-2266`），所以持锁的 UI 代码只能用 `push_undo_snapshot(before)`，并把 `before` 快照留到帧末统一入栈（`pending_undo` + `undo_frame_marked`，字段声明 `app.rs:1020-1023`，帧末入栈 `app.rs:4108-4119`）。

**可见性方向**：界面是 `profile` 的唯一写入者（除了引擎不再写入配置），引擎是 `aim_live`、`live`、`notices`、`space_recheck`、`control` 与 `enabled`（由总开关键触发的那一路）的写入者；`control` 由 UI 挂载（连接成功后写、断开时置 None），引擎只读。**第二轮新增的 `notices` / `space_recheck` 是"引擎写、界面每帧取走"的一次性信箱**：引擎侧的写点常常同时借着 `control` 与 `profile`，所以 `notify` 只接受 `&mut Vec<String>`（借一个字段而不是整个 `Shared`），攒不下时先放进循环局部变量、在循环顶部（已经持锁处）统一落账（`engine.rs:823-828`、`engine.rs:2145-2149`、`engine.rs:2582-2585`）。这个"单一写入者"格局是避免竞态的根本原因。

- **推导方向是"三向互补 + 目录优先"**：任一非空就足够，只填空缺项，绝不覆盖用户已填的值；`scrcpy_dir` 是"最自然的那一个"——只填它，程序会先在目录里找出 exe，再自动补齐另外两个。

- **自动刷新设备**：只在"生效 adb"真的变化时刷新，避免每帧跑 `adb devices`。
- **路径记忆与落盘**：`save_settings_now`（`app.rs:2857-2879`）在"选完路径/目录、点[应用]、[自动寻找全部]、勾选[记住路径]"这几处立刻写盘并打日志确认（调用点见 `app.rs:2857`、`app.rs:3476`、`app.rs:3482`、`app.rs:8319`、`app.rs:8358`）；其余改动由帧末的 `remember_now()` + `persist_settings()`（`app.rs:2884-2888`）统一收尾。**即使关掉了[记住路径]也照样登记**——开关状态本身也是设置的一部分，早退会导致"我明明关掉了，下次启动它又自己打开了"。
- **连接链路的完整推导**：`[连接控制]` → `resync()` → `serial()` → 后台线程里 `adb::display_size` → `adb::start_control_server`（push server → forward → `app_process` 启动 server）→ `ControlClient::connect` 重试 20 次（每次间隔 150ms）→ 成功后 UI 侧 `sync_display_space`。断开时 `ControlServer::drop` 会 `kill` 子进程并 `adb forward --remove`（`adb.rs:639-668`）。
- **假连接防护**：`ControlClient::connect` 必须读到 1 个 dummy 字节，否则报"设备侧 socket 未就绪(EOF)"。没有这一步，`adb forward` 造成的"本地 TCP 握手成功"会被误判为连接可用。

### 3.14 宏组 → 十指预算 / 组合键 / 结构指纹（2026-10-06 W2-8 起）

- **宏与十指预算（唯一共享资源）**：宏触点数 `macro_down.len()` 计入 `live.pointers` 与所有 `reserved` 求和（`engine.rs:2245-2250`、`engine.rs:3547`、`engine.rs:3275` 等 12 处），落指前先查"宏 + 其它 lane < 10"（`engine.rs:2329`）。挤不下时**跳过该步**并给一句节流提示（每秒最多一条，`engine.rs:2330-2342`），**不静默、也不顶掉用户自己的触点** —— 这是用户点名的冲突 (a) 的处置。
- **宏与组合键**：宏的**触发键**和普通键位一样参与"键位组合"切换（不同组合里的宏互不串用）；但宏内部的动作**不再回到 `combo_gate`** —— 0.1.5 让录制步骤重新进入派发链路，正是"录了点击+滑动、回放不出来"的根因（W2-8 结构性删除 `SchedAct::MacroButton`）。宏内部要按组合键，用设置宏的 `combo` 指令（它同样被展成"逐个按下 → 持续 → 逐个抬起"，不经过组合门控）。
- **宏与结构指纹 / 归属对账**：宏触点不进 `held` 物理按键镜像，因此 `sync_structures` / `reconcile_binds` 的"结构变化先抬手"对账不会抬掉宏按着的触点；换键位方案时 `apply_scheme_switch` 把宏触点计入总量（`macro_extra` 参数），**宏不因换方案被取消**。宏的取消只发生在三个明确时点（见 2.12）。
- **宏与坐标取点**：宏的 `click` / `swipe` 指令坐标可在宏页用截图取点（`CoordSlot::MacroClickPoint` / `MacroSwipeStart` / `MacroSwipeEnd`，`app.rs:6375`、`app.rs:6359-6437`），复用与键位同一套取点面板（`begin_pick`）；虚拟键盘编辑器与宏展开编辑器里的取点按钮**不开放**（它们编辑的是克隆，写了也存不回去）。
- **宏与界面风格**：宏页（`RightTab::Macro`）在两种风格里都在（默认风格：键位 / 宏 / 摇杆 / FPS / 其他；可视化：键位 / 宏 / FPS / 其他，`app.rs:312`）；可视化风格的虚拟键盘里宏键用独立青绿色，点击宏键打开宏编辑、不会像空闲键一样新建普通键位；**只有可视化风格的宏页带自己的虚拟键盘**，默认风格只保留物理键录制/设置。

### 4.9 宏组

| 限制 | 说明与代码位置 |
|---|---|
| 录制只记按键，不记鼠标移动 | `MacroStep { code, pressed, delay_ms }`（`keymap.rs:474`）没有坐标/位移字段：录的是键盘与鼠标**按键**的按下/抬起时序，鼠标移动不会被录进去 |
| 录制空闲自动收尾，上限 2000ms | 宏页"空闲停止"滑杆范围 `100..=2000`（默认 800，`app.rs:5480-5481`）。想录一段"中间停 3 秒"的时序做不到 —— 停顿会被提前判定为录制结束 |
| 宏没有长按语义 | 录制步骤是**字面时间线**（按下…抬起原样重放），设置步骤一律"按下 → 持续 → 抬起"。`MacroKeyMode` 与 `Key` 指令的 `mode` 字段已随 W2-8 从数据模型删除；旧配置里的 `mode` 被 serde 忽略（全仓无 `deny_unknown_fields`，加载不报错，见 `keymap.rs:418`） |
| 只有按键/组合键/轮盘步骤受虚拟层重解释 | 扩展宏存在时，录制步骤与 `key` / `combo` / `wheel` 指令按虚拟层解析；`click` / `swipe` / `fps` / `delay` 是绝对坐标与绝对动作，不受虚拟层影响 |
| 虚拟层里的轮盘"并不存在" | 它不会真的驱动一个摇杆（设备上没有这个摇杆），而是展开成**一次推离手势**（`live_wheels = virtual_ctx.is_none()`，`engine.rs:4395-4397`） |
| 触点号按执行实例分段，实例号 8 段循环 | `pid = 7000 + (exec % 8) × 4096 + slot`（`engine.rs:4284-4288`、`MacroPlan` 的文档注释）：**同一个宏连续触发第 9 次会回到第 1 段的 pid 空间**。上一轮宏早已结束时不相干；只有"同一宏被触发 9 次以上、且每轮都还没跑完"才理论上有 pid 段复用（单实例内不复用 slot） |
| 十指挤不下就跳过该步 | 宏落指前查 `macro_down.len() + 其它 lane < DEVICE_MAX_POINTERS`（`engine.rs:2329`）；落不下时**跳过这一步**并给节流提示（每秒最多一条），不排队、不抢占用户触点 |
| 嵌套只走显式的宏指令 | `Action::Macro` 绑定在宏内部**不**展开（`emit_action_press` 的 `Action::Macro(_) => None`，`engine.rs:4906`）；要嵌套就显式加 `macro` 指令，子宏未自带虚拟层时继承父宏的（`inherited_virtual`，`engine.rs:4387`） |
| 宏的取消不是"回滚" | 取消只保证**抬起已落下的触点**（按最近位置，`macro_down`，`engine.rs:3760-3795`）并清掉排程；已经注入过的触摸/系统键不会被撤销（设备端没有"撤销"这回事） |
| 录制事件默认折叠 | 宏页默认只显示"事件数 / 约时长"摘要，需要排查时展开 [显示录制事件] 看逐条（`macro_summary`，`app.rs:11708`）——长时序不会把界面撑爆 |
